# Phase 1 — PoC: 수직 슬라이스 하나를 끝까지

## 목표

**클래스 1개**에 대해 "테스트 생성 → 샌드박스 실행 → 통과"가 끝에서 끝까지 도는 것.
그리고 그 과정에서 발견한 문제·개선점을 `docs/poc-findings.md`로 남기는 것.
PoC의 산출물은 코드 절반, 리포트 절반이다.

## 범위

**포함 (M0 → M3 순서 고정)**

- M0 스캐폴딩: 리포 구조, `test_layering.py`, Fake 어댑터. 관문: `pytest`가 Java·Docker 없이 통과
- M1 Java 어댑터 최소: 프로젝트 탐지, `dependency:go-offline` 2단계 샌드박스. 관문: 네트워크 차단 컨테이너에서 `mvn -o test -Dtest=...` 통과
- M2 `llm/` 계층: 게이트웨이 클라이언트 + record & replay. 관문: 카세트 재생으로 결정적 테스트
- M3 도구 6개 + 테스트 작성 서브그래프(LangGraph). 관문: 대상 클래스 1개에 테스트 생성 → 샌드박스 통과
- **컨텍스트 최소본**: 구조가 비슷한 기존 테스트 찾기(few-shot 검색)의 **파싱 기반** 버전 — 프로젝트의 기존 테스트를 파싱해 대상 메서드와 형태(입력 개수·예외 유무)가 닮은 것을 골라 프롬프트에 예시로 첨부. 산출물 양식 1.3(데이터·메모리)의 실물이 되고 M3 생성 품질에도 기여한다

**제외 (스텁으로 대체)**

- Neo4j 실물 — `query_code_graph`는 인터페이스만 정의. 단 쿼리 중 "비슷한 모양의 테스트는?"만 위의 파싱 기반 최소본으로 응답하고, 나머지 쿼리는 "그래프 없음: inspect_target을 쓰라" 문자열 반환
- 변경 추출·의도 분류·조치 결정 파이프라인 — PoC는 "새 테스트 생성" 경로 하나만 하드코딩
- 품질 게이트 — assert 검사 1종만 최소 구현(수정 전후 assert 노드 수 비교 수준), 나머지는 2단계
- interrupt 실연결 — 서브그래프에 interrupt 지점은 **골격으로 넣되**, PoC에서는 자동 "계속" 응답 스텁

## PoC여도 지키는 것

- R1(층 분리)·R7(llm/ 경유)은 첫 커밋부터. "PoC니까 나중에"는 이 프로젝트의 1번 실패 패턴이다 — PoC 코드가 그대로 2·3단계의 뼈대가 된다
- 프롬프트는 파일로 분리(`llm/prompts/`). 코드에 f-string으로 흩뿌리지 않는다
- 도구 반환은 예외가 아니라 모델이 읽을 문자열 + 길이 상한. PoC부터 이 형태로

## 1주차에 반드시 확인 (설계의 미확정 3건)

1. 게이트웨이 임베딩 API 제공 여부  2. Neo4j 별도 구동 가능 여부(사내망)  3. 모델별 tool calling 지원 여부 → 미지원 시 JSON 파싱 폴백 확정
결과를 `docs/poc-findings.md`에 기록한다.

## 산출물 — 제출 양식을 역산해서 쌓는다

1단계 제출물은 회사 양식(핵심 구현 내용 / 문제 해결·리서치 / 핵심 동작 검증)을 따른다.
`docs/poc-findings.md`는 그 **원재료 축적 파일**이며, 양식에 바로 흘려 넣을 수 있게
아래 틀을 쓴다. `/poc-report` 명령이 이 틀을 만든다.

```
## 구현 내역 (→ 양식 1. 핵심 구현 내용)
   워크플로우 / 도구·함수 연동 / 데이터·컨텍스트 세 항목으로 나눠,
   각각 [구현 기능 / 동작 원리 / 주요 기술]을 완성 시점마다 3~4줄로 기록
   - 워크플로우: LangGraph 서브그래프, 상태 정의, interrupt 골격
   - 도구: 6개 도구, 문자열 반환 + 길이 상한, 샌드박스 실행
   - 데이터·컨텍스트: 파싱 기반 few-shot 검색, 프롬프트 관례 주입, record & replay
## 문제·리서치 로그 (→ 양식 2. 문제 해결 및 기술 리서치)
   막힌 것마다 [이슈 구분(프롬프트/도구 연동/샌드박스/성능) | 문제와 원인 |
   리서치 출처(URL·문서명) | 적용한 해결 | 전후 변화]를 그 자리에서 기록.
   ⚠️ 리서치 출처는 나중에 복원이 안 된다 — 참고한 순간 적는다
## 검증 캡처 (→ 양식 3. 핵심 동작 검증)
   골든 케이스 1개의 [입력 명령 | 도구 호출 순서(트레이스에서 발췌) | 최종 결과]를
   실제 출력으로 보존. 해당 카세트를 evals/golden/에 커밋해 재현 가능하게
## 설계 수정 필요 — v4 문서·ADR과 다르게 가야 하는 지점 + 이유 (→ ADR 후보)
## 2단계 반영 목록 — 우선순위 순, 각 항목에 "왜" 한 줄
## 측정 메모 — 토큰/시간/재시도 횟수 대략값
```

**검증 캡처 팁**: record & replay 카세트에 도구 호출 순서가 그대로 남는다.
양식의 "에이전트 동작 1→2→3"은 카세트·트레이스에서 발췌하면 된다 — 별도 기록 불필요,
단 골든 카세트를 지우지만 않으면 된다.

## 이 단계에서 흔한 실수

- 성급한 추상화 — 빌드 시스템 인터페이스를 만들지 않는다. Maven 하나뿐이다
- 카세트 없이 실호출로 테스트를 돌려 놓고 "테스트 있음"이라 보고
- 샌드박스 워밍업 생략 — `go-offline`은 일부 의존성을 빠뜨린다. 준비 단계에서 실제 테스트 1회 실행으로 캐시를 완성
- PoC 범위 확장 — "그래프도 금방인데" 금지. 발견은 리포트에 적고 2단계로 넘긴다
