# Phase 3 — E2E 서비스: 남이 쓸 수 있는 물건으로

## 목표

개발자(나 아닌 사람)가 설치 가이드만 보고 자기 프로젝트에 돌릴 수 있는 상태.
데모 시나리오 2개가 처음부터 끝까지 매끄럽게 도는 것.

## 범위 (M8)

- **CLI 완성**: 새 테스트 생성 / diff 기반 유지보수 / escalate 응답(resolve) / 변경 diff 확인 / apply / 리포트 출력. 종료 코드 3종(성공·사람 확인 필요·실패)을 CI에서 쓸 수 있게
- **MCP 서버**: Claude Code 등에서 도구로 호출 가능하게. CLI와 같은 core를 공유(로직 중복 금지)
- **장기 기억**: escalate 해결 시 판단 메모 자동 기록(상황·결정·이유·코드 위치), 임베딩 검색으로 유사 판단을 프롬프트에 첨부. **참고용일 뿐 경로표를 우회하지 못한다** — 이 불변식의 테스트 포함. 게이트웨이가 임베딩 API 미제공이면 키워드 검색으로 강등하고 문서에 명시
- **대화 압축**: 원문 유지(규칙·현재 테스트 코드·직전 실패) / 요약 대상(오래된 도구 출력·폐기 시도, 단 "실패했다는 사실"은 유지) 구분 구현
- **설정 파일**: 커버리지 기준치, 재시도 상한, 반복·비용 예산, 모델 선택. 기본값은 v4 문서와 일치
- **시크릿 점검**: 게이트웨이 토큰은 환경변수만, 샌드박스에 미전달, 로그 마스킹 — 3개 모두 테스트로 고정
- **UX 다듬기**: 에러 메시지에 다음 행동 제시, escalate 메시지에 기대/실제/의심 지점 포함

## 데모 시나리오 — 발표의 뼈대

1. **콜드 스타트**: 테스트 없는 클래스 지정 → 생성 → 게이트 통과 → diff 확인 → apply
2. **유지보수**: 버그 수정 커밋 → diff 분석 → 재발 방지 테스트 추가 / 이어서 refactor인데 테스트가 깨지는 커밋 → escalate → 사용자 응답 → 재개
두 시나리오를 스크립트가 아니라 **문서화된 명령 순서**로 만들고, 녹화 전 3회 연속 성공을 확인한다.

## 이 단계에서 흔한 실수

- 기능 추가 유혹 — 3단계는 넓히는 단계가 아니라 **닫는 단계**다. 새 아이디어는 "향후 과제"로
- CLI와 MCP에 로직 복제 — 둘 다 core 호출 껍데기여야 한다
- 데모 직전 리팩터링 — 데모 시나리오 고정 후에는 게이트 통과 없는 변경 금지
