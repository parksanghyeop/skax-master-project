# 피드백 반영 계획 — PoC 산출물 보강 + 워크플로우에 스킬 붙이기

작성일 2026-09-06. 대상 문서는 `docs/제출자료/PoC구현.md`(요약본)와 `핵심구현.md`(상세본)다.

**진행 상태 (2026-09-06)**: §1의 A(10줄 요약)·B(최소 계약 §2.0)·C(실행 로그 원문 4건, PNG는 접힘)·D(3구역 표 §5) 반영 완료.
E(길이 조정)는 미착수. §2(스킬)는 제품 워크플로우 해석(①)으로 진행 — ADR-0017, 스킬 2개, 규칙 선택기,
단위 테스트까지 완료(2026-09-06). 전/후 측정은 Docker·게이트웨이가 있는 환경에서(작업목록 B-1 5번).
멘토 확인 질문 1번 답이 ②(개발 스킬 어필)라면 산출물에 한 단락 추가로 대응한다.

피드백 출처 두 곳.

| 출처 | 핵심 메시지 |
|---|---|
| AI 멘토 | 설계·구현 설명은 강하다. "실제로 무엇이 돌아갔는가"의 증거가 약하고, 계약·범위·요약이 흩어져 있다 |
| 사람 멘토 | 기술적 어필이 부족하다. 지금 워크플로우에 **스킬(skill)** 을 붙여 보라 |

## 0. 먼저 짚을 것 — 현재 문서 진단

AI 멘토가 "증거가 약하다"고 했지만 `PoC구현.md` §4에는 검증 6건(SC-001~004, 재생)이 표·단계·캡처로 이미 있다.
그래서 "없어서 약한 것"이 아니라 **"있는데 안 보이는 것"** 이 문제다. 원인 세 가지.

1. **증거가 전부 PNG다.** 콘솔 로그를 `render_capture.py`로 그림으로 만들었다. 사람은 확대해야 읽고, AI 검토자는 아예 못 읽는다. 검색도 안 된다.
2. **증거가 문서 뒤쪽에 있다.** §2 구조 설명 + §3 문제 해결 표(12행)를 지나야 §4가 나온다. 검토자는 그 전에 지친다.
3. **계약·범위가 흩어져 있다.** 상태 키와 필드는 `contracts.md`·`핵심구현.md` 여기저기에 있고, "완료/제한/예정"은 §5 한계 목록 한 덩이로만 있다.

따라서 보강의 방향은 **새로 만드는 것보다 끌어올리고 텍스트로 바꾸는 것**이다. 재실행이 거의 필요 없다.

  - SC-002 `maintain` — 입력 diff 요약 → 의도 분류 JSON 원문(category/confidence/evidence) → 규칙표 행(`bugfix × none → create_test`) → 작성 루프 시도 1 실패(Mockito 오류 요지) → 시도 2 통과 → 게이트 6종 결과 한 줄씩(regression 포함) → 종료 코드 0

  1. `render_capture.py`가 읽은 원본 로그 파일이 남아 있으면 그대로 쓴다 (`.cta/` 또는 스크립트 입력 경로 확인).

  3. 로그는 다듬지 않는다. 길면 `...`로 가운데를 자르되 시작·판정·끝은 원문 유지.
- **검증**: 검토자가 이미지 없이 텍스트만으로 "입력 → 판정 → 액션 → 재시도 → 종료"를 따라갈 수 있는가. PNG는 보조로 남긴다.

## 2. 사람 멘토 피드백 — "워크플로우에 스킬 붙이기"

### 2.1 해석

"스킬"은 두 가지로 읽힐 수 있다. **멘토에게 확인이 필요하지만, 기술 어필이 목적이라면 ①이 본류**다.

| 해석 | 뜻 | 현재 상태 |
|---|---|---|
| ① 제품 워크플로우의 스킬 | 에이전트가 상황에 맞는 **지식 묶음(SKILL.md)** 을 골라 프롬프트에 싣는 구조. Anthropic Agent Skills 패턴(폴더 + 설명 + 필요할 때만 본문 로드) | 없음. 프롬프트는 `system.md`·`write_test.md` 두 파일 고정. `[프로젝트 관례] $style` 빈칸에는 `cli/generate.py`가 **"기존 테스트 스타일을 따른다" 고정 문장 한 줄**만 넣는다. 상황별로 달라지는 지식은 없다 |
| ② 개발 프로세스의 스킬 | Claude Code 스킬(`.claude/skills/phase1~3`)로 구현 단계를 구동한 것 | 이미 있음. 산출물에는 언급 없음 |

②는 한 단락으로 어필하면 끝난다. ①은 설계·구현·수치가 필요하고, 그만큼 어필이 된다.

### 2.2 왜 지금 구조에 스킬이 자연스럽게 들어가나

- `write_test.md`의 **`$style` 빈칸에 고정 문장 한 줄만 들어간다.** 스킬 본문이 들어갈 자리가 이미 뚫려 있는데 상황별 내용 없이 쓰고 있다.
- 재료 수집(`materials.py`)이 이미 **"mock이 필요한가, builder인가, 예외 분기가 있는가"를 결정적으로 세고 있다.** 이 결과가 곧 스킬 선택 조건이다.
- `ActionDecision.kind`(create_test / regression / resolve 재작성)가 **작업 종류를 이미 구분**한다. 종류별 스킬로 1:1 대응된다.
- 층 구조상 Java 지식은 `adapters/java/`에만 있어야 한다(R1). 스킬 파일을 어댑터 아래에 두면 **"새 언어 = 어댑터 폴더 + 스킬 폴더"** 로 확장 스토리가 완성된다.

### 2.3 설계 스케치 (구현 전 ADR-0016으로 먼저 기록)

**스킬 파일 위치와 형식**

```
cta/adapters/java/skills/
  junit5-mockito/SKILL.md        # 목 주입·@ExtendWith·when/thenReturn 관례, 흔한 컴파일 오류
  spring-slice-test/SKILL.md     # @WebMvcTest·@DataJpaTest 선택 기준, 컨텍스트 없이 단위로 푸는 법
  regression-test/SKILL.md       # 재발 방지 테스트: 버그 버전에서 실패해야 함, 이슈 번호를 테스트 이름에
  boundary-exception/SKILL.md    # 경계값·null·예외 확인 항목을 assert로 옮기는 패턴
  refactor-preserve/SKILL.md     # 리팩터링 대응: 기대값 불변, 실패 테스트 1건만 동작 기준으로
```

SKILL.md 머리에 `name`, `description`, `when`(선택 조건 키워드)을 두고, 본문은 300~600자로 짧게. 설명만 먼저 읽고 본문은 선택된 것만 싣는다.

**선택기 — LLM 없이 결정적으로 (R2 유지)**

| 신호 (이미 있는 데이터) | 선택되는 스킬 |
|---|---|
| 재료 수집: 의존 객체를 mock으로 판정 | junit5-mockito |
| 대상 클래스 어노테이션에 `@Service`/`@Repository`/`@RestController` | spring-slice-test |
| `ActionDecision.kind == create_test` 이고 `Intent.category == bugfix` | regression-test |
| 확인 항목에 경계값·null·예외가 1개 이상 | boundary-exception |
| `resolve` 재개 (허용 목록에 테스트 1건) | refactor-preserve |

선택기는 `adapters/java/skills/select.py` 한 파일. 입력은 재료 수집 결과 + `ActionDecision`, 출력은 스킬 본문을 이어 붙인 문자열. 이 문자열이 `$style`로 들어간다.

**core와의 경계**

- core는 스킬 내용을 모른다. 포트 하나만 추가한다: `SkillProvider.select(decision, materials) -> str`. Fake는 빈 문자열을 돌려준다.
- **도구를 늘리지 않는다**(R4). 스킬 로딩은 도구 호출이 아니라 프롬프트 조립 시점에 끝난다. 모델이 "스킬을 찾아 읽는" 자율 방식은 토큰과 재시도가 늘고 재생 대조가 깨진다. PoC 규모에서는 결정적 주입이 맞다.
- LLM 호출은 여전히 `llm/` 계층만 경유한다(R7). 프롬프트 내용이 바뀌므로 **저장된 호출 기록은 재생성**해야 한다(`record_golden.py --live`).

**규칙 충돌 점검**

| 규칙 | 판정 |
|---|---|
| R1 core 언어 무지 | 스킬 파일·선택기 모두 `adapters/java/` 아래. 통과. `test_layering.py`가 검사 |
| R2 안전장치 결정적 | 선택기는 표 조회. 게이트·규칙표는 건드리지 않음 |
| R4 도구 6개 | 도구 추가 없음 |
| R7 llm 계층 경유 | 변화 없음. 기록 재생성만 필요 |
| phase2 "수치 없는 개선 금지" | 아래 측정 계획으로 충족 |

### 2.4 어필로 만드는 방법 — 수치가 있어야 어필이다

스킬을 붙였다는 사실만으로는 어필이 안 된다. **전/후 비교**를 문서에 넣어야 한다.

- **측정 대상**: 예제 앱 SC-001(`--max-methods 4`) + SC-002. 현재 수치가 기준선이다(1차 실패→2차 통과, 18,896 토큰 / Mockito 오류 1회).
- **지표**: 1차 통과율, 총 시도 횟수, 토큰, 게이트 탈락 횟수, 검출력(뮤테이션).
- **가설**: junit5-mockito 스킬이 Mockito 1차 오류를 없앤다. regression-test 스킬이 regression 게이트 1차 통과율을 올린다.
- **실행**: 스킬 없음 / 있음 각 3회(재현성). 결과는 `evals/results/`에 프롬프트 버전과 함께.
- **문서화**: `PoC구현.md`에 "스킬 도입 전/후" 표 한 개 + 스킬 선택 로그 1건(어떤 신호로 어떤 스킬이 붙었는지) 텍스트로.

기술 어필 문장은 이렇게 잡는다.

> 에이전트의 지식을 프롬프트 한 덩이가 아니라 **선택 가능한 스킬 단위**로 모듈화했다. 선택은 규칙 기반이라 재현되고, 새 프레임워크 지원은 스킬 폴더 추가로 끝난다. 도입 전/후를 같은 시나리오로 측정해 1차 통과율과 토큰을 비교했다.

### 2.5 하지 않을 것

- 모델이 스킬을 스스로 탐색하는 도구(7번째 도구). R4 위반이고 재생이 깨진다.
- 스킬 안에 게이트 완화·기대값 수정 허용 같은 규칙 변경. 스킬은 "어떻게 잘 쓰나"만 담고 "무엇을 해도 되나"는 못 바꾼다.
- 스킬 5개를 한 번에. **junit5-mockito + regression-test 2개로 시작**해 수치를 보고 늘린다.

## 4. 멘토에게 확인할 질문

1. "스킬"이 제품 워크플로우(에이전트가 고르는 지식 묶음) 쪽인지, Claude Code 개발 스킬을 산출물에 드러내라는 뜻인지.
2. 스킬 선택을 규칙 기반(결정적)으로 두는 것과 모델이 고르는 것 중 어느 쪽이 더 어필이 되는지. 우리 원칙은 결정적이지만 멘토 의도가 "에이전트답게"라면 절충안(모델이 후보 중 고르되 허용 목록 안에서)을 검토한다.
3. 실행 예시 2건이면 충분한지, 아니면 SC-001~003 전부 텍스트로 원하는지.
