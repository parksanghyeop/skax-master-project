# Code Test Agent 사용 가이드 — `cta` CLI

Java 코드 변경에 맞춰 JUnit 테스트를 자동으로 생성·유지보수하는 CLI 도구다.
이 문서만 보고 설치부터 실사용까지 따라할 수 있게 썼다. 명령 이름은
`docs/제출자료/시나리오수립.md`의 기능 이름과 대응한다.

| 시나리오 기능 | 명령 |
|---|---|
| 테스트 생성 기능 (SC-001) | `cta generate --class <클래스> [--max-methods N]` |
| 변경 대응 기능 (SC-002·003) | `cta maintain [--diff <기준 커밋>]` |
| 판단 전달 기능 (SC-003) | `cta resolve [id] --intended \| --test-issue \| --proceed \| --as <의도> \| --skip` |
| 변경 내용 확인 기능 / 반영 기능 | `cta diff` / `cta apply` |
| 프로젝트 분석 기능 | `cta graph --coverage` |

## 1. 핵심 개념 — 3줄 요약

1. `cta generate`(대상 클래스 지정) 또는 `cta maintain`(git 변경에서 자동 판단)으로 테스트를 만든다
2. 생성물은 **바로 소스에 반영되지 않고 "제안"으로 보관**된다 — 이 PC의 Maven·JDK에서
   실행 검증 + 품질 게이트를 통과한 결과물이다(격리가 필요하면 `--runner docker`)
3. `cta diff`로 검토하고 `cta apply`로 반영한다 — 코드에 손대는 건 언제나 사람의 명령이다

## 2. 준비물

| 항목 | 확인 |
|---|---|
| Python 3.11+ | `python --version` |
| JDK 17+ · Maven (PATH) | `mvn -version` |
| (선택) Docker | `--runner docker` 격리 실행에만 필요 — `docker info` |
| 사내 게이트웨이 API 키 (`atl-...`) | 사내 안내 문서 |
| 대상 프로젝트 | Maven 단일 모듈, 기존 테스트 1개 이상 권장 |
| (선택) Neo4j | `cta maintain`의 "기존 테스트 찾기" 정확도 향상 — 7절 |

실행은 이 PC의 Maven·JDK로 돈다. 의존성은 사용자의 `~/.m2`를 쓰고, 없는 것은 첫 실행 때 Maven이 받는다.

## 3. 설치 (최초 1회)

### 방법 A — 일반 사용: pip로 설치해 아무 폴더에서나 `cta` 실행

```powershell
py -m venv $env:USERPROFILE\.cta
& $env:USERPROFILE\.cta\Scripts\pip install <리포지토리 경로 또는 git+사내git주소>
[Environment]::SetEnvironmentVariable("Path",
  "$env:USERPROFILE\.cta\Scripts;" + [Environment]::GetEnvironmentVariable("Path", "User"), "User")
```

> pipx가 있다면 위 두 단계 대신 `pipx install <리포지토리 경로>` 한 줄로 끝난다.

### 방법 B — 개발 중: 리포지토리 안에서 편집 설치

```powershell
git clone <이 리포지토리> && cd <리포지토리>
python -m venv .venv
.venv\Scripts\pip install -e .
.venv\Scripts\Activate.ps1
```

### 공통 — 설정 파일 `.env`

`cta`는 `.env`를 이 순서로 찾는다: **① 실행하는 폴더** → **② `~\.cta\.env`(전역)**.

```
CTA_GATEWAY_URL=      ← 게이트웨이 주소
CTA_GATEWAY_API_KEY=  ← 본인 API 키 (atl-...)
CTA_LLM_MODEL=gpt-5   ← 모델 (생략 시 gpt-4.1)
CTA_GATEWAY_TIMEOUT=300  ← (선택) 응답 대기 상한(초). 큰 테스트 파일 생성은 2~3분 걸린다
CTA_EMBEDDING_MODEL=text-embedding-3-small  ← (선택) 판단 메모 검색용 임베딩 모델 (기본값 그대로면 생략)
```

⚠️ 키가 든 `.env`는 어떤 저장소에도 커밋하지 않는다.

## 4. 테스트 생성 기능 — `cta generate` (SC-001)

테스트가 없는 클래스에 실제로 실행되는 테스트를 만든다. 프로젝트 폴더(또는 부모 폴더)에서:

```powershell
cta generate --class com.example.order.OrderService --max-methods 4
# 파일 이름으로도 된다: cta generate OrderService.java
# 특정 메서드만:       cta generate --target "OrderService#applyDiscount,total"
```

화면에는 시나리오의 4단계가 그대로 나온다:

```
  대상: com.example.demo.order.OrderService

  [1/4] 재료 수집
        건너뜀 OrderService.create — 기존 테스트가 이미 참조 (강제 생성: --all)
        테스트 만들 메서드 4개 선정: findByCustomer, updateAmount, pay, applyDiscount
        확인해야 할 항목 25개 (분기 9, 경계값 5, 예외 7, null 4)

  [2/4] 파라미터 객체 만드는 법 확인
        Order           → 직접 생성 (Order.builder() 사용)
        Customer        → 직접 생성 (값만 담는 객체)
        OrderRepository → mock 사용 (DB에 접근하는 인터페이스)
        기존 테스트 파일 있음 → OrderServiceTest에 메서드 추가 (기존 4개 유지)

  [3/4] 테스트 작성  (모델: gpt-5, 결과: src/test/.../OrderServiceTest.java)
        [   0초] 코드 생성 중 — LLM 호출 (1번째 시도 …)
        …
        1차  전체 통과

  [4/4] 품질 확인
        확인 항목 충족   n / 25  (n%)
        버그 검출력      n%
        기준 낮춤 여부   없음
        게이트[assert] 통과 — … / [skip] / [scope] / [coverage] / [mutation]

  수정됨   src/test/.../OrderServiceTest.java  (+n 테스트, 제안 'OrderServiceTest')
  테스트   n개 / 전체 통과
  소요     n분 n초 · n 토큰

  결과 상태: 정상 완료
```

- **메서드 선정**: 공개 메서드 중 기존 테스트가 참조하지 않는 것을 확인 항목(분기·경계값·예외·null)이
  많은 순으로 `--max-methods`(기본 4)개. 전부 강제하려면 `--all`
- **테스트 클래스는 대상 클래스당 하나**(`<클래스>Test`). 이미 있으면 기존 메서드는 그대로 두고 추가한다
- **작성 루프**: 컴파일 → 방금 만든 테스트만 실행 → 실패하면 직전 코드+실패 내용으로 다시(최대 8회).
  같은 실패가 반복되면 멈추고 터미널로 묻는다(Enter=계속, s=중지, 텍스트=힌트). `--non-interactive`면 자동 계속
- **결과 상태와 종료 코드**: 정상 완료 0 / 사람 확인 필요 3 / 품질 미달 2 / 실패 1

| 게이트 | 잡아내는 것 |
|---|---|
| assert | 기존 검증을 지우거나 느슨하게 바꾼 경우 — 테스트 메서드별 "바뀌기 전/후 (점수)"로 보고 (SC-004) |
| skip | @Disabled 등으로 테스트를 꺼버린 경우 |
| scope | 테스트 폴더 밖(대상 코드 등)을 몰래 수정한 경우 |
| coverage | 대상 라인 80%·분기 70% 미달 (조정: 8절) |
| mutation | 일부러 심은 버그를 못 잡는 "빈 테스트" |
| regression | (maintain의 버그 수정 건만) 수정 전 코드에서도 통과하는 테스트 — 버그를 잡지 못한다 |

탈락 시 사유를 모델에게 돌려주고 재시도(기본 3회), 소진하면 "품질 미달" 상태로 사람 확인용
제안이 남는다. **어느 경우든 apply 전에는 소스가 바뀌지 않는다.**

주요 옵션: `--max-methods N` `--all` `--test-class` `--instruction` `--model`
`--fast`(커버리지·뮤테이션 게이트 생략 — §12) `--runner docker`(격리 실행 — §12) `--non-interactive` `--quiet` `--project`

## 5. 검토·반영 — `cta diff` / `cta apply`

```powershell
cta diff        # 제안이 1건이면 바로 diff, 여러 건이면 목록
cta apply       # 제안이 1건이면 이름 생략 가능 (여러 건: 이름 또는 --all)
cta discard     # 폐기
```

## 6. 변경 대응 기능 — `cta maintain` (SC-002 / SC-003)

코드를 고친 뒤 실행한다. `--diff` 생략은 미커밋 변경, `--diff HEAD~1`은 마지막 커밋:

```powershell
cta maintain --diff HEAD~1
```

에이전트가 ① git diff에서 바뀐 메서드를 찾고 단서(커밋 메시지·이슈 번호·시그니처·접근 제어자·
줄 수)를 모으고 ② **변경 건마다** 의도를 판단해 화면에 적고 ③ 기존 테스트를 찾아 실행한 뒤
④ **규칙표**로 할 일을 정한다:

```
  변경 2건 확인  (비교 기준: HEAD~1, 커밋 메시지: "fix: 할인 임계금액 경계 조건 오류 수정 (#4821)")

  ① OrderService.applyDiscount
     판단   버그 수정        (확신도 85%)
     근거   · 커밋 메시지가 "fix:"로 시작, 이슈 #4821 참조
            · 경계 조건 > 를 >= 로 변경 (흔한 오차 패턴)
            · 메서드 시그니처는 그대로
     분석   …어떤 상황을 시험해야 하는지…
     기존 테스트   OrderServiceTest  → 통과
     참고   비슷한 과거 사례 없음
     할 일  재발 방지 테스트 추가

  ② OrderService.total
     판단   의미 없는 변경   (확신도 100%)
     근거   · 주석만 수정됨 (코드 줄 변경 0)
     할 일  없음
```

| 의도 | 기존 테스트 | 결정 |
|---|---|---|
| 버그 수정·새 기능 | — | 테스트 생성 → 제안. 버그 수정은 **수정 전 코드에서 실패하는지**까지 확인 |
| 리팩터링 | 통과 | 할 일 없음 (동작 보존 확인) |
| 리팩터링 | **실패** | **사람 확인** — 저장하고 멈춤(종료 코드 3), 기대값은 절대 자동 수정 안 함 |
| 의미 없는 변경(주석·공백) | — | 할 일 없음 (LLM을 부르지 않는다) |
| 판단 불확실 | — | 사람에게 질문 — 저장하고 멈춤 |

사람 확인이 필요하면 실패한 테스트(기대·실제)와 확인해 보실 곳(바뀌기 전/후)을 보여주고
`cta resolve` 명령을 안내한다. 의도를 어떻게 판단하는지(단서·프롬프트·확신도·규칙표)는 `docs/의도분류.md`에 따로 풀어 두었다. 옵션: `--plan-only`(판단만 출력) `--intent`·`--message`(아래) `--fast` `--runner` `--non-interactive` `--quiet`

**미커밋 변경을 볼 때 의도를 직접 말하기.** 커밋 메시지가 없으면 모델이 "판단 불확실"로 멈출 수 있다. 작성자가 아는 것은 바로 알려준다:

```powershell
cta maintain --message "fix: 임계금액 경계 조건"   # 커밋 메시지 자리에 들어가는 단서 — 판단은 모델이 한다
cta maintain --intent bug_fix                      # 분류를 이 값으로 확정 (bug_fix | refactor | new_feature). 근거·분석은 모델이 채운다
```

`--intent`를 줘도 규칙표는 그대로다 — 리팩터링인데 기존 테스트가 깨져 있으면 여전히 사람 확인으로 간다. 주석만 바뀐 메서드는 지정과 무관하게 "의미 없는 변경"이다.

**영향 범위 — 바뀐 메서드를 호출하는 곳.** 변경 건마다 "영향 범위" 줄에 호출하는 메서드가 확신도와 함께 나온다(정적 추정 — 같은 클래스 호출과 선언 타입이 읽히는 호출은 high, 이름만 유일하면 medium). 이 목록은 작업 지침서에도 들어가 "호출자를 거쳐 변경된 동작이 드러나는 시나리오"를 시험하게 한다. 호출자에도 테스트를 만들려면:

```powershell
cta maintain --diff HEAD~1 --impact    # 확신 high 호출자에 파생 생성 건 (깊이 1, 기본 최대 3건 — cta.toml [impact] max_callers)
```

파생 건은 화면에 `↳ 영향 범위 (OrderService.findById 변경의 호출자)`로 표시되고 원본의 의도를 물려받는다(LLM 추가 호출 없음). 영향 범위는 조치 결정(규칙표)과 "기존 테스트 통과/실패" 판정에는 쓰이지 않는다 — 추정 관계가 안전장치 입력이 되면 안 되기 때문이다. 호출자의 테스트가 정말 그 메서드를 실행하면 코드 그래프의 COVERS(실측)가 이미 잡는다.

## 7. 판단 전달 기능 — `cta resolve` (SC-003 8단계)

```powershell
cta resolve                       # 대기 항목 목록 (1건이면 자동 선택)
cta resolve <id> --intended       # 일부러 동작을 바꾼 게 맞다 → 실패한 테스트의 기대값을 새 기준으로 수정
cta resolve <id> --test-issue     # 테스트 쪽 문제다 → 실패한 테스트를 동작 기준으로 다시 작성
cta resolve <id> --proceed        # (질문 항목) 계획대로 테스트 생성   [--hint "지시"]
cta resolve <id> --as bug_fix     # (질문 항목) 의도를 직접 지정 → 규칙표부터 다시 진행 (bug_fix | refactor | new_feature)
cta resolve <id> --skip           # 이번엔 건너뜀
```

저장해 둔 상태를 불러와 멈춘 지점(테스트 작성 단계)부터 이어서 실행한다. **사람이 지정한 실패
테스트만** assert 변경이 허용되고 나머지 기존 assert는 여전히 게이트가 보호한다. 결정은 판단
메모(`.cta/memos/`)로 남아 다음 `maintain`의 "참고" 줄에 나온다.
메모에는 상황 요약(커밋 메시지·대상·분석 — 자연어)과 그 임베딩 벡터가 함께 저장되고, 다음 `maintain`은 같은 메서드·클래스 이름 일치를 먼저, 그 다음 상황이 닮은 메모(코사인 유사도)를 찾아 최대 3건을 붙인다 — "간헐적 실패 수정"과 "flaky 대응"처럼 말이 달라도 같은 상황을 찾기 위해서다. 게이트웨이가 없으면 이름 일치만 동작하고, 화면 "판단 메모 검색" 줄에 어느 쪽인지 나온다. 어느 쪽이든 메모는 참고일 뿐 규칙표를 바꾸지 못한다.

`--as`는 "판단 불확실"로 멈춘 항목용이다. 지정한 의도 × 저장된 기존 테스트 상태로 규칙표를 다시 본다: 버그 수정·새 기능이면 테스트를 만들고(버그 수정은 수정 전 코드에서 실패하는지도 확인), 리팩터링에 테스트 통과면 할 일 없음으로 닫고, 리팩터링에 테스트 실패면 `--intended`/`--test-issue`를 안내하고 항목을 남긴다. LLM은 부르지 않는다.

## 8. (선택) 코드 그래프 — 기존 테스트를 실측으로 찾기

```powershell
docker run -d --name cta-neo4j -e NEO4J_AUTH=neo4j/원하는암호 -p 7687:7687 -p 7474:7474 neo4j:5
# .env에 추가: CTA_NEO4J_PASSWORD=원하는암호
cta graph --coverage
```

그래프가 없으면 테스트 소스에서 클래스·메서드 호출을 찾는 파싱 폴백으로 동작한다(화면에 표시됨).
스키마·질의 예시는 `docs/코드그래프.md`.

## 9. 프로젝트 설정 — `cta.toml`

대상 프로젝트 루트(pom.xml 옆)에 두면 읽는다. 전부 선택 항목이고 안 적은 값은 기본값이다.
**주소·API 키는 여기 쓰지 않는다** — `.env`만(§3). 같은 항목이 여러 곳에 있으면 환경변수 > `.env` > `cta.toml` > 기본값 순으로 이긴다.

```toml
[gates]                 # 품질 게이트 기준치
line_min = 0.9          # 변경 라인 커버리지 하한 (기본 0.80)
branch_min = 0.8        # 분기 커버리지 하한 (기본 0.70)
max_retries = 2         # 게이트 탈락 → 재생성 횟수 (기본 3)
mutation_min = 0.6      # 심은 버그 검출률 하한 (기본 0.5)

[retry]                 # 테스트 작성 루프
ask_every = 4           # 이 횟수 실패마다 사람에게 묻기 (기본 4)
max_total = 8           # 시도 상한 (기본 8)

[gateway]
timeout_sec = 600       # 모델 응답 대기 상한 (기본 300) — 환경변수 CTA_GATEWAY_TIMEOUT과 같은 항목

[llm]
model = "gpt-5"         # deployment 이름 — 환경변수 CTA_LLM_MODEL과 같은 항목
reasoning_effort = "low"   # gpt-5 계열의 추론 강도 minimal/low/medium/high/none (기본 low) — 환경변수 CTA_LLM_REASONING_EFFORT

[impact]
max_callers = 3         # maintain --impact 파생 생성 건 상한 (0이면 없음)

[budget]
max_tokens_per_run = 50000   # 한 번 실행의 토큰 상한. 넘으면 멈추고 생성물을 되돌린다 (기본 무제한)
```

토큰 비용은 화면 마지막 "소요 … 토큰 (입력 · 출력 · 추론 · 캐시)"에서 본다. 기존 테스트 클래스에 메서드를 추가할 때는 모델이
새 메서드만 출력하고 도구가 파일에 합치므로 출력 토큰이 작다. 추론 강도 `low`는 실측(같은 대상 2메서드)에서 `20,969 → 5,128`토큰,
2분 37초 → 32초였다. 품질이 아쉬우면 `medium`으로 올린다.

## 10. 시나리오 재현 (개발 리포 안)

`examples/demo`(Spring Boot 주문 CRUD)와 `scripts/demo_scenarios.py`로 SC-001~003을 재현한다 —

## 11. 문제가 생기면

실패하면 화면에 원인 한 줄과 **왜 / 할 일 / 명령** 세 줄이 나온다. 예:

```
오류: 환경변수 CTA_GATEWAY_URL·CTA_GATEWAY_API_KEY가 필요하다 — …
  왜:    게이트웨이 주소·API 키가 설정에 없다
  할 일: .env를 실행 폴더 또는 ~/.cta/.env에 만들고 CTA_GATEWAY_URL, CTA_GATEWAY_API_KEY를 채운다 (.env는 커밋 금지)
  명령:  copy .env.example .env   (그다음 값 채우기)
```

안내가 없는 오류는 `CTA_DEBUG=1`을 붙여 다시 실행하면 전체 오류 추적이 나온다. 화면·로그에 API 키는 `****`로 가려진다.

| 증상 | 해결 |
|---|---|
| `cta` 명령을 못 찾음 | 방법 A: PATH 등록 후 **새 터미널** / 방법 B: `.venv\Scripts\Activate.ps1` |
| `환경변수 CTA_GATEWAY_URL·CTA_GATEWAY_API_KEY가 필요하다` | `.env` 위치 확인 — 실행 폴더 또는 `~\.cta\.env` |
| `게이트웨이 응답 대기 초과` | `cta.toml` `[gateway] timeout_sec = 600` 또는 `.env`에 `CTA_GATEWAY_TIMEOUT=600` |
| `토큰 예산 초과` | `cta.toml` `[budget] max_tokens_per_run` 확대 또는 `--max-methods` 축소 |
| `mvn 실행 파일을 찾을 수 없다` | Maven·JDK를 설치해 PATH에 넣는다(`mvn -version`). Docker가 있으면 `--runner docker` |
| `failed to connect to the docker API` (`--runner docker`) | Docker Desktop 실행 후 재시도. 또는 `--runner`를 빼고 이 PC에서 실행(기본) |
| 첫 실행이 수 분째 진행 | 정상 — 없는 의존성(JaCoCo·PIT 포함)을 Maven이 받는다. `--runner docker`는 프로젝트당 최초 1회 준비(Spring Boot 5~6분) |
| `뮤테이션 리포트 없음` 탈락 | `--runner docker`의 예전 캐시 — `<프로젝트>\.cta\m2repo` 삭제 후 재실행 |
| `사람 확인 항목 ... 이 없다` | `cta resolve`로 id 확인 |
| 한글 깨짐 (Windows) | `$env:PYTHONIOENCODING='utf-8'` |

## 12. 명령 요약

| 명령 | 역할 | 종료 코드 |
|---|---|---|
| `cta generate --class C [--max-methods N]` | 테스트 없는 메서드에 생성 → 제안 | 0/2/3/1 |
| `cta maintain [--diff REF] [--intent 의도] [--message "..."] [--impact]` | git 변경 → 건별 판단 출력 → 규칙표 → 생성/사람 확인. `--impact`는 호출하는 곳에도 생성 | 0/2/3/1 |
| `cta resolve [id] --intended\|--test-issue\|--proceed\|--as 의도\|--skip` | 사람 확인 항목에 답해 재개 | 0/2/3/1 |
| `cta diff [이름]` | 제안 목록 / 코드 diff | 0 |
| `cta apply [이름\|--all]` / `cta discard` | 제안 반영 / 폐기 | 0 |
| `cta graph [--coverage]` | 코드 그래프 빌드 (Neo4j) | 0/1 |
| `cta demo` / `cta eval [--cases a,b] [--intents [--variant both\|with\|without]]` | 재생 시연 / 결함 세트 검출률 · 의도 분류 정확도 (개발용) | 0/1 |

generate·maintain·resolve 공통 옵션: `--non-interactive`(질문 없이 자동 진행), `--quiet`(경과 시간 진행 줄 생략),
`--fast`(무거운 게이트 생략 — 아래), `--runner docker`(격리 실행 — 아래).

### 실행 장치 — 기본은 이 PC, 격리는 `--runner docker`

기본 실행 장치는 **이 PC의 Maven·JDK**다(ADR-0022). 준비 단계가 없고 실행 1회가 몇 초다. 대가는 **격리가 없다**는 것이다 —
생성된 테스트가 사용자 권한으로 돌고 네트워크도 막지 않는다. 화면 `[3/4]` 아래에 안내 한 줄이 나온다.
신뢰하는 코드베이스에서 쓰고, 남의 코드나 CI처럼 격리가 필요하면 `--runner docker`를 붙인다: 네트워크를 끊은 컨테이너에서
읽기 전용 의존성 캐시로 돌며, 프로젝트당 최초 1회 준비(다운로드 + 예열, 5분쯤)가 있고 `.cta/m2repo`에 캐시된다.

```powershell
mvn -version                                        # 기본 실행에 필요한 것 — Maven과 JDK 17+
cta generate --class com.example.order.OrderService                  # 이 PC에서 실행
cta generate --class com.example.order.OrderService --runner docker  # 격리 실행
```

### 빠른 실행 `--fast` — 무거운 게이트 생략

`--fast`는 커버리지·뮤테이션 게이트와 생성 전 검출력 측정(PIT)을 생략한다. assert·skip·scope·regression 게이트는 그대로다.
실행 장치와는 무관하다 — `--fast --runner docker`면 격리는 유지하고 게이트만 줄인다.

## 13. CI에서 쓰기 — 종료 코드 해석

| 종료 코드 | 결과 상태 | CI에서의 뜻 |
|---|---|---|
| 0 | 정상 완료 | 제안이 저장됐다(또는 할 일이 없었다). `cta diff`로 검토 후 `cta apply` |
| 3 | 사람 확인 필요 | **실패가 아니다.** 리팩터링인데 테스트가 깨졌거나 판단이 불확실해 멈췄다. 사람이 `cta resolve`로 답한다 |
| 2 | 품질 미달 | 게이트를 재시도 상한까지 통과하지 못했다. 제안은 "사람 확인용"으로 저장돼 있다 |
| 1 | 실패 | 환경·설정 오류. 화면의 왜/할 일/명령을 따른다 |

PR 검사 예(GitHub Actions). 게이트웨이 키는 저장소 시크릿으로, 러너에 JDK·Maven이 있어야 한다(격리가 필요하면 Docker + `--runner docker`).

```yaml
- name: Code Test Agent — 변경 대응
  env:
    CTA_GATEWAY_URL: ${{ secrets.CTA_GATEWAY_URL }}
    CTA_GATEWAY_API_KEY: ${{ secrets.CTA_GATEWAY_API_KEY }}
  run: |
    set +e
    cta maintain --diff origin/${{ github.base_ref }} --non-interactive --quiet
    code=$?
    if [ "$code" = "3" ]; then echo "::warning::사람 확인 항목이 있다 — cta resolve"; exit 0; fi
    exit $code
```

`--non-interactive`는 작성 루프의 질문에 자동으로 "계속"을 답한다(상한 `[retry] max_total`은 그대로 지킨다). 종료 코드 3을 실패로 볼지는 팀이 정한다 — 위 예는 경고로만 남긴다.

## 14. 지원 범위와 한계

| 구분 | 내용 |
|---|---|
| 지원 | Maven **단일 모듈**, JUnit 5, Java 17+ 대상 프로젝트. 기존 테스트가 1개 이상 있으면 준비 단계 예열과 관례 학습이 된다 |
| 미지원 | 멀티모듈 Maven, Gradle, Kotlin. 다른 언어는 어댑터를 추가해야 한다 |
| 파서 | 정규식 기반 경량 파서다. 제네릭·중첩 클래스·어노테이션이 많은 코드에서 메서드 경계나 확인 항목을 놓칠 수 있다 |
| 확신도 | 화면의 "확신도 86%"는 모델이 매긴 값이다. 보정된 확률이 아니며 코드는 이 값으로 분기하지 않는다 |
| 기존 테스트 찾기 | Neo4j 그래프가 있으면 실측(JaCoCo) 기준, 없으면 "테스트 소스에 클래스명 + 메서드 호출 모양이 있는가"의 근사다 |
| 첫 실행 | 기본(이 PC)은 준비 단계가 없고 없는 의존성만 첫 실행 때 받는다. 격리도 없다. `--runner docker`는 프로젝트당 최초 1회 의존성 다운로드 + 예열에 5분쯤 걸린다(이후 `.cta/m2repo`에 캐시) |
| 응답 시간 | 메서드 4개짜리 테스트 파일 생성은 모델 응답만 100초를 넘길 수 있다(`[gateway] timeout_sec`) |
| 재생 시연 | `cta demo`는 저장된 LLM 호출 기록에 묶여 있어 예제 프로젝트를 바꾸면 기록을 다시 만들어야 한다 |

제한이 어디서 오는지의 자세한 설명은 `docs/제출자료/PoC구현.md` §5(구현 범위 3구역)에 있다.
