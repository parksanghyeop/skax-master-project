# Code Test Agent 사용 가이드 (CLI)

Java 코드 변경에 맞춰 JUnit 테스트를 자동으로 만들어 주는 에이전트를 터미널에서
직접 사용하는 방법이다. 이 문서만 보고 처음부터 끝까지 따라할 수 있게 썼다.

> 진입점은 스크립트 형태다(`scripts/`). 정식 설치형 CLI는 3단계에서 제공 예정.

---

## 1. 무엇을 하는 도구인가

두 가지 사용 방식이 있다.

**방식 A — 대상을 직접 지정** (`generate_test.py`): "이 메서드에 테스트를 만들어 줘"

**방식 B — 변경에서 자동 판단** (`run_pipeline.py`): git으로 바뀐 코드를 찾아
"무엇을 해야 하는지"부터 에이전트가 정한다:

1. git diff에서 바뀐 클래스·메서드를 뽑는다
2. LLM이 변경 의도를 분류한다 (버그 수정 / 리팩터링 / 새 기능 / 불확실)
3. **미리 정해진 규칙표**가 할 일을 정한다 — 여기엔 LLM이 관여하지 않는다:
   - 버그 수정·새 기능 → 새 테스트 생성
   - 리팩터링 + 기존 테스트 통과 → 할 일 없음 (동작 보존 확인)
   - 리팩터링인데 기존 테스트 실패 → **사람에게 넘김** (동작이 바뀐 것일 수 있음)
   - 분류가 불확실 → 사람에게 물음
4. 테스트 생성이 결정되면 방식 A와 같은 생성 흐름으로 이어진다

생성 흐름(공통): LLM이 테스트를 만들고 → **인터넷 차단 Docker 환경**에서
컴파일·실행하고 → 실패하면 스스로 고치고(같은 실패가 반복되면 그 자리에서 멈추고
사용자에게 묻는다) → 통과하면 **품질 게이트 5종**을 통과해야 최종 승인된다.

**품질 게이트 5종** (전부 LLM 없는 기계 검사 — 에이전트 자신은 판정에 관여 못 함):

| 게이트 | 잡아내는 것 |
|---|---|
| assert 보존 | 기존 테스트의 검증(assert)을 지우거나 느슨하게 바꾼 경우 |
| 스킵 금지 | @Disabled/@Ignore로 테스트를 꺼버린 경우 |
| 파일 범위 | 테스트 폴더 밖(대상 코드 등)을 몰래 수정한 경우 |
| 커버리지 | 대상 메서드의 라인 80%·분기 70% 미달 (기준치 조정 가능) |
| 뮤테이션 | 코드에 일부러 심은 버그를 하나도 못 잡는 "빈 테스트" |

탈락하면 사유가 모델에게 그대로 전달돼 재시도(기본 3회)하고, 그래도 안 되면
"사람 확인 필요"로 보고한다. 생성된 파일의 채택 여부는 항상 **사람이 diff를 보고** 결정한다.

## 2. 준비물

| 항목 | 확인 방법 |
|---|---|
| Python 3.11 이상 | `python --version` |
| Docker (데몬 실행 중) | `docker info` 가 오류 없이 출력되면 됨 |
| 사내 게이트웨이 API 키 (`atl-...`) | 사내 안내 문서 참조 |
| 대상 프로젝트 | Maven 단일 모듈(`pom.xml`), 기존 테스트 1개 이상 권장 |
| (선택) Neo4j | 방식 B에서 "기존 테스트 찾기" 정확도를 높인다 — 4.4 참조 |

Java·Maven은 PC에 설치할 필요 없다 — 전부 Docker 컨테이너 안에서 돈다.

## 3. 설치 (최초 1회)

리포지토리 루트에서:

```powershell
python -m venv .venv
.venv\Scripts\pip install -e .
.venv\Scripts\pip install pytest ruff        # 개발·검증 도구 (실행만 할 거면 생략 가능)
copy .env.example .env
```

`.env`를 열어 값을 채운다:

```
CTA_GATEWAY_URL=      ← 게이트웨이 주소 (사내 안내 문서)
CTA_GATEWAY_API_KEY=  ← 본인 API 키 (atl-...)
CTA_LLM_MODEL=gpt-5   ← 사용할 모델 (생략 시 gpt-4.1)
```

> ⚠️ **`.env`는 절대 커밋하지 않는다** (gitignore 등록됨). `.env.example`에 실제 값을 쓰면 안 된다.

설치 확인: `.venv\Scripts\python -m pytest -q` → 전부 통과하면 정상 (Docker·키 없이 통과).

## 4. 실행

### 4.1 5분 체험 — 동봉된 예제로

```powershell
.venv\Scripts\python scripts\generate_test.py --project examples\demo --target "Calculator#divide"
```

최초 실행은 Docker 이미지·의존성 다운로드로 몇 분 걸린다(이후 캐시로 단축).
성공하면 게이트별 판정과 함께 끝난다:

```
결과: accepted  (게이트 루프 1회, ...)
  게이트[assert] 통과 — 기존 assert 2개 모두 보존됨
  게이트[skip] 통과 — 새 스킵 어노테이션 없음
  게이트[scope] 통과 — 변경이 허용 목록(1개) 안에 있음
  게이트[coverage] 통과 — 라인 100%, 분기 100% (기준 충족)
  게이트[mutation] 통과 — 심은 버그 n개 중 m개 검출(..%)

생성 파일: ...\CalculatorDivideTest.java
```

> 뮤테이션 게이트는 1~2분 걸린다. 급하면 `--fast`(결정적 게이트 3종만)로 생략 가능.

### 4.2 내 프로젝트 — 대상 직접 지정 (방식 A)

```powershell
.venv\Scripts\python scripts\generate_test.py `
  --project C:\work\my-service `
  --target "OrderService#cancel"
```

| 옵션 | 설명 |
|---|---|
| `--project` (필수) | Maven 프로젝트 루트 |
| `--target` (필수) | `클래스#메서드` |
| `--test-class` | 생성할 테스트 클래스 이름 (기본: `<클래스><메서드>Test`) |
| `--instruction` | 지침에 덧붙일 요구. 예: `"음수 경계값도 시험하라"` |
| `--model` | 이번 실행만 다른 모델 (예: gpt-4.1-mini) |
| `--fast` | 커버리지·뮤테이션 게이트 생략 (빠른 실행) |
| `--non-interactive` | 실행 중 질문 없이 자동 진행 (CI·배치용) |

**실행 중 에이전트가 물어볼 수 있다** — 같은 실패가 반복되거나 재시도 한도에
닿으면 멈추고 터미널에 질문이 뜬다:

```
⏸ 에이전트가 묻습니다: 2회 실패했다. 마지막 실패: ... 계속할까?
답 [Enter=계속 / s=중지 / 그 외 입력=힌트로 전달하고 계속]:
```

힌트를 입력하면(예: `null 케이스는 빼고 경계값 위주로`) 다음 시도의 프롬프트에 반영된다.

종료 코드: `0` 승인 / `1` 설정·입력 오류 / `2` 통과 못 함(이유 보고) / `3` 게이트 탈락(사람 확인 필요).

### 4.3 내 프로젝트 — 변경에서 자동 판단 (방식 B)

코드를 고친 뒤(커밋 전) 프로젝트에서:

```powershell
.venv\Scripts\python scripts\run_pipeline.py `
  --project C:\work\my-service `
  --message "쿠폰 중복 적용 버그 수정"
```

기본은 **결정까지만 출력**(dry-run)이다. 실제 생성까지 하려면 `--execute`.

| 옵션 | 설명 |
|---|---|
| `--message` | 커밋 메시지 등 의도 단서 — 분류 정확도를 높인다 |
| `--base` | diff 기준 (기본 HEAD=미커밋 변경, `HEAD~1` 등 가능) |
| `--intent` | 의도를 확실히 알면 직접 지정(bug_fix/refactor/new_feature) — LLM 분류 생략 |
| `--execute` | create_test 결정을 실제로 수행 |
| `--non-interactive` | 사람 확인(escalate/ask)을 묻지 않고 보고만 |

"사람에게 넘김/물음" 결정이 나오면 터미널에서 답을 받아 이어간다:

```
⏸ 사람 확인 필요 [escalate] OrderService#cancel
   사유: 리팩터링인데 테스트 실패 → 동작이 바뀌었을 수 있음, 사람에게 넘김
   답 [c=테스트 생성으로 진행 / Enter=건너뛰기 / 그 외=힌트와 함께 진행]:
```

### 4.4 (선택) 코드 그래프 — 기존 테스트를 실측으로 찾기

방식 B가 "기존 테스트가 통과하는가"를 판단하려면 어떤 테스트가 그 메서드를
실행하는지 알아야 한다. 코드 그래프를 만들어 두면 **커버리지 실측** 기반으로
정확히 찾는다(없으면 "커버 테스트 없음"으로 보수적으로 동작).

```powershell
# 1) Neo4j 컨테이너 (최초 1회)
docker run -d --name cta-neo4j -e NEO4J_AUTH=neo4j/원하는암호 -p 7687:7687 neo4j:5
# .env에 추가: CTA_NEO4J_PASSWORD=원하는암호

# 2) 그래프 빌드 (+--coverage: 테스트별 실행 실측, 테스트 수에 비례해 걸림)
.venv\Scripts\python scripts\build_graph.py --project C:\work\my-service --coverage
```

코드가 많이 바뀌면 다시 빌드한다(현재는 전체 재빌드, 증분 갱신은 개발 예정).

### 4.5 게이트 기준치 조정

대상 프로젝트 루트에 `cta.toml`을 만들면 기준을 바꿀 수 있다:

```toml
[gates]
line_min = 0.9      # 라인 커버리지 하한 (기본 0.80)
branch_min = 0.8    # 분기 커버리지 하한 (기본 0.70)
max_retries = 2     # 게이트 탈락 재시도 (기본 3)
mutation_min = 0.6  # 심은 버그 검출률 하한 (기본 0.5)
```

### 4.6 알아둘 제약

- Maven **단일 모듈** 기준 (Gradle·멀티 모듈 미지원)
- 최초 준비 단계 예열에 기존 테스트 1개 필요 (`--warmup-test`로 지정 가능)
- 뮤테이션 게이트는 pom에 `<plugins>` 절이 있어야 한다 (원본 pom은 수정하지 않고
  복제본을 만들어 쓴다 — `pom-cta-pit.xml`, 자동 생성·gitignore 대상)
- 게이트를 전부 통과해도 **최종 채택은 사람 몫**이다

## 5. 문제가 생기면

| 증상 | 원인과 해결 |
|---|---|
| `failed to connect to the docker API ...` | Docker Desktop이 꺼져 있다. 실행 후 재시도 |
| `환경변수 CTA_GATEWAY_URL·CTA_GATEWAY_API_KEY가 필요하다` | `.env` 미설정 — 3번 절차 확인 |
| `게이트웨이 호출 실패 ... 401/403` | API 키 오류·만료 — 재발급 후 `.env` 갱신 |
| 준비 단계가 몇 분째 안 끝남 | 정상(의존성+분석 도구 전체 다운로드). 프로젝트당 최초 1회 |
| `뮤테이션 리포트 없음` 으로 게이트 탈락 | 예전 캐시에 PIT가 없다 — `<프로젝트>/.cta` 삭제 후 재실행(재준비됨) |
| `환경변수 CTA_NEO4J_PASSWORD가 필요하다` | 4.4의 Neo4j 설정 누락 (그래프 기능을 안 쓰면 무시 가능) |
| 게이트 탈락(종료 코드 3) | 출력의 탈락 사유 확인 — 남긴 파일을 직접 검토·수정하거나 재실행 |
| `빈 selector — 전체 테스트 실행은 금지다` | 의도된 안전장치 — 전체 실행은 지원하지 않는다 |
| 한글 출력 깨짐 (Windows) | `$env:PYTHONIOENCODING='utf-8'` 설정 후 실행 |
| 저장된 LLM 호출 기록 관련 pytest 실패 | `evals/golden/`이 지워짐 — `git checkout evals/golden/` |

## 6. 명령 모음

```powershell
# 방식 A: 대상 지정 테스트 생성 (게이트 5종 포함)
.venv\Scripts\python scripts\generate_test.py --project <경로> --target "<클래스>#<메서드>"

# 방식 B: 변경에서 자동 판단 → (--execute 시) 생성
.venv\Scripts\python scripts\run_pipeline.py --project <경로> --message "<커밋 메시지>" --execute

# 코드 그래프 빌드 (선택, Neo4j 필요)
.venv\Scripts\python scripts\build_graph.py --project <경로> --coverage

# 데모: LLM 호출 없이 대표 시나리오 재생
.venv\Scripts\python scripts\demo_golden.py

# 평가: 결함 세트로 검출률 측정 (개발용, evals/results/에 기록)
.venv\Scripts\python scripts\run_eval.py

# 검증: 단위(외부 의존 없음) / 통합(Docker) / 그래프 왕복(Neo4j)
.venv\Scripts\python -m pytest -q
.venv\Scripts\python -m pytest -m docker -o addopts=""
.venv\Scripts\python -m pytest -m neo4j -o addopts=""
```
