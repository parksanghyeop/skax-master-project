# Code Test Agent — 구현 산출물

**한 줄 요약**: Java 코드 변경에 맞는 JUnit 테스트를 자동 생성·유지보수하는 CLI 도구(`cta`).
LLM은 두 곳(의도 분류·테스트 작성)에만 쓰고, 안전장치는 전부 일반 코드다.
명령은 `시나리오수립.md`의 기능 이름과 1:1로 대응한다.

| 시나리오 기능 | 명령 | 시나리오 |
|---|---|---|
| 테스트 생성 기능 | `cta generate --class <클래스> --max-methods N` | SC-001 |
| 변경 대응 기능 | `cta maintain --diff <기준 커밋>` | SC-002 · SC-003 |
| 판단 전달 기능 | `cta resolve <id> --intended \| --test-issue \| --proceed \| --skip` | SC-003 |
| 변경 내용 확인 기능 / 반영 기능 | `cta diff` / `cta apply` | 공통 |
| 프로젝트 분석 기능 | `cta graph --coverage` | 사전 조건 |

**사용 흐름** — 프로젝트 폴더에서:

```powershell
cta generate --class com.example.demo.order.OrderService --max-methods 4   # 테스트 없는 메서드 4개 선정·생성
cta maintain --diff HEAD~1                                                 # 커밋의 변경 건별 의도 판단 → 규칙표 → 처리
cta resolve --intended                                                     # 사람 확인 항목에 답해 멈춘 지점부터 재개
cta diff; cta apply                                                        # 검토 후 반영 — 코드 변경은 항상 사람의 명령으로만
```

### 핵심 구현 내용

**1.1 에이전트 워크플로우**

* **구현 기능**: 5단계 파이프라인 + 사람 개입 지점 2곳(저장 후 멈춤 → 재개) + 변경 건별 의도 분석 출력

![에이전트 워크플로우](images/workflow.png)

보라 = LLM 호출(2곳뿐) / 초록 = 결정적 안전장치(LLM 관여 불가) / 주황 = 사람 개입

* **동작 원리**
  - **의도 분류는 변경 건마다 LLM 1회**. 단서(커밋 메시지·이슈 번호·시그니처·접근 제어자·줄 수)는
    일반 코드가 수집해 프롬프트와 화면에 같이 넣는다. 결과는 `판단 (확신도) / 근거 / 분석 / 할 일`로
    **전부 화면에 출력**된다 — 사용자가 왜 그 조치가 나왔는지 본다. 주석·공백만 바뀐 변경은
    LLM 없이 "의미 없는 변경"으로 판정한다
  - 조치 결정은 규칙표 조회 — LLM 분석은 지침서 내용만 채우고 **길은 못 바꾼다**.
    "기대값 자동 수정" 행은 표에 없음. 리팩터링+테스트 실패 = 무조건 사람에게
  - **사람 개입은 저장 후 멈춤**: escalate/ask는 `.cta/escalations/`에 상태(실패 테스트·기대/실제·의심
    위치·지침)를 저장하고 종료 코드 3으로 끝난다. `cta resolve`가 그 상태를 읽어 테스트 작성 단계부터
    이어 간다. "일부러 바꾼 게 맞다"고 하면 **사람이 지정한 실패 테스트만** 기대값 수정이 허용되고
    나머지 assert는 게이트가 계속 보호한다. 결정은 판단 메모로 남아 다음 실행의 "참고"에 나온다
  - 작성 루프는 실패 로그+직전 코드를 다음 프롬프트에 넣어 자기 수정(최대 8회, 4회마다 사용자 확인).
    정지 지점에서 힌트를 받으면 **같은 지점부터 재개**(LangGraph interrupt + checkpointer)
* **주요 기술**: LangGraph(StateGraph·interrupt·checkpointer), gpt-5(사내 게이트웨이),
  포트/어댑터 구조(Fake 교체로 단위 테스트 168건이 LLM·Docker 없이 실행)

**1.2 도구(Tool) 및 함수 연동**

* **구현 기능**: 에이전트 도구 6종 + 인터넷 차단 실행 환경 + 게이트 6종 + 제안·사람 확인 저장소

![도구·함수 연동](images/tools.png)

* **동작 원리**
  - 도구 반환은 예외 대신 "모델이 읽을 문장"(상한 4,000자) — 실패도 다음 행동의 재료가 된다
  - **재료 수집(일반 코드)**: 테스트 만들 메서드 선정(공개·미참조 메서드를 확인 항목 많은 순으로 N개),
    확인 항목(분기·경계값·예외·null) 열거, 파라미터 객체 만드는 법(builder / 값 객체 / 저장소 mock)
    판단, 기존 테스트 파일 첨부 — 한 번에 모아 프롬프트에 넘긴다
  - 게이트 6종(전부 기계 검사, 테스트를 만든 에이전트는 판정 관여 불가):

  | 게이트 | 검사 방법 | 잡는 것 |
  |---|---|---|
  | assert | 테스트 메서드 단위 전/후 비교 + 엄격함 점수 | 기존 검증 삭제·완화 (assertEquals 4점 → assertNotNull 1점) |
  | skip | 어노테이션 카운트 | @Disabled 부착 (전체 경로 우회 포함) |
  | scope | 소스 전체 해시 대조 | 허용 목록 밖 수정 (대상 코드 조작) |
  | coverage | JaCoCo 실측 | 대상 라인 80%·분기 70% 미달 → 확인 항목 충족 수로 표시 |
  | mutation | PIT (복제 pom, 대상 메서드 집계) | 심은 버그를 못 잡는 빈 테스트 → 버그 검출력 % (전후 비교) |
  | regression | 수정 전 소스로 바꿔 끼워 실행(git show) | 수정 전 코드에서도 통과하는 "버그를 못 잡는" 재발 방지 테스트 |

  탈락 사유는 문장으로 모델에 반환→재생성(최대 3회)→소진 시 "품질 미달" 상태로 사람 확인 제안
* **주요 기술**: Docker, Maven go-offline+예열, JaCoCo, PIT(+junit5 플러그인), Mockito(대상 앱)

**1.3 데이터 및 컨텍스트**

* **구현 기능**: Neo4j 코드 그래프(+파싱 폴백) + few-shot 예시 검색 + 판단 메모 + LLM 호출 녹화·재생
* **동작 원리**
  - 그래프에는 **확정 관계만**: 선언한다 / 만든다(정적 파싱) / 검증한다(**JaCoCo 실측**).
    "이 메서드를 검증하는 테스트는?"이 실측 기반이라 "기존 테스트가 깨졌는가" 판단 근거가 된다.
    그래프가 없으면 테스트 소스의 클래스·메서드 호출 참조로 찾는 파싱 폴백(화면에 표시)
  - few-shot: 기존 테스트 중 대상과 모양(파라미터 수·예외 유무)이 닮은 2건을 프롬프트에 첨부
  - 판단 메모: `cta resolve`의 결정(대상·분류·결정·이유)을 저장하고 같은 메서드·클래스의 사례를
    다음 `maintain`에서 "참고"로 보여준다 — 참고일 뿐 규칙표를 우회하지 못한다
  - 녹화·재생: 모든 LLM 호출은 한 계층 경유, 요청·응답(토큰 수 포함)을 JSON으로 저장 → 자동
    테스트는 재생(비용 0, 결정적). 기록 없으면 실패 — 몰래 실호출 금지
* **주요 기술**: Neo4j 5, Azure OpenAI 호환 게이트웨이(usage 토큰 합산), `.env` 시크릿 분리

### 주요 문제 해결 및 기술 리서치

에이전트(프롬프트·도구 연동·컨텍스트·안전장치)와 직접 연관된 항목만 기록한다.

| 구분 | 문제 상황 및 원인 | 리서치 및 적용 |
|---|---|---|
| **프롬프트** | 의도 분류가 변경 전체를 묶어 1회 판정 — 사용자는 "왜 이 조치인가"를 볼 수 없었고, 여러 변경이 섞이면 한 분류로 뭉개짐 | • **리서치:** 시나리오 문서의 기대 출력(변경별 판단·확신도·근거) 대조 <br>• **적용:** 변경 건별 JSON(category/confidence/evidence/analysis) 호출 + 단서를 일반 코드가 수집·표시 → SC-002/003 형식 그대로 출력 |
| **프롬프트** | 리팩터링 커밋의 diff에서 모델이 "동작이 바뀐 것 같다"며 **unclear(87%)**로 도망 → 질문 상자로 가 시나리오 흐름(refactor+실패=escalate)이 안 나옴 | • **리서치:** v4 2.1 — 의도(작성자가 하려던 것)와 동작 보존 판정(테스트 실행)의 역할 분리 <br>• **적용:** "category는 작성자의 의도, 보존 여부는 기존 테스트가 판정 — 의심 지점은 근거에 적어라" → refactor(90%) + 근거에 빈 리스트 처리 변경 의심 → 규칙표 escalate |
| **프롬프트** | 자기 수정 루프가 수렴하지 않음 — 실패 로그만 주면 같은 코드를 다시 생성 | • **리서치:** self-repair 루프의 실패 로그 단독 재주입 한계 <br>• **적용:** 직전 코드+실패 로그 재주입, "같은 실패 2회 = 사람에게" 결정적 분기 → SC-001 실측 2차에 수렴 |
| **도구 연동** | 게이트웨이 응답 대기 120초 초과 — gpt-5가 메서드 4개짜리 테스트 파일(9,500자)을 만드는 데 100초+ 걸려 원문 스택으로 중단 | • **리서치:** 게이트웨이 스트리밍 미사용 시 긴 생성의 소요 시간 실측 <br>• **적용:** 상한 300초 + `CTA_GATEWAY_TIMEOUT` 조정, 소켓 시간 초과를 안내 문구로 변환 |
| **도구 연동** | 재발 방지 테스트가 정말 그 버그를 잡는지 알 수 없음 — 고친 코드에서 통과하는 것만 확인 | • **리서치:** 시나리오 SC-002 7단계, 회귀 테스트의 정의(버그 버전에서 실패) <br>• **적용:** 게이트 regression — 변경 파일을 git의 수정 전 내용으로 바꿔 끼워 실행, 통과하면 탈락·재생성, finally로 복구 |
| **도구 연동** | Neo4j 미기동 환경에서 폴백이 질의 시점에 예외로 터짐(드라이버 생성은 접속 없이 성공) | • **적용:** 생성 직후 탐색 질의로 접속 확인 → 파싱 폴백으로 전환, 어느 쪽인지 화면에 표시 |
| **도구 연동** | 파서가 생성자 `public OrderService(…)`를 메서드로 오인해 선정 후보에 포함 | • **적용:** 이름이 클래스와 같으면 생성자로 제외(결정적 필터) |
| **안전장치** | 사람이 "일부러 바꿨다"고 답하면 기대값을 고쳐야 하는데, assert 게이트가 모든 변경을 막음 | • **리서치:** R3의 범위 — 금지 대상은 *사람 확인 없는* 자동 갱신 <br>• **적용:** 사람이 이름을 지정한 실패 테스트만 게이트 허용 목록에 넣고 나머지 assert는 계속 보호. 실측: "기존 assert 9개 모두 보존됨 (사람 허용 1건 제외)" |
| **안전장치** | 모델이 게이트를 편법 우회 — FQN `@Disabled`, assert 완화 | • **적용:** 전체 경로 허용 정규식 + assert **내용** 비교, 탈락 사유를 테스트 메서드 단위 "바뀌기 전/후 (점수)"로 보고(SC-004), 불변식 테스트로 상시 검증 |

### 핵심 동작 검증 (실측, gpt-5 + Docker, 2026-09-03)

대상: `examples/demo` — Spring Boot 3.3 주문 CRUD 앱(OrderService·OrderRepository·PricingCalculator, Mockito 테스트).

**검증 1 — SC-001 테스트 생성** `cta generate --class com.example.demo.order.OrderService --max-methods 4`

```

        건너뜀 OrderService.create — 기존 테스트가 이미 참조 (강제 생성: --all)

        확인해야 할 항목 25개 (분기 9, 경계값 5, 예외 7, null 4)
  [2/4] 파라미터 객체 만드는 법 확인

        Customer        → 직접 생성 (값만 담는 객체)

        기존 테스트 파일 있음 → OrderServiceTest에 메서드 추가 (기존 4개 유지)
  [3/4] 테스트 작성  (모델: gpt-5)
        1차  실행 실패 — 20개 중 실패 0건, 오류 2건

  수정됨   OrderServiceTest.java  (+16 테스트)
```

**검증 2 — SC-003 리팩터링인데 테스트가 깨짐** `cta maintain --diff HEAD~1` (for문→스트림, 빈 목록 처리 누락 커밋)

```
  ① PricingCalculator.calculate
     판단   리팩터링 (동작 안 바뀜)    (확신도 90%)
     근거   · 커밋 메시지: refactor: calculate를 스트림으로 정리
            · 메서드 시그니처와 접근 제어자 변경 없음
            · 빈 리스트 처리 변경: 기존 BigDecimal.ZERO 반환 → 변경 후 orElse(null)로 null 반환
     기존 테스트   PricingCalculatorTest  → 실패
     할 일  사람 확인 (자동으로 고치지 않음)

  영향 테스트 실행 → 4건 중 1건 실패
  ┌────────────────────────────────────────────────────┐
  │  사람 확인 필요 — 자동으로 고치지 않았습니다       │
  └────────────────────────────────────────────────────┘
   실패한 테스트
     · calculate_emptyItems_returnsZero         기대 0, 실제 null
   확인해 보실 곳
     PricingCalculator.java 17행 부근  (바뀌기 전 / 바뀐 후 diff)
   수정한 테스트   0건 (일부러 안 함)
     · 일부러 동작을 바꾼 게 맞다  → cta resolve 20260903-001139-PricingCalculator-calculate --intended
  결과 상태: 사람 확인 필요          ← 종료 코드 3, 1,997 토큰
```

이어서 `cta resolve --intended`: 저장된 항목을 읽어 재개 → 실패했던 테스트 1건만 기대값 수정
