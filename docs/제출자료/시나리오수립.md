### 핵심 사용자 시나리오

### **시나리오 1 : 테스트가 없는 클래스에 테스트 코드 만들기**

* ID : SC-001

* 상황 : 오래된 클래스를 수정해야 하는데 테스트 코드가 하나도 없다. 고친 뒤에 제대로 도는지 확인할 방법이 없어서 손대기가 부담스러운 상황

* 목표 : 실제로 실행되고, 버그가 생기면 잡아낼 수 있는 테스트 코드를 만든다

* 사전 조건 : 대상 프로젝트가 Maven 단일 모듈이고 빌드가 정상 동작. **프로젝트 분석 기능**을 한 번 실행해서 이 팀의 테스트 작성 방식과 테스트-소스 연결 정보를 미리 수집해 둔 상태

* 상세 흐름

| 단계 | 사용자 행동                                | 시스템 동작                                                                       | 비고                 |
| -- | ------------------------------------- | ---------------------------------------------------------------------------- | ------------------ |
| 1  | **테스트 생성 기능**에 대상 클래스 또는 경로를 지정해 실행한다 | 클래스 안에서 테스트를 만들 메서드를 고른다.                                                    |                    |
| 2  | 없음                                    | 테스트를 쓰는 데 필요한 재료를 모은다. (메서드 코드, 확인해야 할 항목, 파라미터로 넘길 객체를 어떻게 만드는지, 테스트 작성 방식) | 한 번에 다 모아서 넘김      |
| 3  | 없음                                    | 테스트 코드 작성 후 바로 컴파일해 본다                                                       | 실패하면 오류 내용을 알려줌    |
| 4  | 없음                                    | 컴파일이 되면 방금 만든 테스트만 실행한다                                                      |                    |
| 5  | 없음                                    | 실패하면 3~4단계를 다시 한다                                                            | 최대 8번, 나아지지 않으면 중단 |
| 6  | 없음                                    | 품질을 확인한다. 확인 항목을 얼마나 덮었는지, 버그를 잡을 수 있는지                                      |                    |
| 7  | **변경 내용 확인 기능**으로 결과를 본다              | 만들어진 테스트 코드를 보여준다.                                                           |                    |
| 8  | **반영 기능**을 실행한다                       | 테스트 파일을 프로젝트에 실제로 저장한다                                                       |                    |

* 입력 예시

아래는 실제로 입력하는 명령어 예시입니다.

console

```console
$ cta generate --class com.example.order.OrderService --max-methods 4
```

테스트를 만들 대상 코드는 다음과 같습니다.

java

```java
public class OrderService {
    private final OrderRepository repository;

    public BigDecimal applyDiscount(Order order, Customer customer, boolean isPromo) {
        if (order == null) throw new IllegalArgumentException("order required");
        BigDecimal amount = order.getAmount();
        if (amount.signum() < 0) throw new IllegalArgumentException("negative amount");
        if (customer.getGrade() == Grade.GOLD && amount.compareTo(THRESHOLD) >= 0) {
            return amount.multiply(GOLD_RATE);
        }
        return isPromo ? amount.multiply(PROMO_RATE) : amount;
    }
}
```

**시나리오 2 : 버그를 고친 커밋에 재발 방지 테스트 붙이기**

* ID : SC-002

* 상황 : 계산 로직의 경계 조건 버그를 고쳐서 커밋했다. 같은 버그가 다시 들어오는 걸 막으려면 테스트를 추가해야 하는데, 귀찮아서 자주 건너뛰게 되는 상황

* 목표 : 그 버그가 다시 생기면 바로 잡아내는 테스트를 만든다

* 사전 조건 : 대상 클래스에 기존 테스트가 있고, 커밋이 끝나서 변경 전후를 비교할 수 있다.

* 상세 흐름

| 단계 | 사용자 행동                                | 시스템 동작                                                                       | 비고                     |
| -- | ------------------------------------- | ---------------------------------------------------------------------------- | ---------------------- |
| 1  | **변경 대응 기능**에 비교할 커밋 범위를 지정해 실행한다     | 변경 내용을 메서드 하나 단위로 쪼갠다                                                        |                        |
| 2  | 없음                                    | 판단에 쓸 단서를 코드로 뽑는다. 메서드 시그니처가 바뀌었는지, 접근 제어자가 바뀌었는지, 몇 줄이 바뀌었는지, 커밋 메시지, 이슈 번호 |                        |
| 3  | 없음                                    | 비슷한 과거 변경 사례를 찾아 참고 자료로 같이 보여주고, AI가 변경 의도를 판단한다                             |                        |
| 4  | 없음                                    | 규칙표를 보고 할 일을 정한다. "버그 수정"이면 재발 방지 테스트 추가                                     | AI가 아니라 규칙표가 결정        |
| 5  | 없음                                    | 영향받는 테스트 목록을 찾아 현재 상태를 확인한다                                                  | 미리 수집해 둔 소스코드 연결 정보 사용 |
| 6  | 없음                                    | AI가 재발 방지 테스트를 작성하고 컴파일·실행한다                                                 | 기존 테스트는 건드리지 않음        |
| 7  | 없음                                    | 만든 테스트를 **수정 전 코드**에 적용해서 실패하는지 확인한다                                         | 통과하면 무효로 보고 다시 만듦      |
| 8  | 없음                                    | 기존 테스트가 확인하던 조건이 느슨해지지 않았는지 검사한다                                             |                        |
| 9  | **변경 내용 확인 기능**으로 본 뒤 **반영 기능**을 실행한다 | 변경을 프로젝트에 저장한다                                                               |                        |

**시나리오 3 : 리팩터링만 했는데 테스트가 깨졌을 때 사람에게 넘기기**

* ID : SC-003

* 상황 : 로직은 그대로 두고 코드만 정리하는 리팩터링을 했는데 기존 테스트가 깨졌다. 보통은 테스트의 기대값을 실제값에 맞춰 고치지만, 그러면 버그가 묻히게 된다.

* 목표 : 테스트를 함부로 고치지 않고, 버그일 가능성을 근거와 함께 개발자에게 알린다

* 사전 조건 : SC-002와 같은 조건이다. 변경한 메서드에 기존 테스트가 있고, 변경 전에는 통과하던 상태

* 상세 흐름

| 단계 | 사용자 행동                                              | 시스템 동작                                                   | 비고            |
| -- | --------------------------------------------------- | -------------------------------------------------------- | ------------- |
| 1  | **변경 대응 기능**에 비교할 커밋 범위를 지정해 실행한다                   | 변경 내용을 메서드 하나 단위로 쪼갠다                                    |               |
| 2  | 기다림                                                 | 시그니처가 그대로인지 확인하고 커밋 메시지를 본다                              | 일반 코드가 처리     |
| 3  | 기다림                                                 | AI가 "리팩터링(동작 안 바뀜)"으로 판단한다. 확신도 88%                      |               |
| 4  | 기다림                                                 | 영향받는 테스트를 실행한다 → 3건 중 2건 실패                              |               |
| 5  | 기다림                                                 | 규칙표 적용 — 리팩터링인데 실패했으므로 사람 확인으로 넘긴다. 기대값을 고치는 길은 아예 없다    | 가장 중요한 안전 규칙  |
| 6  | 기다림                                                 | 실패한 테스트, 기대값과 실제값 차이, 의심되는 위치를 정리해 알려주고 현재 상태를 저장한 뒤 멈춘다 | 테스트 파일은 그대로   |
| 7  | 내용 확인 후 코드 점검                                       | 기다림                                                      |               |
| 8  | 코드를 직접 고치거나, **판단 전달 기능**으로 "일부러 동작을 바꾼 게 맞다"고 알려준다 | 저장해 둔 상태를 불러와 멈춘 지점부터 이어서 실행한다                           | 처음부터 다시 하지 않음 |

**시나리오 4 : 테스트가 확인하는 조건을 느슨하게 만들려는 시도 막기**

* ID : SC-004

* 상황 : SC-001이나 SC-002를 하는 중에, AI가 테스트를 통과시키려고 확인 조건을 느슨하게 바꾸거나 확인 항목을 지우려는 상황

* 목표 : 그 수정을 반영하지 않고, 왜 통과가 안 되는지를 개발자가 보게 한다

* 사전 조건 : 테스트 수정 작업이 진행 중이고, 수정 전 테스트 코드가 남아 있다

* 상세 흐름

| 단계 | 사용자 행동 | 시스템 동작                                                                         | 비고    |
| -- | ------ | ------------------------------------------------------------------------------ | ----- |
| 1  | (진행 중) | AI가 고친 테스트를 고치기 전과 코드 구조 단위로 비교한다                                              |       |
| 2  | (진행 중) | assert 개수가 줄었는지, 확인이 얼마나 꼼꼼한지가 약해졌는지, 예외 확인이 사라졌는지, 테스트를 건너뛰게 하는 표시가 붙었는지 검사한다 |       |
| 3  | (진행 중) | 걸리면 반영하지 않고 이유를 알려주며 다시 시도하게 한다                                                | 최대 3번 |
| 4  | (진행 중) | 3번 해도 안 되면 사람 확인으로 넘긴다                                                         |       |
| 5  | 결과 확인  | 어떤 항목이 어떻게 약해졌는지 비교해서 보여준다                                                     |       |

* 입력 예시 AI가 제안한 수정 내용입니다. 반영하기 전에 이 내용을 검사합니다.
