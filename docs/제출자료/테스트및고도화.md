# Code Test Agent (`cta`) — 테스트 및 고도화 산출물

PoC 구현(→ [PoC구현.md](PoC구현.md)) 이후 수행한 테스트와 고도화 기록이다.
평가 대상은 "생성한 테스트가 실제 버그를 잡는가"이고, 개선은 **수치 전/후 비교가 있는 것만** 개선으로 적는다(고도화 규칙).
실측은 전부 gpt-5(사내 게이트웨이) + Docker 샌드박스 + Neo4j 코드 그래프를 실제로 연결해 얻었다.

| 항목 | 값 |
|---|---|
| 평가 세트 | 로컬 결함 세트 v1 — 6건 (ADR-0014, Defects4J·EvoSuite는 환경 제약으로 보류) |
| 평가 방식 | 고친 코드에서 테스트 생성 → 버그 코드에 끼워 실행 → 실패하면 검출 성공 (Defects4J와 같은 판정) |
| 베이스라인 | 게이트 승인 6/6 · **검출률 83.3%(5/6)** · 에스컬레이션 0% · 평균 시도 1.0회 |
| 자동 테스트 | 단위 172건(LLM·Docker 없이 Fake로) · Docker 통합 3건 · Neo4j 통합 1건 · ruff 통과 |
| 실측일 | 2026-09-02(베이스라인) ~ 2026-09-04(결함 점검) |

## 1. LLM 답변 품질 평가 및 개선

이 에이전트에서 "답변"은 두 가지다. ① 변경 의도 판단(분류·확신도·근거) ② 생성한 테스트 코드.
①은 시나리오 기대 출력과 대조해 평가했고, ②는 평가 하네스로 검출률을 쟀다.

### 1.1 생성 테스트의 버그 검출력

| 항목 | 내용 |
|---|---|
| 평가 대상 기능 | `cta generate` — 메서드 하나에 대해 실제로 실행되는 JUnit 테스트 생성 |
| 평가 방식 | 벤치 프로젝트(`examples/evalbench`)의 메서드 6개에 (고친 버전, 버그 버전) 쌍을 수작업 구축 → 고친 버전에서 생성 → 버그 버전에 끼워 실행. 실패하면 검출 성공. LLM 심사 없이 **실행 결과로만** 판정 |
| 결함 종류 | 경계 off-by-one · null 누락 · 빈 문자열 처리 · 연산자 오류 · 음수 처리 누락 · 재귀 기저 조건 오류 |
| 평가 결과 (베이스라인) | 게이트 승인 6/6, **검출률 5/6 = 83.3%**, 에스컬레이션 0%, 평균 생성 시도 1.0회, 총 19.5분(준비 포함), 케이스당 102~148초 |
| 미검출 분석 | `truncate-boundary`(`<=` → `<`): 생성 테스트가 "길이 == 최대" 경계 사례를 만들지 않았다. 게이트 5종은 전부 통과했으므로 **게이트로는 못 거르는 종류**의 미달이다 |
| 개선 조치 | ① 재료 수집 단계 신설 — 대상 코드에서 확인 항목(분기·경계값·예외·null)을 일반 코드가 정규식으로 열거해 프롬프트에 넣고, 결과 화면에 "확인 항목 충족 n/m"(JaCoCo 라인 기준)을 표시 ② 검출력(PIT 뮤테이션 점수)을 게이트 겸 화면 지표로 상시 출력 |
| 개선 후 결과 | 데모 실측(SC-001·002): 확인 항목 12/12·25개 열거, 검출력 95%(22개 중 21개)·100%. **같은 결함 세트 6건 재측정은 아직 하지 않았다** — 미검출 케이스가 잡히는지는 §6 실험 후보 ①로 남긴다 |

베이스라인 케이스별 기록(`cta/evals/results/eval-local-defects-v1-gpt-5-20260902-020408.json`, 프롬프트 해시 4f3a5818756b):

| 케이스 | 대상 | 심은 버그 | 게이트 | 검출 | 소요 |
|---|---|---|---|---|---|
| clamp-wrongop | MathUtil#clamp | `Math.min` → `Math.max`, 상한 미적용 | 5/5 | ✅ | 104초 |
| fib-base | MathUtil#fibonacci | 기저 조건 `n` 대신 `1` | 5/5 | ✅ | 102초 |
| palindrome-empty | TextUtil#isPalindrome | 빈 문자열에서 true | 5/5 | ✅ | 115초 |
| rounding-negative | MathUtil#divideRounded | 음수 반올림 분기 삭제 | 5/5 | ✅ | 146초 |
| truncate-boundary | TextUtil#truncate | `<=` → `<` 경계 오류 | 5/5 | ❌ | 148초 |
| truncate-null | TextUtil#truncate | null 검사 삭제 | 5/5 | ✅ | 143초 |

![평가 요약](images/eval-summary.png)

**모델 비교 실측 (2026-09-04, ADR-0013 실험 ②)** — 같은 결함 세트·같은 프롬프트·게이트 5종 full로 작성 모델만 바꿨다.

| 모델 | 검출률 | 게이트 승인 | 평균 작성 시도 | 총 소요 | 케이스당 | 기록 |
|---|---|---|---|---|---|---|
| gpt-5 (기준) | 5/6 = 83.3% | 6/6 | 1.00회 | 19.5분 | 102~148초 | `eval-local-defects-v1-gpt-5-20260902-020408.json` |
| gpt-4.1 | 5/6 = 83.3% | 6/6 | 1.17회 | 8.7분 | 63~93초 | `eval-local-defects-v1-gpt-4.1-20260904-135950.json` |

두 모델의 미검출은 같은 케이스(`truncate-boundary`)다. gpt-4.1은 `rounding-negative`에서 1차 실행이 실패해 2차에 통과했고, 그 외는 1차 통과.
LLM 작성 1회는 gpt-5 47~72초 → gpt-4.1 2~5초. 6건이라 통계적 힘은 약하지만, 이 세트에서는 **모델을 바꿔도 검출률이 떨어지지 않았고 시도 수가 약간 늘었다**.

### 1.2 변경 의도 판단의 정확성

| 항목 | 내용 |
|---|---|
| 평가 대상 기능 | `cta maintain` — 변경 건별 의도 분류(버그 수정 / 리팩터링 / 기능 추가 / 의미 없는 변경 / 불명확) + 확신도 + 근거 |
| 평가 방식 | 시나리오 문서(SC-002·003)의 기대 출력과 실제 화면 대조. 정답은 커밋을 만든 사람(우리)이 안다 |
| 평가 결과 (개선 전) | 리팩터링 커밋에서 모델이 diff의 빈 목록 처리 누락을 알아채고 **"불명확 (87%)"** 로 도망 → 질문 상자로 가 버려 시나리오 흐름(리팩터링 + 테스트 실패 = 사람 확인)이 나오지 않음. 또한 초기 구현은 변경 묶음 전체를 한 번에 분류해 사용자가 "왜 이 조치인가"를 볼 수 없었다 |
| 개선 조치 | ① 변경 건별 LLM 1회 호출, JSON(판단·확신도·근거·분석)으로만 응답, 깨진 응답은 불명확 처리 ② 프롬프트에 역할을 분리해 명시: "category는 작성자의 의도다. 동작이 보존됐는지는 기존 테스트 실행이 판정한다. 의심 지점은 근거에 적어라" ③ 단서(커밋 메시지·이슈 번호·시그니처 변경 여부·접근 제어자·줄 수)는 일반 코드가 수집해 프롬프트와 화면에 같이 표시 |
| 개선 후 결과 | SC-003: **리팩터링 86~90%** + 근거에 의심 지점 → 규칙표가 사람 확인으로 정확히 안내. SC-002: 버그 수정 98%(근거: fix 메시지·`>`→`>=`·시그니처 불변), 주석만 바뀐 메서드는 LLM 없이 "의미 없는 변경 100%". 기대값 자동 수정 0건 |

**의도 세트 실측 (2026-09-04, ADR-0020)** — "의도 모름으로 많이 빠진다"는 사용자 피드백을 수치로 확인하기 위해 의도가 알려진 변경 10건(버그 수정 3·리팩터링 3·새 기능 2·주석만 1·애매 1)을 예제 복사본에 적용해 **커밋 메시지 있음/없음** 두 변형으로 분류만 돌렸다(`cta eval --intents`, Docker 불필요).

| 변형 | 정확도 | 잘못된 "의도 모름" | 확신도 범위 | 평균 소요 |
|---|---|---|---|---|
| 커밋 메시지 있음 (10회) | 10/10 | 0 | 78~100% | 9.3초 |
| 커밋 메시지 없음 (10회) | 10/10 | 0 | 64~96% | 12.1초 |

애매한 케이스(효과 없는 대입, 실제로 저장됐던 사례)는 양쪽 모두 "의도 모름"으로 답했고 이것이 정답이다. 결론: 현재 프롬프트에서 잘못된 "의도 모름"은 재현되지 않았고, 메시지가 없으면 확신도만 낮아진다. 그래서 단서 확대와 확신도 기준치는 보류하고, 모델이 정당하게 모른다고 답하는 경우를 위해 **작성자가 의도를 직접 말하는 길**(`cta maintain --intent`, `--message`, `cta resolve --as`)을 구현했다. 실측: 같은 애매한 미커밋 변경이 옵션 없이는 "판단 불확실 85%", `--intent refactor --message "..."`를 주면 "리팩터링 100%, 근거: 작성자 지정 의도"로 바뀌고 규칙표는 그대로 탄다(테스트 실패 중이라 사람 확인).

### 1.3 자기 수정 루프의 수렴

| 항목 | 내용 |
|---|---|
| 평가 대상 기능 | 작성 루프 — LLM 작성 → Docker 실행 → 실패 시 재작성 |
| 평가 결과 (개선 전) | 실패 로그만 다시 주면 같은 코드를 다시 생성해 수렴하지 않음 |

| 개선 후 결과 | SC-001(메서드 4개): 1차 Mockito 오류 2건 → 2차 전체 통과. 베이스라인 6건은 전부 1회 통과(평균 시도 1.0) |

## 2. 성능 및 비용 최적화

### 2.1 적용된 것

| 항목 | 내용 |
|---|---|
| 기존 병목 | ① 매 실행마다 Maven 의존성 다운로드와 분석 도구(JaCoCo·PIT) 초기화 ② 자동 테스트·시연마다 LLM 실호출 → 비용 발생 + 결과가 매번 달라 재현 불가 ③ 주석만 바뀐 변경에도 LLM을 호출 ④ 커버리지·뮤테이션 게이트가 실행 시간의 대부분 |
| 개선 전략 | 준비 단계 분리 + 캐시 / LLM 호출 기록·재생 / LLM 전 결정적 사전 필터 / 게이트 생략 옵션 |
| 적용 기술 | • **샌드박스 2단계**: 준비 단계만 네트워크를 켜 `.cta/m2repo`에 의존성·JaCoCo·PIT를 내려받고 테스트 1회 예열. 실행 단계는 `--network none` + `mvn -o` + 캐시 읽기 전용 마운트 <br>• **호출 기록·재생**(`llm/replay.py`): 모든 LLM 호출이 한 층을 경유하며 요청·응답·토큰 수를 JSON으로 저장. 요청 전문이 같으면 파일만으로 응답 <br>• **사전 필터**: 주석·공백만 바뀐 변경은 규칙표에서 "의미 없는 변경"으로 확정(LLM 미호출) <br>• **`--fast`**: 커버리지·뮤테이션 게이트를 생략하는 옵션(개발 중 빠른 확인용, 제출용 실측은 전부 full) <br>• **PIT는 복제 pom**(overlay)으로 대상 메서드만 집계 <br>• **토큰 계량**(`llm/metering.py`): 실호출·재생 어느 쪽이든 호출 수·토큰을 합산해 결과 화면에 표시 |
| 개선 결과 | • 첫 실행 준비 5분 → 이후 실행은 캐시 재사용(케이스당 102~148초, 게이트 5종 포함) <br>• `cta demo` 재생: 7개 테스트 생성·통과 **74초 · 0 토큰** (자동 테스트도 같은 방식이라 CI 비용 0) <br>• SC-002 주석 변경 1건: LLM 호출 0회로 판정 <br>• `--fast`: 파일 모드 실측 47초(gpt-5 1회 호출) vs full 122~182초 <br>• 실측 토큰: SC-001(메서드 2개) 8,874 / SC-002 17,816 / SC-003 판단만 1,737 / resolve 4,516 |

Semantic Cache 같은 유사 질의 캐시는 도입하지 않았다. 이 에이전트의 입력은 매번 다른 diff·소스라 동일 질의가 반복되지 않고, 재현이 필요한 곳(시연·CI)은 기록·재생이 이미 비용 0을 만든다.

### 2.2 실행 시간 단축 — 병목 실측과 개선안 (2026-09-04, **미적용**)

목표: `cta maintain` 한 번을 3분 → 1분 전후(가능하면 30초)로. 먼저 시간이 어디에 쓰이는지 실측했다.

**병목 분해 1 — 사람 확인으로 끝나는 경우(SC-003형)**. 리팩터링 커밋 저장소를 새로 만들어(target/ 없음, Neo4j 연결) `cta maintain --diff HEAD~1 --plan-only`를 돌리고 화면 출력에 경과 시간을 붙였다.

| 구간 | 소요 | 비고 |
|---|---|---|
| 변경 추출 · 그래프 조회 | 1.8초 | 일반 코드 |
| 의도 분류 (gpt-5 1회) | 15.6초 | 모델 응답 시간. 실행마다 15~60초로 흔들린다 |
| 기존 테스트 실행 (Docker Maven 1회) | 43.3초 | 테스트 자체는 0.2초. 나머지는 Maven 부팅·컴파일·의존성 로딩 |
| 판단 출력 · 저장 | 0.2초 | |
| **합계** | **60.9초** | |

**병목 분해 2 — 재발 방지 테스트까지 만드는 경우(SC-002형, 9분 30초)**. 실행 로그의 경과 시간을 그대로 옮겼다.

| 구간 | 소요 | Maven 실행 횟수 |
|---|---|---|
| 재료 수집 + 기존 테스트의 검출력 측정(PIT, 전후 비교용) | 113초 | 1 |
| LLM 작성 1차 → 파일 쓰기(컴파일 확인) → 샌드박스 실행 | 72 + 34 + 45초 | 2 |
| LLM 작성 2차 → 파일 쓰기 → 샌드박스 실행 | 47 + 32 + 42초 | 2 |
| 게이트 regression · coverage · mutation | 187초 | 3 |
| 의도 분류 등 | 15초 | 0 |
| **합계** | **570초** | **8회 ≈ 450초** |

두 경우 모두 **Docker 안 Maven 실행이 전체의 70~80%** 다. 컨테이너 기동(0.9초)과 JVM·Maven 부팅(0.9초)은 문제가 아니었다.

**원인 실험** — 같은 테스트 1건(`PricingCalculatorTest`)을 조건만 바꿔 실행했다. LLM 없음, 네트워크 차단 그대로.

| 조건 | target/ 있음 | target/ 없음(전체 컴파일) |
|---|---|---|
| ① 현행: 의존성 캐시 `.cta/m2repo`를 호스트 폴더 바인드 마운트 | 23.3초 (재측정 20.9초) | 43.3초 |
| ② ① + 단명 JVM 플래그 (`-XX:TieredStopAtLevel=1 -XX:+UseSerialGC -Xshare:auto`) | 19.9초 | — |
| ③ 의존성 캐시를 **Docker named volume**으로 | **5.3초** | — |
| ④ ③ + JVM 플래그 | **4.5초** | **7.6초** |

원인: Windows Docker Desktop의 바인드 마운트는 파일 공유 계층을 거치므로 jar 수백 개(161MB)를 읽는 Maven에 치명적이다. 캐시를 named volume(리눅스 VM 안 디스크)에 두면 같은 명령이 **4~5배** 빨라진다. 읽기 전용 마운트(`:ro`)와 `--network none`은 그대로 유지된다.

**구조 개편안** — 위 실측을 근거로 "Maven을 매번 부르는 구조" 자체를 바꾸는 안이다. 전부 `adapters/java`·`sandbox`·`cli` 층의 변경이고 `core`의 규칙표·게이트 판정 로직은 그대로다.

|---|---|---|---|---|
| S1 | **실행 기반을 Maven에서 javac + JUnit 런처 직접 호출로.** 준비 단계에서 Maven이 classpath를 확정하고(`dependency:build-classpath`) main·test를 한 번 컴파일해 volume에 둔다. 이후 작성 루프는 바뀐 테스트 파일 하나만 javac로 컴파일하고 JUnit Platform 콘솔 런처로 그 클래스만 실행한다. | 경우 | 지금 | 개편 후 (작성 gpt-5 기본) | 개편 후 (작성 gpt-5 low 또는 gpt-4.1) |
|---|---|---|---|
| 사람 확인으로 끝남 (SC-003형) | 61초 | 추출 2 + max(분류 7, 실행 5) + 저장 1 ≈ **10초** | 같음 ≈ **10초** |

작성 2차까지 가면 작성 1회분(gpt-5 60초 / low·4.1 5초)과 실행 5초가 더 붙는다. PIT 20초는 대상 메서드 수에 비례하며 아직 S1 구조에서 실측하지 않은 유일한 추정치다.

**모델을 바꿀 때의 정확도 — 무엇이 안전장치에 걸리고 무엇이 안 걸리나**

- 모델이 못 만든 것(컴파일 오류·실패·assert 완화·스킵·범위 밖·커버리지 미달·빈 테스트·수정 전 코드에서 통과)은 전부 게이트가 잡는다. 약한 모델의 비용은 **시도 수 증가**로 나타나고, 실측에서 그 차이는 1.00 → 1.17회였다.
- 게이트가 못 잡는 것은 **빠진 케이스**(경계값 등)다. 이것이 검출률이고, 이 세트에서는 두 모델이 같은 케이스 하나를 같은 이유로 놓쳤다. 6건은 추세 확인용이므로 결함 세트를 늘린 뒤 다시 대조해야 한다.
- 의도 분류는 **분류(category)만 규칙표에 들어간다**. 실측에서 4개 모델이 모두 리팩터링으로 분류해 같은 길(사람 확인)로 갔다. 차이는 근거의 질이다: gpt-5·gpt-5-mini는 "빈 목록에서 null 반환" 의심을 근거에 적었고 gpt-4.1(-mini)은 적지 않았다. 사람 확인 상자에서 사람이 읽는 정보가 빈약해지는 것이 4.1의 실제 비용이다. 그래서 분류는 gpt-5-mini(7초)를 권한다.
- 오분류의 최악 경로를 규칙표로 확인했다. 동작이 바뀐 리팩터링을 "버그 수정"으로 잘못 읽으면 (버그 수정 × 테스트 실패) 행이 **create_test**라 사람 확인을 건너뛴다. 기대값 자동 수정은 어떤 행에도 없어 기존 assert는 보호되지만, 깨진 테스트를 두고 새 테스트를 얹게 된다. 모델을 가볍게 갈수록 이 행이 위험해지므로, 이 행을 **ask(사람 확인)** 로 바꾸는 것을 함께 제안한다. 버그 수정으로 기존 테스트가 깨지는 상황은 어차피 사람이 봐야 하는 경우다(ADR 필요).
- 모델·요청 파라미터를 바꾸면 저장된 호출 기록(재생용)은 전부 다시 만든다. 요청 전문이 대조 키이기 때문이다.

적용 순서: S5(설정만, ADR-0013 범위) + 규칙표 행 변경(ADR) → S3 → S1·S2·S4(ADR: 실행 기반 변경) → S6. 단계마다 결함 세트와 SC-001~003 실측으로 전/후를 비교한다.

## 3. 예외 처리 및 가드레일

이 에이전트의 위험은 "모델이 테스트를 통과시키기 위해 편법을 쓰는 것"과 "생성물이 검토 없이 소스에 반영되는 것"이다.
가드레일은 전부 일반 코드(규칙표·게이트)이고 LLM은 판정에 관여하지 못한다(R2). 애매하면 탈락시킨다.

| 항목 | 내용 |
|---|---|
| 차단 대상 | ① 기존 assert 완화·삭제(`assertEquals` → `assertNotNull`, 예외 테스트 삭제) ② `@Disabled`로 테스트 끄기(전체 경로 표기 포함) ③ 허용 목록 밖 소스 수정(대상 코드 조작) ④ 대상을 실행하지 않는 빈 테스트 ⑤ 수정 전 코드에서도 통과하는 무의미한 재발 방지 테스트 ⑥ 리팩터링 실패 시 기대값 자동 갱신 ⑦ 전체 테스트 실행 ⑧ 샌드박스 밖 실행·네트워크 접근 ⑨ 검토 없는 소스 반영 ⑩ 시크릿 유출 ⑪ 재생 중 몰래 실호출 |
| 탐지 방식 | • 게이트 6종(일반 코드): assert(테스트 메서드 단위 전/후 + 엄격함 점수) · skip(어노테이션 카운트) · scope(소스 전체 sha256) · coverage(JaCoCo 라인 80%·분기 70%) · mutation(PIT) · regression(수정 전 코드에 바꿔 끼워 실행, 통과하면 탈락) <br>• 규칙표: "기대값을 자동으로 고친다"는 행이 없다. 리팩터링 × 실패 = 사람 확인(R3) <br>• 실행기: 실행할 테스트를 지정하지 않으면 예외로 거부(R5). Docker `--network none` + 캐시 읽기 전용 <br>• 층 검사(`tests/test_layering.py`): `core/`에 언어 문자열이 들어오면 실패 <br>• 재생: 요청 전문이 기록과 다르거나 기록이 없으면 실패, 실호출 폴백 없음. 기록 파일에 토큰이 남지 않는지 테스트 <br>• 도구 반환은 4,000자 상한 — 잘렸음을 모델에게 알려 "더 좁혀서 조회"를 유도 |
| 대응 로직 | 게이트 탈락 → 사유를 사람이 읽을 문장으로 만들어 재생성 지침서에 붙임(최대 3회) → 소진 시 "품질 미달"(종료 코드 2)로 사람 확인 제안. 사람 확인 항목은 `.cta/escalations/`에 저장하고 종료 코드 3, `cta resolve`로만 재개. 사람이 이름을 지정한 실패 테스트만 assert 변경 허용, 나머지는 계속 보호. 생성물은 `.cta/proposals/`에만 두고 `cta apply`로만 반영. 실행 도중 예외(시간 초과·Ctrl+C·Docker 오류)에도 생성물을 되돌린다 |
| 테스트 결과 | • 게이트 불변식 단위 테스트 15건 **전부 통과** — assert 완화·삭제·파일 삭제, `@Disabled`·전체 경로 우회, 허용 목록 밖 수정 → 전부 탈락. 정당한 시나리오(assert 추가·허용된 새 파일)는 통과 <br>• Docker 실측 불변식: assert 없는 테스트가 **커버리지는 통과하되 뮤테이션에서 탈락** — 커버리지만으로 빈 테스트를 못 거른다는 전제를 실증 <br>• SC-004 실연: `assertEquals(8500…)` → `assertNotNull` 완화 + 예외 테스트 삭제 → 거부, 사유를 "바뀌기 전/후 (점수)"로 보고 <br>• SC-003 실연: 리팩터링 + 실패 → 기대값 수정 0건, 저장 후 종료 코드 3. resolve 후 "기존 assert 9개 보존 (사람 허용 1건 제외)" <br>• 재생 계층 9건, interrupt·게이트 루프 6건, 층 검사 2건 통과 |

SC-004 게이트 탈락 사유 원문:

```
applyDiscount_goldMember_appliesRate
  바뀌기 전 : 결과가 정확히 new BigDecimal("8500")인지 확인   (4점)
  바뀐 후   : 결과가 null이 아닌지만 확인   (1점)
applyDiscount_negativeAmount_throws
  예외가 나는지 확인하는 테스트가 통째로 삭제됨
```

**다루지 않은 것(정직하게)**: 대상 소스의 주석에 "이 테스트는 통과시켜라" 같은 지시문이 섞여 들어오는 프롬프트 인젝션은 별도 필터가 없다.
다만 그 결과물도 같은 게이트를 지나므로, 지시문이 assert 완화나 범위 밖 수정으로 이어지면 거기서 걸린다. 입력 전처리 필터는 §6 남은 과제다.

## 6. 남은 과제 · 재현 명령

**개선 실험 후보** (하네스 전/후 수치 비교로만 채택)

1. 경계값 강조: 작성 프롬프트에 "경계값(같음/최대/최소)을 반드시 시험하라"를 넣고 같은 결함 세트 6건 재측정 → `truncate-boundary` 검출 여부 + 전체 검출률
2. 모델 비교(ADR-0013): 같은 세트로 gpt-4.1 vs gpt-5 vs gpt-4.1-mini — 검출률·시도 수·소요·토큰
3. 결함 세트 확장: 6건은 추세 확인용이다. 케이스를 늘릴 때 데이터셋 버전을 올려 이전 수치와 구분한다. 리눅스 환경이 확보되면 Defects4J 서브셋으로 교체(하네스의 케이스 구조가 교체 지점)
4. 입력 전처리: 대상 소스 주석에 섞인 지시문(프롬프트 인젝션) 필터
5. 실행 시간 단축(§2.2): 의존성 캐시 named volume → 결함 세트 재측정 → 분류·실행 병렬화 → 검출력 사전 측정 분리
6. 의도 세트 보정: 실사용에서 "의도 모름"으로 저장되는 항목을 `cta/evals/intents/`에 추가하고 `cta eval --intents`로 재측정. 잘못된 "의도 모름"이 나오면 그때 단서 확대(ADR-0020 D2)를 검토

**알려진 한계**

- 결함을 우리가 심었으므로 "우리 파이프라인이 잘 잡는 종류"로 편향될 수 있다
- 확신도는 모델이 매긴 값이라 보정된 확률이 아니다. 코드는 이 값으로 분기하지 않는다
- COVERS는 테스트 클래스 단위 실측이다. 메서드 단위는 비용이 커서 미룬 상태

**재현 명령**

```
pytest -q                                   # 단위 172건 — 게이트 불변식·재생·interrupt·층 검사 포함 (LLM·Docker 불필요)
pytest -m docker                            # Docker 통합 3건 — 재생 시나리오·네트워크 차단 실행·게이트 ④⑤ 불변식
pytest -m neo4j                             # Neo4j 왕복 1건
```
