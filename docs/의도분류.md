# 의도 분류 — 에이전트는 "왜 바꿨는지"를 어떻게 알아내나

`cta maintain`을 실행하면 에이전트는 바뀐 메서드마다 **"이 변경은 버그 수정인가, 리팩터링인가, 새 기능인가"**를
판단하고 화면에 근거와 함께 보여준다. 이 문서는 그 판단이 정확히 어떤 순서로, 무엇을 재료로, 누가(LLM인지
일반 코드인지) 하는지를 처음 보는 사람 기준으로 설명한다.

코드 위치: `cta/adapters/java/changes.py`(단서 수집) → `cta/llm/intent.py` + `cta/llm/prompts/classify_intent.md`(LLM 호출)
→ `cta/core/pipeline/maintain.py`(순서 조립) → `cta/core/pipeline/decide.py`(규칙표) → `cta/cli/render.py`(화면 출력)

---

## 1. 왜 의도를 분류하나 — 같은 diff라도 할 일이 다르다

테스트 도구가 코드 변경을 봤을 때 할 수 있는 일은 크게 셋이다.

| 개발자가 한 일 | 테스트 쪽에서 할 일 |
|---|---|
| 버그를 고쳤다 | 같은 버그가 다시 생기면 잡아낼 **재발 방지 테스트**를 추가한다 |
| 동작은 그대로 두고 코드만 정리했다(리팩터링) | 기존 테스트가 **그대로 통과해야** 한다. 깨졌다면 정리하다가 동작을 바꾼 것이므로 사람이 봐야 한다 |
| 새 기능을 넣었다 | 그 기능을 시험하는 테스트를 추가한다 |

diff만 봐서는 이 셋이 구분되지 않는다. `> 0`을 `>= 0`으로 바꾼 한 줄이 버그 수정일 수도, 일부러 정책을 바꾼
새 기능일 수도 있다. 그래서 **"왜 바꿨나"를 먼저 정하고**, 그 답에 따라 할 일을 고른다.

## 2. 전체 흐름 한눈에

```
git diff ──① 변경 추출──▶ 메서드 단위 목록 + 단서 ──② 건별 의도 분류──▶ 판단·확신도·근거
                                                          (주석만 바뀌면 LLM 생략)
                                                                  │
기존 테스트 찾아 실행 ──③ pass / fail / none ────────────────────┤
                                                                  ▼
                                                    ④ 규칙표 ──▶ 할 일 (create_test / no_action / escalate / ask)
                                                                  ▼
                                                    ⑤ 화면 출력 ── ① 대상 / 판단 (확신도) / 근거 / 분석 / 기존 테스트 / 참고 / 할 일
```

여기서 **LLM이 등장하는 곳은 ② 하나뿐**이다. ①③④⑤는 전부 일반 코드(정규식·git·표 조회)다.
이렇게 나눈 이유는 3절 끝에 있다.

## 3. 단계별로 무엇을 하나

### ① 변경 추출 — "어디가 바뀌었나"와 단서 모으기 (일반 코드)

`git diff --unified=0`을 읽어 바뀐 줄을 **메서드 단위**로 묶는다. 같은 커밋에 두 메서드가 바뀌었으면 두 건이 된다.
묶으면서 판단에 쓸 **단서**를 같이 센다. 전부 계산이라 같은 diff면 언제나 같은 결과가 나온다.

| 단서 | 어떻게 얻나 | 왜 단서가 되나 |
|---|---|---|
| 커밋 메시지·이슈 번호 | `git log base..HEAD`, `#4821` 같은 표기 정규식 | "fix:", "refactor:" 접두사는 작성자가 직접 밝힌 의도다 |
| 메서드 시그니처가 바뀌었나 | 바뀐 줄이 메서드 선언 모양인지 | 시그니처가 바뀌면 "코드만 정리"일 가능성이 낮다 |
| 접근 제어자가 바뀌었나 | 선언 줄의 public/private 비교 | 위와 같다 |
| 늘고 준 줄 수 | `+`/`-` 줄 세기 | +1/-1이면 조건 하나 고친 것, +40이면 기능 추가에 가깝다 |
| 주석·공백만 바뀌었나 | 바뀐 줄이 전부 `//`, `*`, 빈 줄인지 | 시험할 동작 자체가 없다 |

결과는 `ChangeSet`(심볼 목록 + 커밋 메시지 + 이슈 번호) 하나로 다음 단계에 넘어간다.

### ② 의도 분류 — LLM에게 묻기 (변경 한 건당 1회)

**주석·공백만 바뀐 변경은 LLM에 묻지 않는다.** 계산으로 확정되는 것을 굳이 물을 이유가 없고, 물으면 비용과
흔들림만 생긴다. 이 경우 바로 "의미 없는 변경 (확신도 100%)"으로 정한다. 여기서 100%는 모델의 추정치가 아니라
"계산으로 판정했다"는 뜻이다.

나머지는 변경 **한 건마다** 프롬프트를 하나씩 만들어 보낸다. 프롬프트에 들어가는 것:

```
[대상]          OrderService#applyDiscount
[단서]          - 커밋 메시지: fix: 할인 임계금액 경계 조건 오류 수정 (#4821)
                - 이슈 참조: #4821
                - 메서드 시그니처: 그대로
                - 접근 제어자: 그대로
                - 바뀐 줄 수: +1 / -1
[변경 diff 발췌] -  if (customer.getGrade() == Grade.GOLD && amount.compareTo(THRESHOLD) > 0) {
                +  if (customer.getGrade() == Grade.GOLD && amount.compareTo(THRESHOLD) >= 0) {
[과거 판단 사례]  없음
```

그리고 답을 **JSON 형식으로만** 달라고 한다:

```json
{
  "category":   "bug_fix",          // bug_fix | refactor | new_feature | trivial | unclear
  "confidence": 98,                 // 0~100
  "evidence":   ["커밋 메시지: fix: …", "조건문 비교 연산자 변경: > 0 → >= 0", "메서드 시그니처와 접근제어자 불변"],
  "analysis":   "임계값과 정확히 같은 금액에서도 할인이 적용되도록 … 테스트는 amount == THRESHOLD일 때 …"
}
```

프롬프트가 모델에게 못 박는 규칙 두 가지가 핵심이다.

1. **category는 "작성자가 무엇을 하려 했나"다.** 그 의도대로 동작이 실제로 보존됐는지는 뒤에서 기존 테스트를
   돌려 판정하니, 모델이 그걸 대신 판정하지 않는다. 커밋 메시지가 refactor를 말하고 시그니처가 그대로면
   refactor로 보되, 정리하다 동작이 달라진 것 같으면 그 의심 지점을 `evidence`에 적으라고 한다.
   (처음엔 이 규칙이 없어서 모델이 "동작이 바뀐 것 같다"며 unclear로 도망갔다 — 4절 참고)
2. **확신이 없으면 반드시 unclear.** 추측으로 bug_fix나 refactor를 고르면 안 된다. unclear는 뒤에서
   "사람에게 묻기"로 이어지므로, 모르는 것을 모른다고 하는 쪽이 안전하다.

응답은 `parse_intent()`가 읽는다. 여기서도 방어를 한다:

- JSON 앞뒤에 설명이나 코드 블록이 붙어 있어도 `{ … }` 부분만 뽑는다
- JSON이 깨졌거나 category가 다섯 값 밖이면 → **unclear**로 강등한다 (예외를 던지지 않는다)
- confidence가 0~100이면 100으로 나누고, 0~1이면 그대로, 이상한 값이면 0.0
- evidence는 문자열 목록으로 최대 4개까지

즉 모델이 아무리 이상하게 답해도 결과는 항상 `Intent(category, confidence, evidence, analysis)` 하나이고,
이상할수록 unclear에 가까워진다.

### ③ 기존 테스트 상태 — 이 메서드를 검증하는 테스트를 찾아 돌린다 (일반 코드)

의도만으로 할 일이 정해지지 않는다. "리팩터링"이라도 기존 테스트가 **통과하면 할 일 없음**, **실패하면 사람에게**다.
그래서 대상 메서드를 실제로 실행하는 테스트를 찾는다.

- Neo4j 코드 그래프가 있으면: JaCoCo로 실측한 COVERS 관계("이 테스트 클래스가 이 메서드를 실행했다")에서 찾는다
- 없으면: 테스트 소스에서 클래스 이름과 `메서드이름(` 호출 모양을 같이 가진 파일을 찾는다(근사치)

찾은 테스트만 Docker 샌드박스에서 돌려 `pass` / `fail` / `none`(테스트 없음) 중 하나를 얻는다.

### ④ 규칙표 — 의도 × 테스트 상태 → 할 일 (일반 코드, 표 조회뿐)

| 의도 | 기존 테스트 | 할 일 |
|---|---|---|
| 버그 수정 | (무관) | `create_test` — 재발 방지 테스트 추가 |
| 새 기능 | (무관) | `create_test` — 기능 테스트 추가 |
| 리팩터링 | 통과 | `no_action` — 동작 보존 확인됨 |
| 리팩터링 | **실패** | `escalate` — 사람 확인 (저장하고 멈춤) |
| 리팩터링 | 없음 | `ask` — 특성 테스트를 만들지 사람에게 묻기 |
| 의미 없는 변경 | (무관) | `no_action` |
| 판단 불확실 | (무관) | `ask` — 사람에게 묻기 |

표에 **"기대값을 자동으로 고친다"는 행이 없다**는 점이 이 표의 존재 이유다. LLM의 분석 문장은 뒤에서 테스트를
만들 때 지침서로 붙을 뿐, 어느 행으로 갈지는 못 바꾼다.

### ⑤ 화면 출력 — 판단을 숨기지 않는다

②의 결과와 ③④를 합쳐 변경 건마다 이렇게 찍는다(실제 실행 출력):

```
  ① OrderService.applyDiscount
     판단   버그 수정             (확신도 98%)
     근거   · 커밋 메시지: fix: 할인 임계금액 경계 조건 오류 수정 (#4821)
            · 조건문 비교 연산자 변경: amount.compareTo(THRESHOLD) > 0 → >= 0
            · 메서드 시그니처와 접근제어자 불변, 변경 라인 수 +1/-1로 경계 조건만 조정
     분석   GOLD 등급 고객의 할인 적용 조건에서 임계값 비교를 초과(>)에서 이상(>=)으로 수정하여 … 테스트는
            GOLD 고객에서 amount == THRESHOLD일 때 할인 적용 여부가 참인지 확인하고 …
     기존 테스트   없음  → 없음
     참고   비슷한 과거 사례 없음
     할 일  재발 방지 테스트 추가

  ② OrderService.total
     판단   의미 없는 변경          (확신도 100%)
     근거   · 주석만 수정됨 (코드 줄 변경 0)
     할 일  없음
```

- **판단·확신도·근거**: ②의 JSON 그대로
- **분석**: 이 문장이 그대로 테스트 작성 지침서에 들어간다 — 무엇을 시험해야 하는지
- **기존 테스트**: ③의 결과
- **참고**: 같은 메서드·클래스에 대해 사람이 전에 내린 결정(`cta resolve`가 남긴 판단 메모). 프롬프트의
  "과거 판단 사례"에도 같은 내용이 들어가지만 **참고일 뿐** 규칙표를 우회하지 못한다
- **할 일**: ④의 결과

### 왜 LLM을 ②에만 쓰나

틀렸을 때의 피해가 다르기 때문이다.

- ②의 **분석 문장**이 틀리면 → 만들어지는 테스트의 품질이 떨어진다. 아쉽지만 사고는 아니다. 게이트가 뒤에서 거른다
- ④의 **길**이 틀리면 → 사람 확인 없이 기존 테스트의 기대값이 바뀔 수 있다. 이건 사고다

그래서 흔들릴 수 있는 것(LLM)은 문장을 채우는 자리에만 두고, 길을 정하는 자리는 표로 고정했다.
②가 흔들려도 결과가 unclear로 수렴하고, unclear는 표에서 "사람에게 묻기"로 가므로 안전한 쪽으로 기운다.

## 4. 실제로 어떻게 판단했나 — 실측 사례 3건 (gpt-5, 2026-09-03)

| 변경 | 단서 | 모델의 판단 | 규칙표 결과 |
|---|---|---|---|
| `applyDiscount`의 `> 0` → `>= 0` | fix 메시지, #4821, 시그니처 그대로, +1/-1 | 버그 수정 98% — 근거: fix 메시지 / 연산자 변경 / 시그니처 불변 | 재발 방지 테스트 추가 → 수정 전 코드에서 실패하는지까지 확인 |
| `total`의 주석 한 줄 | 코드 줄 변경 0 | (LLM 미호출) 의미 없는 변경 100% | 할 일 없음 |
| `calculate`의 for문 → 스트림 | refactor 메시지, 시그니처 그대로, +10/-11 | 리팩터링 86~90% — 근거: refactor 메시지 / 시그니처 그대로 / **빈 목록 처리가 ZERO → null로 바뀐 의심** | 기존 테스트 4건 중 1건 실패 → 사람 확인(저장하고 멈춤) |

세 번째 사례가 이 설계의 요점을 보여준다. 모델은 "동작이 달라진 것 같다"는 의심을 **근거에 적었을 뿐** 분류를
바꾸지 않았고, 실제로 동작이 바뀌었는지는 기존 테스트 실행이 판정했으며, 그 결과 규칙표가 사람에게 넘겼다.
사람은 화면에서 근거·실패한 테스트(기대 0, 실제 null)·바뀐 위치를 보고 `cta resolve`로 답한다.

프롬프트를 고치기 전에는 같은 diff에서 모델이 unclear(87%)를 골랐다. 틀린 답은 아니지만 "질문" 상자로 가서
사용자가 실패 테스트 정보를 못 보는 흐름이었다. "의도와 동작 보존 판정을 분리한다"는 규칙을 프롬프트에 넣자
refactor + 근거의 의심 지점으로 답했고, 그게 시나리오가 원하는 흐름이다.

## 5. 자주 하는 오해

- **"확신도 98%면 98% 확률로 맞는다는 뜻인가?"** — 아니다. 모델이 스스로 매긴 점수라 보정된 확률이 아니다.
  사람이 근거를 읽을 때 "얼마나 자신 있어 하는가"를 보는 참고값이고, 코드는 이 값으로 분기하지 않는다.
  분기는 category로만 한다.
- **"모델이 refactor라고 했으니 동작이 안 바뀐 것 아닌가?"** — 아니다. refactor는 작성자의 **의도**일 뿐이고,
  동작 보존 여부는 기존 테스트 실행이 판정한다. 그래서 refactor + 실패 조합이 존재한다.
- **"unclear가 자주 나오면 성능이 나쁜 것 아닌가?"** — 단서가 없으면(커밋 메시지 없음, 미커밋 변경) unclear가
  나오는 게 맞다. 커밋 메시지에 `fix:`/`refactor:` 접두사와 이슈 번호를 적으면 판단이 안정된다.
- **"LLM 응답이 깨지면 파이프라인이 죽나?"** — 안 죽는다. 어떤 실패도 unclear로 수렴하고, unclear는 사람에게
  묻는 길로 간다.

## 6. 바꾸고 싶을 때 어디를 만지나

| 바꾸고 싶은 것 | 위치 |
|---|---|
| 분류 기준 문구, 근거 작성 규칙 | `cta/llm/prompts/classify_intent.md` |
| 새 단서 추가(예: 바뀐 파일 수) | `changes.py`의 `_Bucket`·`ChangedSymbol`, `intent.py`의 `describe_clues()` |
| 분류 값 추가 | `core/pipeline/models.py`의 `KNOWN_INTENTS` + `decide.py`의 규칙표 행 + `render.py`의 라벨 |
| 화면 형식 | `cta/cli/render.py`의 `render_analysis()` |
| 단위 테스트 | `tests/test_maintain_core.py` (파싱·규칙표·출력), `tests/test_java_reporting.py` (단서 추출) |
