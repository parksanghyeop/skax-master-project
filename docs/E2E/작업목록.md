# E2E 작업 목록 — 무엇을, 왜, 어떻게, 어떻게 확인하나

우선순위 순. 각 항목은 `무엇 / 왜 / 어떻게 / 검증` 네 줄이다. 검증은 실행 결과여야 한다("될 것 같다" 금지).
마일스톤 표기: **a** 마감 · **b** 확장 · **c** 릴리스 (README.md §3).

모든 코드 작업은 CLAUDE.md 규칙을 따른다. 특히 새 의존성은 추가 전에 묻고, 설계가 바뀌면 ADR을 코드보다 먼저 쓴다.

## A. 제품 마감 (M8-a)

### A-1. CI 파이프라인 — 재생 모드로 그린 [a]

- **무엇**: `.github/workflows/ci.yml`(또는 사내 CI 동등물). 잡 2개 — `check`(ruff check · ruff format --check · `pytest -q`), `integration`(수동 트리거, `pytest -m docker`, `pytest -m neo4j`).
- **왜**: R7 "CI는 replay 모드, 기록 없으면 실패"가 규칙인데 CI 자체가 없다. 남이 PR을 열 수 있는 상태가 아니다.
- **어떻게**: Python 3.11·3.12 매트릭스. `pip install -e . --group dev`. 저장된 LLM 호출 기록이 리포에 있는지 먼저 확인(없으면 재생 테스트가 실패한다 — 그게 의도). Windows 전용 스크립트(`render_capture.py` 폰트 경로)는 CI 대상에서 제외.
- **검증**: PR 하나 열어 `check` 그린. 기록 파일 하나를 지운 브랜치에서 빨강이 되는지 확인(폴백 없음 증명).

### A-2. 설정 파일 `cta.toml` 확장 [a]

- **무엇**: 게이트 기준치 4개 외에 `retry.ask_every`(4) · `retry.max_total`(8) · `gateway.timeout_sec`(300) · `llm.model` · `budget.max_tokens_per_run`(새로 추가, 기본 무제한)을 `cta.toml`에서 읽는다. 환경변수가 있으면 환경변수가 이긴다(현행 `.env` 규칙과 같은 우선순위).
- **왜**: 3단계 스킬 "설정 파일: 커버리지 기준치, 재시도 상한, 반복·비용 예산, 모델 선택. 기본값은 v4와 일치". 지금은 `writer_graph.py` 상수와 `gateway.py` 환경변수에 흩어져 있다.
- **어떻게**: `core/gates.py`의 `load_gate_config`를 `core/config.py`로 일반화(core는 키 이름만 알고 의미는 몰라도 된다). 시크릿(URL·API 키)은 **절대** toml로 옮기지 않는다 — ADR-0011.
- **검증**: `cta.toml`로 `max_total=2`를 두고 Fake 어댑터 테스트에서 3번째 시도가 일어나지 않는지. 사용가이드 §9 갱신.

### A-3. 시크릿 3 테스트 [a]

- **무엇**: ① 게이트웨이 키는 환경변수·`.env`만(있음, `test_llm_config.py`) ② 샌드박스 컨테이너 env에 `CTA_GATEWAY_*`가 전달되지 않음 ③ 로그·저장된 호출 기록·에러 메시지에 키가 마스킹됨.
- **왜**: 스킬 "3개 모두 테스트로 고정". 지금은 1/3. 게이트웨이 토큰과 샌드박스를 함께 다루는 도구라 사고 한 번이 신뢰를 끝낸다.
- **어떻게**: ② `docker_sandbox.py`의 실행 인자를 조립하는 함수를 순수 함수로 분리해 `-e` 목록을 검사. ③ `llm/gateway.py`·`replay.py`에서 예외 문자열과 기록 JSON을 만들 때 `api_key` 값을 `****`로 치환하는 한 함수. 커밋 전 diff 검사는 hookify 규칙으로(README 1군).
- **검증**: 테스트 3개 초록. 실제 기록 파일 하나를 열어 키 모양 문자열이 없는지 grep.

### A-4. 종료 코드·비대화 실행 — CI에서 쓸 수 있게 [a]

- **무엇**: 종료 코드 0(성공) · 2(품질 미달) · 3(사람 확인 필요) · 1(오류)을 사용가이드에 표로. `cta maintain --diff origin/main...HEAD`를 PR 검사에 넣는 예시(GitHub Actions 스니펫)와 "3이면 실패가 아니라 리뷰 요청"이라는 해석 안내. 진행 표시(`[ 113초] …`)를 TTY가 아니면 끄는 `--quiet` 또는 자동 감지.
- **왜**: 스킬 "종료 코드 3종을 CI에서 쓸 수 있게". 코드는 있고 쓰는 법이 없다.
- **어떻게**: 코드 변경은 TTY 감지 한 곳. 나머지는 문서.
- **검증**: `cta maintain … ; echo $?`로 세 값이 각각 나오는 시나리오 재현(SC-002 → 0, SC-003 → 3, 게이트 3회 탈락 Fake → 2).

### A-5. 에러 메시지에 다음 행동 [a]

- **무엇**: 사용자가 만나는 실패 지점마다 "왜 / 지금 할 일 / 명령" 세 줄. 대상: Docker 미실행, `.env` 없음·키 없음, pom.xml 없음, Neo4j 접속 실패(폴백 안내는 있음), 게이트웨이 시간 초과, 대상 클래스 못 찾음, 기록 없음(재생 모드).
- **왜**: 스킬 UX 항목. 현재 "다음:" 안내는 2곳뿐이고 설치 직후 실패가 가장 많이 나는 곳이 여기다.
- **어떻게**: `cli/render.py`에 안내 문구 표 하나. 예외마다 흩뿌리지 않는다.
- **검증**: 위 7상황을 Fake·환경변수 조작으로 재현해 문구 스냅샷 테스트.

### A-6. 대화 압축 — 판단 기록 [a]

- **무엇**: 구현하지 않는다. 대신 `docs/adr/ADR-0017-no-conversation-compaction.md`(번호는 작성 시점 확정)에 "작성 루프는 매 시도 단발 프롬프트라 대화가 누적되지 않는다. 원문 유지 대상(규칙·현재 코드·직전 실패)은 이미 그 셋만 넣고 있고, 오래된 시도는 `history`에 화면용으로만 남는다"를 기록. 토큰 계측(`llm/metering.py`)으로 시도 회차별 프롬프트 크기가 일정함을 수치로 첨부.
- **왜**: 스킬 항목이지만 구조상 불필요하다. "안 했다"가 아니라 "필요 없음을 확인했다"로 닫아야 한다.
- **검증**: SC-002 재생에서 1차·2차 시도의 요청 토큰 수 비교(둘째가 첫째의 2배가 되지 않음).

## B. 확장 — 기술 어필 (M8-b)

### B-1. 워크플로우에 스킬 붙이기 [b] — 사람 멘토 피드백

설계 스케치는 `docs/피드백반영계획.md` §2에 있다. 여기서는 작업 순서만.

1. **멘토 확인**: "스킬"이 제품 워크플로우 쪽인지(지식 묶음을 골라 프롬프트에 주입) 확인. 답이 없으면 제품 쪽으로 진행.
2. **ADR-0016**: 스킬 = `adapters/java/skills/<이름>/SKILL.md`(설명 + `when` 조건 + 본문 300~600자). 선택기는 규칙 기반(R2), 도구 추가 없음(R4), core는 `SkillProvider` 포트 하나만 안다(R1). 프롬프트는 `write_test.md`의 `$style` 빈칸에 주입(지금은 고정 문장 한 줄).
3. **스킬 2개**: `junit5-mockito`(mock 판정 시), `regression-test`(bug_fix × create_test 시). 5개로 늘리는 것은 수치를 본 뒤.
4. **저장된 호출 기록 재생성**: 프롬프트가 바뀌므로 `scripts/record_golden.py --live`. 모델 이름·프롬프트 해시가 결과에 묶인다.
5. **전/후 측정**: SC-001(`--max-methods 4`) · SC-002 · 로컬 결함 세트. 스킬 없음/있음 각 3회. 지표: 1차 통과율, 시도 수, 토큰, 게이트 탈락 수, 검출률. `evals/results/`에 저장.
6. **산출물**: 전/후 표 + 스킬 선택 로그 1건(어떤 신호로 어떤 스킬이 붙었는지) 텍스트.

- **검증**: `test_layering.py` 통과(스킬 파일이 core 밖). 선택기 단위 테스트(신호 → 스킬 이름). 전/후 표.
- **하지 않을 것**: 모델이 스킬을 탐색하는 도구. 스킬 안에 게이트 완화·기대값 수정 허용 문구.

### B-2. 결함 세트 확장 — 6건 → 12건 이상 [b]

- **무엇**: `cta/evals/defects/`에 6건 추가. 유형을 다양화한다 — 컬렉션 순서, 문자열 대소문자, 날짜 경계, 예외 타입 오류, 상태 전이 누락, 반올림 모드. `DATASET_VERSION`을 v2로.
- **왜**: ADR-0014 "케이스 수가 작아 통계적 힘이 약하다. 유형 다양화". 스킬 전/후(B-1)와 프롬프트 실험(B-3)의 측정 바탕이 이 세트다.
- **어떻게**: 케이스마다 `Buggy.java` + `case.toml`. 고친 버전에서 생성 → 버그 버전에서 실패해야 검출.
- **검증**: `cta eval`로 v2 베이스라인 수치 확보. v1 수치와 구분해 기록.

### B-3. 프롬프트 실험 1건 — 경계값 명시 [b]

- **무엇**: 작성 프롬프트에 "경계값(같음/최대/최소)을 반드시 시험하라" 추가(hardening-notes 개선 후보 1). B-1의 `boundary-exception` 스킬로 흡수해도 된다.
- **왜**: 베이스라인 미검출 1건(truncate-boundary)이 경계 off-by-one이었다.
- **검증**: 하네스 전/후. truncate-boundary 검출 여부 + 전체 검출률.

### B-4. MCP 서버 [b]

- **무엇**: `cta/mcp/server.py`. 노출하는 것은 CLI 명령과 1:1 — `generate`, `maintain`, `resolve`, `list_proposals`(diff), `apply`. 각 핸들러는 `cli/*_cmd.py`가 쓰는 core 조립 함수를 그대로 호출한다.
- **왜**: 스킬 M8. Claude Code 등에서 도구로 호출. 3단계 "발표의 뼈대" 중 하나.
- **어떻게**: **의존성 추가 전에 묻기**(`mcp` SDK). ADR 한 장 — "MCP 도구 5개는 에이전트 내부 도구 6개(R4)와 다른 층이다"를 명시해 R4 혼동을 막는다. 긴 작업(generate 5~10분)은 MCP 응답 시간 초과를 넘기므로 작업 시작 → 진행 조회 → 결과 조회의 3단계로 나눌지, 동기로 두고 시간 초과를 늘릴지 먼저 결정. 시크릿은 서버 프로세스의 환경변수로만.
- **검증**: Claude Code에 MCP 서버 등록 → `generate` 호출 → 제안 생성 확인 캡처. CLI와 MCP가 같은 함수를 호출하는지 grep으로 중복 없음 확인. `mcp-server-dev` 플러그인(README 2군)으로 검사.

### B-5. 판단 메모 검색 강화 + 불변식 테스트 [b]

- **무엇**: ① 게이트웨이가 임베딩 API를 제공하는지 확인. 제공하면 메모 `note`+`target` 임베딩 후 코사인 상위 3건. 미제공이면 키워드 검색(현행) 유지를 문서에 명시. ② 불변식 테스트 — 메모가 어떤 내용이어도 `decide()` 결과가 바뀌지 않음(`memos` 인자는 `IntentClassifier`에만 들어가고 규칙표는 받지 않는다는 것을 테스트로 고정).
- **왜**: 스킬 "참고용일 뿐 경로표를 우회하지 못한다 — 이 불변식의 테스트 포함". 현재 테스트는 검색·렌더만 본다.
- **검증**: 불변식 테스트 초록. 임베딩 여부 결정을 hardening-notes 또는 E2E 노트에 기록.

## C. 릴리스 — 닫기 (M8-c)

### C-1. 데모 시나리오 2개 — 3회 연속 성공 [c]

- **무엇**: ① 콜드 스타트: 테스트 없는 클래스 → `generate` → 게이트 → `diff` → `apply`. ② 유지보수: 버그 수정 커밋 → `maintain` → 재발 방지 테스트 / 리팩터링 깨짐 커밋 → escalate → `resolve` → 재개.
- **왜**: 스킬 "스크립트가 아니라 문서화된 명령 순서로, 녹화 전 3회 연속 성공".
- **어떻게**: `examples/demo/README.md`의 절차를 명령 순서표로 다듬고, 3회 실행 로그(날짜·소요·토큰)를 `docs/E2E/데모실행기록.md`에 남긴다. 데모 고정 후에는 게이트 통과 없는 변경 금지.
- **검증**: 실행 기록 3행. 녹화 파일.

### C-2. 루트 README 재작성 — 제품 README로 [c]

- **무엇**: 현재 `README.md`는 "Claude Code 구현 킷"(플러그인 추천·스킬 사용 흐름)이다. 제품 README(한 줄 소개 · 준비물 · 5분 시작 · 명령 요약 · 문서 지도 · 알려진 한계 · 라이선스)로 바꾸고, 구현 킷 내용은 `docs/개발환경.md`로 옮긴다.
- **왜**: 스킬 릴리스 체크리스트 1번. 리포에 처음 온 사람이 보는 건 루트 README다.
- **검증**: README만 보고 설치 테스트(README.md §4 조건 1) 통과.

### C-3. 설치 테스트 — 리포를 모르는 사람 1명 [c]

- **무엇**: 사용가이드만 주고 새 Maven 프로젝트에 `cta generate` 성공까지. 걸린 시간, 막힌 지점, 문구 개선점 기록.
- **왜**: 3단계 목표 그 자체. 내가 하면 검증이 아니다.
- **검증**: 기록 문서 1건 + 그로 인한 가이드 수정 커밋.

### C-4. 문서 정합 [c]

- **무엇**: ① ADR — 0001~0009 원문을 사용자에게 요청해 반입하거나, 반입 불가면 `docs/adr/README.md`에 각 번호의 결정 한 줄 요약을 남긴다(CLAUDE.md가 0009를 인용하므로 공백을 둘 수 없다). 신규 ADR(스킬·MCP·압축 불필요·설정)이 구현과 일치하는지. ② `architecture.md` 모듈 표에 `core/config.py`, `adapters/java/skills/`, `mcp/`, `cli/render.py` 안내 표 한 줄씩. ③ `contracts.md` ↔ `PoC구현.md` §2.0 필드명 대조. ④ CLAUDE.md의 "LLM 게이트웨이(Kimi/Qwen/GLM)" 표기 — 실제는 gpt-5 단일 deployment(ADR-0011·0013)이므로 갱신.
- **왜**: 스킬 체크리스트 "ADR 목록이 실제 구현과 일치". 문서가 진실의 원천인 프로젝트라 어긋나면 다음 사람이 잘못된 쪽을 믿는다.
- **검증**: `claude-md-management` 플러그인 점검 결과 또는 수동 대조표.

### C-5. 알려진 한계 — 사용가이드에 절 추가 [c]

- **무엇**: `docs/사용가이드.md`에 "지원 범위와 한계" 절. 내용은 `PoC구현.md` §5의 제한적 동작 표를 사용자 말로 옮긴 것(단일 모듈 Maven만, 정규식 파서 한계, 확신도 해석, 첫 실행 5분).
- **검증**: 두 문서의 항목이 1:1로 대응.

### C-6. E2E 산출물 문서 [c]

- **무엇**: `docs/제출자료/E2E서비스개발.md`. 구성은 PoC구현.md와 같게 — 한눈에 보기 → 최소 계약(변경분) → 구현 → 문제 해결 → 검증(실행 로그 원문, 스킬 전/후 표, MCP 캡처, 설치 테스트 기록) → 구현 범위 3구역. 아울러 `PoC구현.md` §3 문제 해결 표를 `핵심구현.md`로 옮기는 길이 조정(피드백반영계획 E).
- **왜**: 검증 증거를 텍스트로 앞에 두는 것이 이번 멘토 피드백의 핵심이었다. E2E 문서는 처음부터 그 형식으로 쓴다.
- **검증**: 요약 10줄만 읽고 검증 절로 바로 갈 수 있는가.

### C-7. 크로스플랫폼 확인 [c]

- **무엇**: Linux(WSL 또는 CI 러너)에서 `pip install` → `cta demo`(재생, Docker 필요) 1회. Docker 마운트 경로·줄바꿈·폰트 의존(`render_capture.py`는 산출물용이므로 제외) 점검.
- **왜**: 지금까지 전부 Windows에서 실측했다. "남이 돌린다"의 남은 대부분 Linux·macOS다.
- **검증**: Linux 실행 로그 1건. 막힌 것은 사용가이드 문제 해결 절에.
