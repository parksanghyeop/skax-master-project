# ADR-0015: 사용자 시나리오(SC-001~004) 정합 — 명령 체계·의도 분석 출력·재개 방식

- 상태: 승인 (2026-09-02). `docs/제출자료/시나리오수립.md`의 핵심 사용자 시나리오 4건에
  구현을 맞추는 결정. v4 2.1~2.4의 원칙은 그대로 두고, 명령 이름·출력·사람 개입의
  형태를 시나리오 문서 기준으로 확정한다

## 배경

시나리오 문서와 구현을 대조한 결과, 원칙(규칙표·게이트·제안 흐름)은 맞지만
사용자가 보는 면이 어긋났다:

1. **의도 분석 결과가 사용자에게 보이지 않았다** — 변경 전체를 묶어 LLM 1회 호출,
   확신도·근거 없이 `[의도 분류] bug_fix — ...` 한 줄. 시나리오는 변경 **건별로**
   "판단 / 확신도 / 근거 / 할 일"을 보여준다(SC-002 ①②, SC-003 ①)
2. 명령이 달랐다 — `cta run --base --message --execute` vs `cta maintain --diff`,
   `cta generate <파일>` vs `cta generate --class <FQN> --max-methods N`
3. 사람에게 넘길 때 터미널 `input()`으로 그 자리에서 답을 요구했다 — 시나리오는
   "상태를 저장하고 멈춘 뒤" 별도 명령(**판단 전달 기능**)으로 이어서 실행한다(SC-003 6~8)
4. 재발 방지 테스트를 **수정 전 코드에 적용해 실패하는지** 확인하는 단계(SC-002 7)가 없었다
5. 커밋 메시지·이슈 번호·접근 제어자 변경 같은 단서를 코드가 수집하지 않고
   사용자가 `--message`로 넣어야 했다(SC-002 2)
6. "의미 없는 변경(주석만)" 분류가 없어 주석 수정에도 LLM 분류·테스트 생성이 돌았다

## 결정

### D1. 명령 체계 (시나리오 기능 이름 ↔ 명령)

| 시나리오 기능 | 명령 |
|---|---|
| 테스트 생성 기능 | `cta generate --class <FQN 또는 클래스명> [--max-methods N]` (파일명 위치 인자도 허용) |
| 변경 대응 기능 | `cta maintain [--diff <기준 커밋>]` (기본 `HEAD` = 미커밋 변경) |
| 판단 전달 기능 | `cta resolve [id] (--intended \| --test-issue \| --proceed \| --skip) [--hint]` |
| 변경 내용 확인 / 반영 | `cta diff` / `cta apply` (기존 유지) |

`cta run`은 폐기한다(`maintain`으로 대체). `--execute` 플래그는 없애고 기본이 실행,
판단만 보려면 `--plan-only`.

### D2. 의도 분석은 변경 건별 LLM 1회 호출 + 사용자에게 전부 출력

- `Intent`에 `confidence`(0~1)와 `evidence`(근거 목록)를 추가한다. 프롬프트는 JSON으로
  `category / confidence / evidence[] / analysis`를 요구하고, 파싱 실패는 전처럼 unclear
- 단서(커밋 메시지, 이슈 번호, 시그니처·접근 제어자 변경, 증감 줄 수)는 **일반 코드가
  수집**해 프롬프트에 넣고 화면에도 그대로 보여준다
- **주석·공백만 바뀐 변경은 LLM을 부르지 않고** `trivial`(의미 없는 변경, 확신도 100%)로
  분류한다 — 결정적으로 판정 가능한 것은 LLM에 묻지 않는다(R2 정신). 규칙표에
  `trivial → no_action` 행을 추가한다
- 출력 형식은 시나리오 문서의 기대 출력을 그대로 따른다(① 대상 / 판단 (확신도) / 근거 / 할 일)

### D3. 사람 개입은 "저장하고 멈춤 → resolve로 재개"

- escalate/ask 결정은 `<프로젝트>/.cta/escalations/<id>.json`에 저장하고 종료 코드 3으로
  끝낸다. 실패 테스트(이름·기대·실제), 의심 위치(변경 diff), 선택지가 보고서에 담긴다
- `cta resolve`가 저장 상태를 읽어 **결정 단계 이후부터** 이어간다. LangGraph 체크포인트를
  디스크에 남기는 방식(sqlite 체크포인터 = 새 의존성)은 쓰지 않는다 — 재개 지점이
  "테스트 작성 단계 진입"으로 고정돼 있어 JSON 상태로 충분하고 의존성이 늘지 않는다
- **R3와의 관계**: `--intended`(일부러 동작을 바꿨다)로 재개하면 실패한 테스트의 기대값을
  새 동작 기준으로 고친다. 이것은 R3 위반이 아니다 — R3가 금지하는 것은 *사람 확인 없는*
  자동 갱신이다. 사람이 이름을 지정한 실패 테스트 **만** assert 변경이 허용되고
  (게이트에 허용 목록으로 전달), 나머지 기존 assert는 여전히 게이트가 보호한다.
  resolve 결정은 `.cta/memos/`에 판단 메모로 남겨 다음 `maintain`에서 참고 자료로 보여준다
  (참고일 뿐 규칙표를 우회하지 못한다 — v4 4.2)

### D4. 재발 방지 테스트는 수정 전 코드에서 실패해야 유효

- 게이트 ⑥ `regression`(어댑터 구현): 변경 파일의 수정 전 내용을 git에서 꺼내 잠시 바꿔
  끼우고 생성 테스트만 실행한다. **통과하면 탈락**(버그를 잡는 테스트가 아니다) — 사유를
  지침서에 붙여 재생성. 파일은 try/finally로 반드시 원상 복구한다
- 의도가 bug_fix인 create_test에만 붙는다

### D5. 테스트 클래스는 대상 클래스당 하나(`<Class>Test`), 있으면 메서드를 추가

- 시나리오의 산출물(`OrderServiceTest.java (+1)`)을 따른다. 기존 파일이 있으면 그 내용을
  재료로 넘기고 "기존 메서드는 그대로 두고 추가하라"고 지시한다 — 기존 assert 보존은
  게이트 ①이, 파일 범위는 게이트 ③이 강제한다
- `--max-methods N`: 테스트 없는 공개 메서드 중 확인 항목(분기·경계·예외·null)이 많은
  순으로 N개를 고른다. 평가 하네스는 종전처럼 메서드별 클래스 이름을 명시해 벤치 의미를 유지

### D6. 재료 수집·품질 수치를 시나리오 항목으로 보여준다

- 재료(일반 코드): 확인 항목 목록(분기/경계값/예외/null — 정규식 기반 열거),
  파라미터 객체 만드는 법(builder 있음 → 직접 생성, 값 객체 → 직접 생성,
  저장소 인터페이스 → mock), 기존 테스트 스타일 발췌
- 품질: 확인 항목 충족(항목 위치 라인의 JaCoCo 실측), 버그 검출력(PIT), 기준 낮춤 여부
  (assert·skip 게이트), 소요 시간·토큰(게이트웨이 usage 합산)
- 작성 루프 상한은 시나리오대로 최대 8회, 4회마다 사용자 확인(대화형일 때)

## 결과

- 바뀌는 계약: `Intent`(필드 추가), `ChangedSymbol`(단서 필드 추가), `ChatResponse.usage_tokens`,
  WriterState(`history`, `extra_context`), 게이트 ⑥ 추가 — contracts.md 동시 갱신
- 저장된 LLM 호출 기록(대표 검증 시나리오)은 프롬프트 재료가 바뀌므로 재생성한다
- 예제 프로젝트를 Spring Boot 주문 CRUD 앱으로 교체한다 — Calculator 예제는 시나리오의
  재료 수집(mock 판단·builder)과 리팩터링 실패 상황을 보여주기에 너무 단순했다
