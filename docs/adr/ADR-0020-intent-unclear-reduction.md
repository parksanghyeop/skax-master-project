# ADR-0020: 의도 모름(unclear) 축소 — 작성자 지정 의도·단서 확대·코드 기준치·의도 세트 측정

- 상태: 승인 (2026-09-04). ADR-0015 D2(변경 건별 의도 분류·화면 출력)를 보완한다
- 관련: R3(불확실하면 추측하지 않고 묻는다), v4 2.1(길은 규칙표, 내용은 LLM), 사용자 피드백
  "의도 모름으로 거의 다 빠지는 것 같다"

## 배경

예제 프로젝트에 남은 사람 확인 항목 2건이 모두 `unclear`였다. 둘 다 **미커밋 변경**(커밋 메시지 없음)이고
변경 자체가 애매했다(`BigDecimal.ZERO → 0`, 효과 없는 대입). 원인은 세 가지가 겹친 것이다.

1. `cta maintain`의 기본값이 미커밋 변경(`--diff HEAD`)이라 가장 강한 단서(커밋 메시지)가 비어 있다
2. 분류 프롬프트가 "단서가 없으면 반드시 unclear"라고 지시한다 — 메시지 없는 변경은 unclear로 밀린다
3. 단서가 얇다: 커밋 메시지·이슈 번호·시그니처/접근 제어자 변경 여부·줄 수·바뀐 줄만의 diff.
   메서드 전체 본문, 호출하는 곳, 브랜치 이름, 파일의 최근 커밋 이력은 주지 않는다

그리고 unclear로 멈춘 항목에 사람이 의도를 알려줄 길이 없다(`cta resolve`는 `--proceed`/`--skip`만).

카테고리 세분화는 원인이 아니다. 규칙표의 행은 의도 4종 × 테스트 상태 3종이고, 분류를 더 쪼개도
단서가 없으면 여전히 고를 수 없다.

## 결정

### D1. 작성자가 의도를 말할 수 있다 — LLM 없이 unclear를 없애는 가장 싼 길
- `cta maintain --intent bug_fix|refactor|new_feature`: 작성자 지정 의도. 분류 LLM은 그대로 호출해
  근거·분석(지침서 재료)을 받되, **category는 코드가 지정값으로 덮어쓴다**(확신도 100%, 근거 첫 줄에
  "작성자 지정 의도"). 사람이 밝힌 의도는 R3의 "추측"이 아니다
- `cta maintain --message "..."`: 미커밋 변경에 커밋 메시지 대신 쓸 설명. 단서의 커밋 메시지 자리에 들어간다
- `cta resolve <id> --as bug_fix|refactor|new_feature`: 질문(ask) 항목의 의도를 사람이 지정해 규칙표부터 재개.
  refactor인데 기존 테스트가 실패 중이면 `--intended`/`--test-issue`를 안내하고 멈춘다(R3 유지)

### D2. (보류) 단서를 일반 코드가 더 모은다 — 근거 없음
D4의 개선 전 측정에서 잘못된 unclear가 0건이었다(20회, 메시지 없음 10회 포함). 단서를 늘려 고칠 대상이
측정되지 않았으므로 구현하지 않는다. 의도 세트에 실사용 unclear 항목을 추가해 `false_unclear > 0`이 되면 다시 본다.
원안: 
`ChangedSymbol`에 `body_before`/`body_after`(메서드 전체 본문, 각 1,200자 상한)와 `callers`(main 소스에서
`.메서드명(`을 부르는 위치, 최대 3곳)를, `ChangeSet`에 `branch`(현재 브랜치)와 `recent_messages`(변경 파일의
최근 커밋 제목 3개, 비교 범위 밖)를 추가한다. 전부 git·정규식으로 결정적으로 뽑는다. 프롬프트는 diff 발췌에
더해 본문 전/후를 받는다.

### D3. (보류) unclear 판정을 코드 기준치로 — 오히려 unclear를 늘린다
측정에서 메시지 없는 변형의 확신도가 64~96%였다. 기준치 0.60은 아무것도 바꾸지 못하고, 0.70이면 정답이던
`feature-average`(64%)를 unclear로 만든다. 확신도는 보정된 확률이 아니므로 기준치로 쓰지 않는다.
원안: 
- 프롬프트: "가장 가까운 분류를 고르고 불확실성은 확신도로 표현한다. unclear는 단서가 서로 **모순**될 때만"
- 코드: `[intent] confidence_min`(cta.toml, 기본 0.60) 아래면 unclear로 강등(`core/pipeline/intent_policy.py`).
  강등 사유를 analysis 앞에 붙여 화면에 보인다. R3는 유지된다 — 불확실하면 여전히 묻되, "불확실"의 기준이
  모델의 자기 선택이 아니라 조정·측정 가능한 숫자가 된다

### D4. 수치로 판단한다 — 의도 세트
`cta eval --intents`: 의도가 알려진 변경 10건(`cta/evals/intents/`)을 예제 프로젝트 복사본에 적용해
**커밋 메시지 있음/없음 두 변형**으로 분류만 실행한다(Docker 불필요). 지표: 정확도, unclear 비율, 확신도,
소요. 결과는 `cta/evals/results/intents-*.json`. 이 ADR의 개선은 이 세트의 전/후 비교로만 채택한다.

## 측정 결과 (2026-09-04, gpt-5, local-intents-v1)

| 변형 | 정확도 | unclear 비율 | 잘못된 unclear | 평균 소요 |
|---|---|---|---|---|
| 커밋 메시지 있음 (10회) | 100% | 10% (정답이 unclear인 케이스 1건) | 0 | 9.3초 |
| 커밋 메시지 없음 (10회) | 100% | 10% (같은 케이스) | 0 | 12.1초 |

결론: "거의 다 unclear로 빠진다"는 이 세트에서 재현되지 않았다. 실제로 저장됐던 unclear 2건은 컴파일이 깨지는
변경과 효과 없는 대입으로, 모델이 모른다고 답하는 것이 맞는 경우였다. 그런 경우에 필요한 것은 D1(사람이 의도를
말하는 길)이고, D1만 구현했다. 기록: `cta/evals/results/intents-local-intents-v1-gpt-5-20260904-151539.json`

## 하지 않는 것

- LangGraph `create_agent`(ReAct 루프)로 근거를 더 모으는 2단계 분류: D1~D3 뒤에도 unclear가 남을 때
  기존 도구(`inspect_target`, `query_code_graph`)만으로 검토한다. 게이트웨이 클라이언트에 도구 호출을 붙여야
  하므로 별도 ADR
- deepagents 도입: 새 의존성 + 자체 도구가 R4(도구 6개)를 깨고, 메서드 하나의 diff 판단에 맞지 않는다
- 규칙표 (bug_fix, FAIL) → create_test 행의 재검토: 오분류 시 사람 확인을 건너뛰는 경로다. 모델을
  가볍게 갈 때 위험해지므로 별도 ADR 후보로 남긴다

## 결과

- 의도 세트는 우리가 만든 변경이라 편향이 있다(결함 세트와 같은 한계). 실제 사용 중 unclear로 저장된
  항목을 세트에 추가해 보정한다
- 확신도는 보정된 확률이 아니다. 기준치는 세트로 조정하되, 코드는 이 값으로 규칙표를 우회하지 않는다
