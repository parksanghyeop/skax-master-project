# ADR-0014: 평가 벤치마크를 로컬 결함 세트로 대체 (Defects4J·EvoSuite 보류)

- 상태: 승인 (2026-09-01). phase2 스킬 M7의 "Defects4J 서브셋 + EvoSuite 비교"와
  다르게 가는 결정 — 환경 제약에 따른 대체이며, 측정 목적은 동일하게 유지한다

## 배경

phase2 스킬은 M7에서 Defects4J 서브셋(실제 버그 20~40건)과 EvoSuite 베이스라인
비교를 요구한다. 그러나 현재 개발 환경(Windows, 오프라인 원칙)에서는:
- Defects4J는 perl + 특정 JDK + 프로젝트별 대용량 체크아웃 인프라가 필요하고
  Windows 지원이 공식적으로 없다
- EvoSuite는 JDK 8/11 시절 도구로 JDK 21 대상에서 동작이 불안정하다

## 결정

1. **측정 목적(생성 테스트가 실제 버그를 잡는가)은 유지하고, 문제 세트를
   로컬 결함 세트로 대체한다**: 벤치 프로젝트(examples/evalbench)의 메서드마다
   (고친 버전, 버그 버전) 쌍을 수작업으로 만든다(evals/defects/, v1은 6건 —
   경계 off-by-one, null 누락, 빈 문자열 처리, 연산자 오류, 음수 처리 누락,
   기저 조건 오류). 고친 버전에서 테스트를 생성하고 버그 버전에서 돌려
   실패하면 검출 성공 — Defects4J의 판정 방식과 같다.
2. 지표는 스킬 그대로: 검출률, 게이트(assert 약화 0건 포함) 통과율,
   에스컬레이션율, 시도 수(비용 근사), 소요 시간. 기록은 evals/results/에
   모델·프롬프트 해시·데이터셋 버전과 묶는다.
3. **Defects4J·EvoSuite는 폐기가 아니라 보류다** — 리눅스 환경(사내 CI 등)이
   확보되면 같은 하네스에 문제 세트만 갈아 끼운다(run_eval의 케이스 구조가
   그 교체 지점이다). EvoSuite 비교의 대안으로 PIT 뮤테이션 점수를 게이트에서
   이미 실측하고 있다.

## 결과

- 케이스 수(6건)가 작아 수치의 통계적 힘은 약하다 — 추세 확인용이며,
  케이스 추가 시 DATASET_VERSION을 올려 이전 수치와 구분한다.
- 결함을 우리가 심었으므로 "우리 파이프라인이 잘 잡는 종류"로 편향될 수 있다 —
  케이스 유형을 다양화하고, 실버그 세트 확보 시 재검증한다.
