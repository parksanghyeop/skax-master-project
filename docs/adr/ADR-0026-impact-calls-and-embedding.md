# ADR-0026: 영향 범위 분석 — 호출 관계(CALLS) 엣지 도입, 임베딩 검색은 자연어 자리에만

- 상태: **승인·구현 완료** (2026-09-13). D1·D2·D3 구현. 임베딩 실호출은 게이트웨이 키가 있는 환경에서 확인해야 한다(아래 검증 계획 D3 비고)
- 관련: v4 4.1 ①(엣지 4종 중 "호출한다"는 추정+확신도) · v4 4.1 ④(임베딩 검색은 커밋 메시지·판단 메모 두 곳에만) ·
  `docs/코드그래프.md` 4절·7절(CALLS 후순위) · ADR-0011·0013(게이트웨이 임베딩 API 존재, text-embedding-3-small 1차 후보) ·
  ADR-0020 D2(보류된 `callers` 단서) · `docs/E2E/작업목록.md` B-5(판단 메모 임베딩 검색) · R2·R4·R7

## 배경

요청: "기술적 어필 요소가 부족하다. RAG를 붙이고 임베딩 벡터 유사도 검색을 넣어, 변경 의도 분석·테스트 작성 때
프로젝트 구조를 파악해 **수정된 메서드에 영향이 가는 곳까지 테스트 케이스로** 만들고 싶다."

이 요청은 두 가지가 섞여 있다. 따로 떼어 검토했다.

1. **영향 범위 분석** — 수정된 메서드를 누가 호출하나 (구조 질의)
2. **임베딩 벡터 검색** — 기술 요소로 넣고 싶은 검색 수단

### 검토 1. 영향 범위를 임베딩 유사도로 찾으면 안 되는 이유

| 이유 | 설명 |
|---|---|
| **v4 설계와 정면 충돌** | v4 4.1은 "이 메서드를 누가 호출하나"에 대해 "비슷한-문서 검색은 추측, 코드 그래프는 정답"이라 못 박고, 임베딩은 **코드 검색에 쓰지 않는다**고 정했다(4.1 ④). 설계 문서가 코드보다 우선한다(CLAUDE.md) |
| **기술적으로 오답을 낸다** | 벡터 유사도는 "닮은 코드"를 찾는다. `OrderService#findById`를 호출하는 `pay`·`cancel`·`updateAmount`의 본문은 `findById`와 닮지 않았고, 오히려 다른 클래스의 `findById`류 메서드가 상위에 온다. 영향 범위는 **의존 관계**이지 유사도가 아니다 |
| **결정성 위반(R2)** | 영향 범위가 기존 테스트 상태·조치 결정에 들어가면 안전장치 입력이 된다. 임베딩 순위는 모델·임계값에 따라 흔들리고 확신도는 보정된 확률이 아니다(ADR-0020 D3와 같은 이유) |
| **재생 비용** | 임베딩 호출도 LLM 호출이라 기록·재생(R7)이 필요하다. 코드 전체를 임베딩하면 기록이 소스 한 줄에도 깨진다 |

결론: **영향 범위 분석은 코드 그래프의 호출 관계(CALLS)로 한다.** v4 4.1 ①이 처음부터 그렇게 설계했고 "나중 단계"로 미뤄 둔 자리다.
임베딩은 버리지 않는다 — v4가 정한 자리(자연어 두 곳)에 붙인다.

### 검토 2. 지금 무엇이 있고 무엇이 비어 있나

- 그래프: 확정 엣지 3종(DECLARES·CREATES·COVERS). `callers` 쿼리는 "후순위다, inspect_target을 쓰라"는 안내 문장만 반환
  (`graph/answers.py`). 파싱 폴백(`similar.py`)도 같다
- 변경 추출(`adapters/java/changes.py`): 바뀐 메서드는 알지만 그 메서드를 부르는 곳은 모른다. ADR-0020 D2가 `callers` 단서를
  원안으로 적고 "근거 없음"으로 보류했다 — 그때의 목적은 unclear 축소였고, 지금 목적(영향 범위 → 테스트)은 다르다
- 판단 메모(`cli/memos.py`): 검색이 클래스·메서드 **이름 일치**뿐. "지금 상황과 비슷한 과거 판단"(v4 4.2)은 사실상 못 찾는다
- 게이트웨이: 임베딩 deployment 존재 확인됨(poc-findings 확인 1번, text-embedding-3-large/small, ada-002). `llm/`에 임베딩 클라이언트는 없다

## 결정

### D1. CALLS 엣지를 넣는다 — 추정이므로 확신도(confidence)를 붙인다 (v4 4.1 ①의 4번째 엣지)

`adapters/java/graph_builder.py`가 main 소스 메서드 본문에서 결정적으로(정규식, LLM 없음) 뽑는다. 테스트 트리는 제외한다 —
테스트→코드 관계는 COVERS(실측)가 담당한다.

| 호출 모양 | 확신도 | 근거 |
|---|---|---|
| 같은 클래스 안에서 `이름(` (수식 없음) | `high` | 같은 클래스의 메서드가 있으면 그것이다 (상속 오버라이드는 알려진 한계) |
| `x.이름(` 이고 `x`의 선언 타입(필드·파라미터·지역변수·`new X()`)이 프로젝트 클래스 X이며 X에 `이름`이 있다 | `high` | 타입이 소스에서 읽힌다. 예: `service.findById(id)` — `OrderController`의 필드 `OrderService service` |
| `x.이름(` 이고 타입은 못 읽었지만 프로젝트 전체에서 `이름`을 가진 클래스가 **하나뿐** | `medium` | 이름이 유일하면 그 메서드다 |
| `이름`을 가진 클래스가 여럿이고 타입도 못 읽음 | 만들지 않는다 | 추측 엣지는 잡음 — "없는 것이 틀린 것보다 낫다"(코드그래프.md 3절) |

- `GraphEdge`에 `props: dict`(확신도)를 더한다. `EDGE_CALLS = "CALLS"`. 인메모리·Neo4j 저장소는 kind 속성 방식이라 Cypher 변경 없이 담긴다
- `callers` 쿼리가 실응답한다: "OrderService#findById를 호출하는 곳(정적 추정): OrderService#pay [high], OrderService#cancel [high],
  OrderController#get [high] — 추정이므로 필요하면 inspect_target으로 확인하라". 답에 "추정"을 반드시 붙인다(v4 4.1 ①)
- 그래프 미구축(폴백)에서도 같은 추출기를 그 자리에서 돌려 답한다 — Neo4j가 필수가 되지 않는다(코드그래프.md 4절)
- 도구는 늘지 않는다(R4). `callers`는 원래 `KNOWN_QUERIES`의 한 항목이다

### D2. 영향 범위의 쓰임은 세 곳 — 규칙표에는 넣지 않는다

1. **화면**: `cta maintain`의 변경 건 출력에 "영향 범위: pay, cancel, updateAmount (정적 추정, 확신 high)" 한 줄
2. **작업 지침서(briefing)**: 호출자 목록 + 확신도 + 호출 줄 발췌를 붙이고, 작성 지침에 "호출자 경유 시나리오를 1개 이상 시험하라"를
   넣는다. 예: `findById`의 예외 타입이 바뀐 버그 수정이면 `pay(없는 id)`가 같은 예외를 내는지 확인하는 케이스
3. **파생 생성 건(옵션)**: `cta maintain --impact`(기본 꺼짐)일 때, 확신 `high`인 호출자를 **깊이 1, 상한 N개**(cta.toml `[impact] max_callers`, 기본 3)로
   ChangeAnalysis 목록에 파생 건으로 추가한다. 파생 건은 의도를 원본에서 물려받고(LLM 추가 호출 없음), 기존 테스트 상태는 그 호출자의
   COVERS로 판정하며, 규칙표는 그대로 탄다. 화면에는 "↳ 영향 범위(OrderService#findById 변경)"로 표시한다

**규칙표·기존 테스트 상태 판정에는 CALLS를 쓰지 않는다.** 이유: 커버리지는 실행 경로를 따라 기록되므로, 호출자의 테스트가 정말 대상을
실행한다면 이미 COVERS(테스트→대상) 엣지가 있다. CALLS를 넣어도 정확한 경우엔 얻는 것이 없고, 틀린 경우엔 "커버 테스트 있음/없음"을
오염시킨다(코드그래프.md 4절의 결정 그대로). 파싱 폴백 로케이터도 같은 이유로 손대지 않는다.

### D3. 임베딩 검색은 v4 4.1 ④의 자리에 붙인다 — 판단 메모(우선), 커밋 메시지(후순위)

작업목록 B-5를 실행하는 것이다. 이름 일치 검색이 못 찾는 "상황이 비슷한 과거 판단"을 찾는다.

- `llm/embeddings.py`: `EmbeddingClient` 프로토콜 + 게이트웨이 구현(`/openai/deployments/{deployment}/embeddings`, deployment 기본
  `text-embedding-3-small` — ADR-0013 3번). 생성은 `llm/config.py`의 `make_embedding_client()`만 경유(ADR-0011)
- **기록·재생(R7)**: 임베딩 호출도 기록한다 — 키는 deployment + 입력 텍스트, 값은 벡터(`RecordingEmbeddingClient`/`ReplayEmbeddingClient`). 재생은 없는 글이면 실패(실호출 폴백 없음). 구현 비고: `maintain`·`resolve`는 재생 옵션이 없는 명령이라(CI는 이 명령을 실호출로 돌리지 않는다) CLI에는 실호출 클라이언트만 연결했고, 기록·재생 클라이언트는 테스트와 향후 시연 기록용이다
- **메모에 상황 요약을 저장**: `Memo`에 `situation`(그때의 커밋 메시지 첫 줄 + 분류 analysis 요약)과 `embedding`(벡터)을 추가.
  `resolve` 시점에 한 번 임베딩한다. 검색 질의는 지금 건의 커밋 메시지 + 단서 + analysis — 전부 자연어다
- **검색은 하이브리드**: 이름 일치(현행, 결정적) 결과를 먼저, 그 다음 코사인 상위 건을 채워 최대 3건. 코사인은 순수 파이썬으로 계산한다
  — 메모는 프로젝트당 수십 건이라 벡터 DB·numpy가 필요 없다(새 의존성 0). Neo4j 벡터 색인은 그래프가 선택 사항이라 쓰지 않는다
  (v4 4.1 ④ "저장소 이원화 금지"는 별도 벡터 DB를 두지 말라는 뜻이고, 메모 파일 옆에 벡터를 두는 것은 저장소를 늘리지 않는다)
- **폴백**: 게이트웨이 임베딩 불가·미설정이면 이름 일치만(현행). 화면에 어느 쪽인지 표시
- **불변식**: 메모가 어떤 내용이어도 `decide()` 결과는 바뀌지 않는다 — B-5 ②의 테스트를 함께 넣는다

커밋 메시지 임베딩(같은 뜻의 다른 표현 찾기)은 메모 검색이 자리 잡은 뒤 같은 클라이언트로 붙인다 — 이 ADR의 범위 밖.

## 하지 않는 것

- 코드 본문·메서드 임베딩과 벡터 유사도로 영향 범위 찾기 (검토 1)
- 벡터 DB·임베딩 라이브러리 신규 의존성 (필요 없다)
- CALLS를 규칙표·로케이터 입력으로 (D2)
- 깊이 2 이상의 전이 영향(호출자의 호출자) — 상한 없이 늘어난다. 깊이 1을 측정한 뒤 판단
- 7번째 도구 — `callers`는 기존 `query_code_graph` 쿼리
- 리플렉션·DI·상속을 통한 호출 추적 — 정규식 한계로 기록하고, 확신도 `high`의 정의에서 뺀다

## 검증 계획

| 단계 | 검증 |
|---|---|
| D1 추출기 | 단위 테스트(인메모리): 같은 클래스 호출 high · 필드 타입 호출 high · 이름 유일 medium · 이름 중복은 엣지 없음. 데모 프로젝트 실측: `findById` 호출자 = `updateAmount`·`pay`·`cancel`(같은 클래스) + `OrderController#get`(필드 타입) |

| D2 | `cta maintain --diff HEAD~1`로 SC-002(버그 수정) 재현 → 화면에 영향 범위 줄, 지침서에 호출자 절. `--impact`로 파생 건이 규칙표를 그대로 타는지 테스트. 결함 세트(`cta eval`) 검출률 전/후 비교 — 떨어지면 되돌린다 |

| 공통 | `ruff check . && pytest -q` 초록(현재 277건), `tests/test_layering.py`(core에 언어 문자열 금지) |

## 발표에서의 어필 포인트 (참고)

"코드 RAG는 벡터가 아니라 그래프다"가 이 프로젝트의 차별점이다. 확정 관계(선언·생성·실측 커버리지)에 추정 관계(호출, 확신도)를 더한
**그래프 검색**으로 영향 범위를 잡고, 자연어(판단 메모)에만 **임베딩 검색**을 쓰는 하이브리드 구성이다 — "왜 코드에는 임베딩을 안 썼나"에
답할 수 있어야 벡터 RAG를 붙인 것보다 강한 이야기가 된다.
