# 스킬 — 테스트 작성 워크플로우에 지식을 붙이는 방법

`docs/의도분류.md`, `docs/코드그래프.md`와 같은 성격의 설명 문서다. 스킬이 무엇이고, 왜 넣었고, 어디에 어떻게 붙어 있는지를
코드 위치와 함께 적는다. 설계 결정 원문은 [ADR-0017](adr/ADR-0017-writer-skills.md)이다.

## 1. 한 줄 요약

> 스킬은 "이런 상황에서 테스트를 이렇게 써라"를 적은 마크다운 파일이고, 어떤 스킬을 프롬프트에 넣을지는 LLM이 아니라
> 규칙표가 정한다.

![스킬 선택 흐름](제출자료/images/skills-flow.png)

## 2. 왜 넣었나

원래 테스트 작성 프롬프트는 파일 두 개였다. 시스템 프롬프트(`llm/prompts/system.md`, 절대 규칙 4개)와 사용자 프롬프트
(`llm/prompts/write_test.md`, 빈칸 5개). 사용자 프롬프트의 빈칸 중 `[프로젝트 관례] $style` 자리에는 늘 같은 문장 한 줄만 들어갔다.

```
프로젝트의 기존 테스트 스타일(이름 규칙, import 방식, mock 사용법)을 따른다.
```

그래서 Mockito를 어떻게 써야 하는지, 재발 방지 테스트는 무엇을 확인해야 하는지 같은 지식은 전부 모델의 사전 지식에 맡겨져
있었다. 실측에서 그 비용이 보였다. SC-002에서 1차 생성이 Mockito 오류로 실패해 2차에 통과했고, SC-001(메서드 4개)도 1차가
실패했다. 해결책으로 "프롬프트에 지식을 더 많이 박아 넣기"는 두 가지가 나쁘다. 상황에 안 맞는 지시가 섞이고(예: mock을
안 쓰는 클래스에 Mockito 지시), 토큰이 매번 늘어난다.

사람 멘토의 피드백도 있었다. 기술적으로 어필할 지점이 부족하니 워크플로우에 스킬을 붙여 보라는 것이었다.

## 3. 스킬이 무엇인가 — 파일 하나

스킬 하나는 폴더 하나다. `cta/adapters/java/skills/<이름>/SKILL.md`.

```
cta/adapters/java/skills/
├── __init__.py
├── select.py                  # 읽기·선택·렌더링
├── junit5-mockito/SKILL.md
└── regression-test/SKILL.md
```

파일은 frontmatter(이름·설명·언제 쓰나) + 본문(300~1,200자)이다. `junit5-mockito`의 실제 내용:

```markdown
---
name: junit5-mockito
description: Mockito로 의존 객체를 대체하는 JUnit 5 단위 테스트 관례 — 대상이 저장소·인터페이스에 의존할 때
when: 재료 수집이 "mock 사용"으로 판정한 의존 객체가 하나 이상 있을 때
---
- 클래스에 `@ExtendWith(MockitoExtension.class)`. 의존 객체는 `@Mock`, 대상은 `@InjectMocks`. …
- 스텁은 `when(repo.findById(1L)).thenReturn(Optional.of(order))`. 반환이 `Optional`이면
  `Optional.empty()`로 "없음" 경로 테스트도 만든다.
- MockitoExtension은 strict stubs다 — 테스트가 쓰지 않는 stub은 `UnnecessaryStubbingException`으로 실패한다. …
- 흔한 컴파일·실행 오류: matcher(`any()`, `eq()`)와 실제 값을 한 호출에 섞기 — 하나를 matcher로 쓰면 전부
  matcher(`eq(값)`)로. …
- 값 객체(builder·record·표준 타입)는 mock하지 않고 직접 만든다 — 재료의 "직접 생성" 목록을 따른다.
```

`regression-test`는 버그 수정 커밋에 붙는 재발 방지 테스트의 작성법이다. 핵심은 "수정 전 코드에서는 실패하고 수정 후에는
통과해야 한다"는 것과, 변경된 조건(예: `>` → `>=`)에서 경계값 세 케이스(같음·바로 아래·바로 위)를 뽑으라는 것,
`assertNotNull`처럼 무엇이든 통과하는 확인을 금지하는 것이다.

본문에 들어가는 것은 **"어떻게 잘 쓰나"**뿐이다. "스킵해도 된다", "기존 assert를 고쳐도 된다" 같은 **"무엇을 해도 되나"**는
게이트와 규칙표가 정하고, 스킬은 그것을 바꿀 수 없다. 이건 문장이 아니라 테스트로 고정돼 있다 — 스킬 본문에 `@Disabled`,
`@Ignore`, `assumeTrue`, `assumeFalse`가 들어 있으면 `tests/test_skills.py`가 실패한다.

왜 `core/`가 아니라 `adapters/java/` 아래인가. 스킬 내용이 Java·JUnit·Mockito 이야기라서다. `core/`에는 언어 이름이 들어갈
수 없다(R1, `tests/test_layering.py`가 검사). 새 언어를 붙이면 그 어댑터 아래에 그 언어의 스킬 폴더가 생긴다.

## 4. 어떤 스킬을 고르나 — 규칙표

선택은 `select.py`의 표 하나가 한다.

```python
@dataclass(frozen=True)
class SkillSignals:
    uses_mock: bool = False              # 재료 수집이 "mock 사용"으로 판정한 의존 객체가 있다
    regression: bool = False             # 버그 수정 → 테스트 추가 실행(regression 게이트가 붙는다)
    resume_with_authorized: bool = False # resolve 재개 — 사람이 허용한 실패 테스트가 있다

_RULES: dict[str, Callable[[SkillSignals], bool]] = {
    SKILL_JUNIT5_MOCKITO: lambda s: s.uses_mock,
    SKILL_REGRESSION_TEST: lambda s: s.regression,
}
```

신호 세 개는 **전부 이미 결정돼 있는 값**에서 나온다. 새 판단은 없다.

| 신호 | 어디서 오나 | 이미 무엇을 위해 계산되던 값인가 |
|---|---|---|
| `uses_mock` | `materials.py`가 파라미터·의존 객체마다 매긴 "직접 생성 / mock 사용" 중 mock이 하나라도 있는가 | 화면 `[2/4] 파라미터 객체 만드는 법 확인`과 프롬프트 재료 |
| `regression` | `run_generation`에 `regression_sources`(수정 전 소스)가 넘어왔는가 | 재발 방지 게이트(수정 전 코드에서 실패해야 통과)를 붙일지 정하던 값 |
| `resume_with_authorized` | `authorized_tests`(사람이 고쳐도 된다고 지정한 테스트)가 비어 있지 않은가 | assert 게이트의 허용 목록 |

세 번째 신호에는 아직 걸리는 스킬이 없다. 후보(`refactor-preserve`)는 전/후 수치를 본 뒤 넣는다.

왜 LLM에게 "어떤 스킬이 필요한지 골라라"고 하지 않았나. 두 가지 이유다. 첫째, 같은 입력에 같은 프롬프트가 나와야 저장된
LLM 호출 기록으로 재생(CI·데모)이 된다. 모델이 고르면 그 선택이 매번 달라질 수 있다. 둘째, 에이전트 도구는 6개로 고정돼
있다(R4). "스킬 검색" 도구를 더하면 7개가 되고, 모델이 스킬을 읽는 호출만큼 토큰과 시간이 든다.

## 5. 어디에 붙나 — 프롬프트의 `$style` 자리

`cli/generate.py`의 `run_generation`이 재료 수집 직후에 스킬을 고른다.

```python
skills = select_skills(signals_from(materials, regression_sources, authorized_tests))
skill_names = [s.name for s in skills]
print(f"{INDENT}      적용 스킬: {', '.join(skill_names) if skill_names else '없음'}")
...
generator=PromptedGenerator(
    client, model, "Java", "JUnit 5",
    "\n\n".join([BASE_STYLE_NOTE, render_skills(skills)]) if skills else BASE_STYLE_NOTE,
),
```

`PromptedGenerator`의 마지막 인자가 `write_test.md`의 `$style` 빈칸에 들어간다. 스킬이 하나도 안 걸리면 예전과 똑같은
고정 문장 한 줄이고, 걸리면 그 뒤에 이렇게 붙는다.

```
프로젝트의 기존 테스트 스타일(이름 규칙, import 방식, mock 사용법)을 따른다.

[스킬: junit5-mockito — Mockito로 의존 객체를 대체하는 JUnit 5 단위 테스트 관례 — …]
- 클래스에 `@ExtendWith(MockitoExtension.class)`. …

[스킬: regression-test — 버그 수정 커밋의 재발 방지 테스트 — …]
- 잡아야 하는 것은 "그 버그"다. …
```

바뀐 것은 이 문자열 하나다. `core/`(작성 루프, 규칙표, 게이트)는 한 줄도 바뀌지 않았고, 시스템 프롬프트의 절대 규칙 4개도
그대로다. LangGraph 그래프의 노드·간선도 그대로다 — 스킬은 노드가 아니라 노드에 들어가는 재료다.

## 6. 예시 — SC-002(버그 수정 커밋)에서 무슨 일이 일어나나

`cta maintain --diff HEAD~1`로 `OrderService.applyDiscount`의 `>` → `>=` 수정 커밋을 처리하는 경우.

1. 의도 분류가 "버그 수정 98%"를 내고 규칙표가 `create_test`를 고른다. 버그 수정이므로 `maintain_cmd`가 수정 전 소스를
   `regression_sources`로 넘긴다 → 신호 `regression = True`
2. 재료 수집이 파라미터를 본다. `Order → 직접 생성 (builder)`, `Customer → 직접 생성`, `OrderRepository → mock 사용
   (DB에 접근하는 인터페이스)` → 신호 `uses_mock = True`
3. 규칙표에서 두 행이 다 걸린다. 화면에 한 줄이 찍힌다.

   ```
   [2/4] 파라미터 객체 만드는 법 확인
         Order           → 직접 생성 (Order.builder() 사용)
         OrderRepository → mock 사용 (DB에 접근하는 인터페이스)
         적용 스킬: junit5-mockito, regression-test
   ```
4. 프롬프트의 관례 자리에 두 스킬 본문이 붙어 LLM에 간다. 결과 dict에도 `"skills": ["junit5-mockito", "regression-test"]`가 남는다.

같은 실행이라도 `cta generate --class PricingCalculator`(파라미터가 `List`, `BigDecimal`뿐, 버그 수정 아님)이면 신호가
전부 False라 "적용 스킬: 없음"이고 프롬프트는 예전과 똑같다.

## 7. 재생·기록과의 관계

프롬프트가 바뀌면 저장된 LLM 호출 기록과 요청이 달라져 재생이 깨질 수 있다. 확인한 것:

- `cta demo`와 자동 테스트가 쓰는 골든 재생(`cta/evals/golden_case.py`)은 `PromptedGenerator`를 **자체 `STYLE_NOTES`로**
  직접 만든다. `run_generation`을 거치지 않으므로 스킬의 영향을 받지 않는다. 그래서 기존 기록이 그대로 재생된다
- 실호출 시나리오(SC-001~003)의 기록을 다시 만들 때는 스킬이 붙은 프롬프트로 녹음된다(`scripts/record_golden.py --live`).
  Docker·게이트웨이가 있는 환경에서 할 일이다

## 8. 테스트 — 무엇이 고정돼 있나

`tests/test_skills.py` 11건.

| 묶음 | 확인하는 것 |
|---|---|
| 읽기 | 리포의 스킬 2개가 frontmatter(이름·설명·when)와 본문을 갖고 있고 본문이 200~1,200자다. frontmatter가 없으면 폴더 이름과 전체 본문으로 읽는다. 본문의 수평선(`---`)은 헤더 닫기로 오해되지 않는다 |
| 선택 | mock 판정이 있으면 `junit5-mockito`, 버그 수정 실행이면 `regression-test`, 둘 다면 규칙표 순서대로 둘 다, 신호가 없으면 빈 목록(렌더도 빈 문자열). resolve 재개 신호는 기록되지만 아직 스킬이 없다 |
| 렌더링 | `[스킬: 이름 — 설명]` 머리 + 본문 |
| 불변식 | 스킬 본문에 `@Disabled`·`@Ignore`·`assume*` 없음. 스킬 폴더가 `core/` 밖(`adapters/`)에 있음 |

패키징도 확인했다. `pyproject.toml`의 package-data에 `skills/*/SKILL.md`가 들어 있어 `pip install`로 설치해도 스킬 파일이
따라간다(wheel 안에 두 파일이 있는 것을 확인).

## 9. 스킬 하나 추가하는 법

1. `cta/adapters/java/skills/<이름>/SKILL.md`를 만든다. frontmatter에 `name`(폴더 이름과 같게)·`description`·`when`, 본문은
   300~1,200자. "어떻게 잘 쓰나"만 쓰고, 게이트가 막는 행동을 권하지 않는다
2. `select.py`의 `_RULES`에 한 행을 더한다. 조건은 `SkillSignals`의 기존 신호로 쓴다. 새 신호가 필요하면 `SkillSignals`에
   필드를 더하고 `signals_from`에서 **이미 계산돼 있는 값**으로 채운다 — 스킬을 위해 새 판단(LLM 호출 포함)을 만들지 않는다
3. `tests/test_skills.py`의 읽기 테스트(`set(skills) == {...}`)와 선택 테스트에 새 스킬을 넣는다
4. 실호출 기록을 다시 만든다(그 스킬이 걸리는 시나리오가 기록에 있다면)
5. 전/후 수치 없이 "좋아졌다"고 적지 않는다. 같은 시나리오를 스킬 없음/있음으로 각 3회 돌려 1차 통과율·시도 수·토큰·
   게이트 탈락 수를 비교한다(2단계 규칙 "수치 없는 개선 금지")

후보로 적어 둔 것: `boundary-values`(확인 항목에 경계값이 있을 때 — 2단계 베이스라인의 미검출과 관련), `spring-slice-test`
(`@Service`·`@Repository` 클래스), `refactor-preserve`(resolve 재개 시).

## 10. 한계와 아직 못 한 것

- **효과를 숫자로 보이지 못했다.** 스킬 2개를 붙였다는 것까지가 이 PC에서 확인한 범위다. 1차 통과율이 실제로 오르는지는
  Docker와 게이트웨이 키가 있는 환경에서 전/후 비교를 돌려야 안다. 측정 방법은 ADR-0017에 있다
- **신호가 거칠다.** `uses_mock`은 "mock을 쓰는 의존 객체가 하나라도 있나"다. Spring 슬라이스 테스트가 맞는 상황과 순수
  Mockito 단위 테스트가 맞는 상황을 구분하지 않는다
- **스킬 본문은 사람이 쓴 Java 지식이다.** 프레임워크 버전이 바뀌면(예: Mockito strict stubs 기본값) 본문도 손봐야 한다.
  코드가 아니라 마크다운이라 고치기는 쉽다
