## 1. 이 프로젝트가 뭔가요

Java 코드를 고치면 JUnit 테스트도 같이 손봐야 하는데, 이걸 대신 해 주는 CLI 툴입니다. `cta`라는 명령어로 씁니다.

핵심 아이디어는 이겁니다.

- LLM은 딱 두 군데서만 씁니다. **"이 diff가 버그 수정인지 리팩터링인지 판단"** 하는 것과 **"테스트 코드 작성"** 입니다.
- 나머지는 전부 일반 Python 코드입니다. 규칙 테이블, 품질 게이트, 재시도 횟수 제한, 사람한테 물어보기 같은 것들이요.
- LLM이 만든 코드는 바로 소스에 안 씁니다. `.cta/proposals/`에 제안(proposal)으로 저장하고, 사람이 `cta diff`로 보고 `cta apply`를 쳐야 `src/test`에 반영됩니다.

숫자로 보면 이렇습니다.

| 항목 | 수치 |
|---|---|
| 제품 코드 | `cta/` 아래 Python 파일 90개, 9,813줄 |
| 단위 테스트 | 38개 파일, **314건 통과** (`pytest -q`, Docker·Neo4j·API 키 없이 돕니다) |
| ADR(설계 결정 기록) | 18건 (ADR-0010 ~ 0026) |
| 의도 분류 정확도 | **10/10 (100%)**, 잘못된 unclear 0건 (gpt-5 실호출) |
| 결함 세트 검출률 | 12건 중 **10건 검출 (83.3%)**, 전부 게이트 통과, 평균 시도 1.0회 |
| 데모에서 만든 테스트 품질 | 라인 커버리지 100%, 브랜치 커버리지 100%, 뮤테이션 킬 100% |
| 실제 API 키로 돌려 본 결과 | 모든 명령 끝까지 실행됨, 그 과정에서 버그 7개 찾아서 고침 |

## 2. 전체 구조

![Agent Architecture](1-agent-architecture.png)

왼쪽에서 오른쪽으로 읽으면 됩니다. 사용자가 터미널에서 `cta` 명령을 치면 → 에이전트가 돌고 → LLM 게이트웨이(사내 Azure OpenAI 호환)를 호출하고 → 결과가 게이트를 거쳐 제안으로 저장됩니다.

### 2.1 에이전트 안쪽

- **메인 에이전트 + 서브에이전트 3개** (탐색 / 작성 / 진단). Deep Agents 프레임워크 위에 올렸고, 옵션으로 옛날 LangGraph 서브그래프 방식(`--engine legacy`, 기본값)도 남겨 뒀습니다.
- **툴 6개**: `inspect_target`, `query_code_graph`, `write_test`, `run_tests`, `check_quality`, `report_finding`. 7번째 툴은 안 만드는 게 규칙입니다(R4).
- **안전장치 4개**: 반복 8회 제한, 4회마다 사람에게 질문, 규칙 테이블, 게이트 6개. 이건 전부 LLM 없이 돕니다.

### 2.2 LLM 게이트웨이

- `llm/` 패키지만 게이트웨이를 호출합니다. 다른 곳에서 `urllib`이나 LangChain 클라이언트를 직접 만들면 안 됩니다(R7).
- 모든 호출은 record & replay가 됩니다. 요청을 JSON으로 저장해 두고 CI에서는 그 파일만 읽어서 답합니다. 파일이 없거나 요청이 달라지면 실호출로 넘어가지 않고 그냥 실패합니다.
- 임베딩 API(`text-embedding-3-small`)도 같은 방식으로 붙였습니다.

### 2.3 패키지 구조

![Project Structure](6-project-structure.png)

의존 방향은 `cli → core ← adapters/java · graph · llm · sandbox`입니다. `core`에는 `java`, `maven`, `junit` 같은 문자열 자체가 있으면 안 되고, `tests/test_layering.py`가 이걸 grep해서 검사합니다. 처음엔 좀 빡빡하다고 생각했는데, 덕분에 `core`가 Java에 종속되지 않아서 Fake 어댑터로 유닛 테스트 짜기가 편했습니다.

패키지별로 하는 일:

- `core/`: `Protocol`로 정의한 포트 9개, 규칙 테이블(`decide.py`), 툴 6개, 작성 루프(`writer_graph.py`), 게이트 계약
- `adapters/java/`: 정규식 파서, git diff 파싱, JaCoCo/PIT 실행, 게이트 구현, 테스트 파일 쓰기·머지
- `graph/`: 코드 그래프 모델, 인메모리 스토어, Neo4j 스토어, 쿼리 응답
- `llm/`: 게이트웨이 HTTP 클라이언트, 프롬프트, 임베딩, record/replay, 토큰 계산, API 키 마스킹
- `sandbox/`: 로컬 Maven 실행 또는 Docker 컨테이너 실행
- `cli/`: `argparse` 서브커맨드 조립. 여기엔 판단 로직이 없습니다

## 3. 명령어별 흐름

![CLI Flows](5-cli-flows-infographic.png)

| 상황 | 명령 | exit code |
|---|---|---|
| 테스트 없는 클래스에 테스트 만들기 | `cta generate --class com.example.OrderService [--max-methods N] [--fast]` | 0 / 2 / 3 |
| 커밋한 뒤 테스트 맞추기 | `cta maintain --diff HEAD~1 [--intent bug_fix] [--message "..."] [--impact]` | 0 / 2 / 3 |
| 멈춘 항목에 답하기 | `cta resolve <id> --intended \| --test-issue \| --proceed \| --as 의도 \| --skip` | 0 / 2 / 3 |
| 검토·반영 | `cta diff` → `cta apply [이름 \| --all]` / `cta discard` | 0 |
| 그래프·평가·시연 | `cta graph [--coverage]` · `cta eval [--intents]` · `cta demo` | 0 / 1 |

exit code 3은 "사람 확인 필요"지 실패가 아닙니다. CI에서는 이 값으로 분기합니다. 2는 게이트 재시도(3회)를 다 써서 품질 미달, 1은 진짜 에러입니다.

### 3.1 generate

재료 수집(테스트 없는 public 메서드 고르기, if/경계값/throw/null 항목 세기, 파라미터를 직접 생성할지 mock할지 판정) → LLM이 테스트 작성 → `mvn test -Dtest=클래스`로 그 테스트만 실행 → 실패하면 실패 로그와 직전 코드를 들고 재시도(최대 8회) → 통과하면 게이트 6개 → 제안 저장.

### 3.2 maintain

`git diff --unified=0`에서 바뀐 메서드를 뽑고, 한 건마다 LLM이 의도를 분류합니다(bug_fix / refactor / new_feature / trivial / unclear + 확신도 + 근거). 그다음 그 메서드를 검증하는 기존 테스트를 찾아 돌리고, (의도 × 테스트 상태) 규칙 테이블로 조치를 정합니다.

- bug_fix, new_feature → 테스트 추가. bug_fix면 **수정 전 코드에 새 테스트를 끼워 돌려서 실패하는지**까지 확인합니다(회귀 게이트).
- refactor + 테스트 통과 → 할 일 없음.
- refactor + 테스트 실패 → 기대값 안 고치고 저장 후 멈춤(exit 3). 동작이 실제로 바뀐 거니까 사람이 봐야 합니다(R3).
- unclear → 사람에게 질문. `--intent`로 작성자가 의도를 직접 주면 그 값으로 확정합니다.

### 3.3 resolve

`.cta/escalations/<id>.json`에서 멈춘 지점을 읽어서 같은 작성 루프로 이어 갑니다. `--intended`면 "일부러 동작 바꾼 거 맞다"는 뜻이라 실패한 테스트 메서드의 기대값을 고치는데, **그 메서드만** assert 변경이 허용되고 나머지는 게이트가 막습니다. 결정은 `.cta/memos/`에 판단 메모로 저장됩니다.

## 4. 코드 그래프

![Graph DB Architecture](4-graphdb-architecture.png)

Neo4j에 클래스·메서드 노드와 관계 4종을 넣습니다.

| 엣지 | 뜻 | 어떻게 만드나 | 확정? |
|---|---|---|---|
| DECLARES | 클래스 → 메서드 | 정규식 파싱 | 확정 |
| CREATES | 메서드 → `new`로 만드는 클래스 | 정규식 파싱 | 확정 |
| COVERS | 테스트 클래스 → 실제로 실행된 메서드 | JaCoCo 리포트(jacoco.xml) 실측 | 확정 |
| CALLS | 메서드 → 호출하는 메서드 | 정규식 + 타입 추론, `confidence` 속성(high/medium) | **추정** |

CALLS는 이번에 추가한 겁니다. Java에서 상속·DI·리플렉션 때문에 static analysis만으로 호출 관계를 100% 못 잡아서, 확신도를 붙이고 **규칙 테이블 입력으로는 안 씁니다**. 화면에 "영향 범위" 한 줄 보여 주고, 작성 지침서에 호출자 목록을 넣고, `--impact` 옵션이면 확신 high인 호출자에도 테스트를 만듭니다.

Neo4j 관련 구현 메모:

- 라벨은 `CodeNode` 하나, 관계 타입은 `REL` 하나로 두고 `kind` 프로퍼티로 구분합니다. Neo4j는 라벨을 파라미터로 못 받아서 종류별 라벨을 쓰면 Cypher 문자열을 조립해야 하는데, 그건 인젝션 위험이 있고 쿼리 캐시도 안 탑니다.
- `project` 프로퍼티로 여러 프로젝트가 한 DB에 같이 있을 수 있습니다.
- 쿼리는 미리 정해진 4종(`verifying_tests`, `how_to_create`, `similar_tests`, `callers`)만 됩니다. LLM이 Cypher를 직접 쓰는 건 막았습니다.
- Neo4j가 없으면 프로젝트를 그 자리에서 파싱해서 인메모리 스토어로 똑같이 답합니다. 그래프 DB는 옵션입니다.

## 5. 이번 단계(9/12~13)에서 한 일

### 5.1 영향 범위 + 판단 메모 임베딩 검색 (ADR-0026)

처음엔 "RAG 붙이고 임베딩 벡터 유사도로 수정된 메서드에 영향 가는 곳을 찾자"는 아이디어로 시작했습니다. 검토해 보니 문제가 있었습니다.

- v4 설계 문서가 이미 "코드 검색엔 임베딩 안 쓴다, 코드 그래프가 정답을 준다"고 못 박아 놨습니다.
- 기술적으로도 코사인 유사도는 "비슷하게 생긴 코드"를 찾는 거지 "이 메서드를 호출하는 코드"를 찾는 게 아닙니다. `findById`를 호출하는 `pay()`는 `findById`랑 하나도 안 닮았습니다.

그래서 이렇게 갈랐습니다.

| 결정 | 구현 | 검증 |
|---|---|---|
| D1. CALLS 엣지 (confidence 포함) | `adapters/java/calls.py`에 추출기. 같은 클래스 안 호출과 필드/파라미터 타입이 프로젝트 클래스인 호출은 high, 타입은 모르지만 메서드 이름이 프로젝트에서 유일하면 medium, 나머진 엣지 안 만듦 | 데모 프로젝트에서 `OrderService#findById` 호출자 4곳(컨트롤러 1 + 같은 클래스 3) 전부 high로 잡힘 |
| D2. 영향 범위 쓰는 곳 | `cta maintain` 출력에 "영향 범위" 줄, 지침서에 호출자·호출 줄 발췌, `--impact`로 파생 생성(깊이 1, `cta.toml [impact] max_callers` 기본 3). `decide()`의 kind·reason은 callers 유무와 무관(테스트로 고정) | `--impact` 실호출: 원본 1건 + 파생 3건 전부 게이트 통과, `OrderControllerTest.java` 신규 생성 |
| D3. 판단 메모 임베딩 | `llm/embeddings.py`(게이트웨이 `/embeddings`, record/replay, 순수 Python 코사인 — numpy 안 씀). 메모에 `situation`(커밋 메시지 + 대상 + 분석)과 `embedding`을 같이 저장. 검색은 이름 일치 먼저, 빈 자리를 코사인 ≥ 0.35 순으로 채움 | 실호출: "chore: flaky 테스트 대응"으로 검색했을 때 다른 클래스의 "fix: 간헐적 실패 수정" 메모가 잡힘. API 키 없으면 이름 일치만 동작 |

### 5.2 실제로 돌려 보고 잡은 버그 7개

API 키 받아서 데모 프로젝트로 전 명령을 돌렸습니다. 유닛 테스트만으로는 못 잡던 게 꽤 나왔습니다.

| # | 증상 | 원인 | 고친 것 |
|---|---|---|---|
| 1 | Windows에서 `cta --help`만 쳐도 `UnicodeEncodeError` | cp949 콘솔에 `—`, `①` 출력 | `main()` 진입에서 `sys.stdout.reconfigure(encoding="utf-8", errors="replace")` |
| 2 | 커버리지 게이트가 3회 재생성 내내 같은 줄(88, 89)로 탈락 | 탈락 사유에 줄 번호만 있어서 LLM이 어느 경로가 빠졌는지 모름 | 사유에 소스 원문 첨부 (`88 \`repository.deleteById(id);\``) → 다시 돌리니 1회에 통과 |
| 3 | 붙여 넣은 테스트 메서드가 8칸 들여쓰기 | LLM 출력 첫 줄(`@Test`)만 들여쓰기가 없고 나머지는 4칸인데, 첫 줄만 보고 4칸 더 얹음 | 공통 들여쓰기 벗기고 4칸으로 통일 |
| 4 | `--impact`로 같은 테스트 클래스에 3번 생성했더니 앞 2번 테스트가 사라짐 | 제안 이름이 `OrderServiceTest`로 같아서 뒤 제안이 덮어씀 | 같은 클래스의 대기 제안이 있으면 그 파일을 "기존 파일"로 삼아 이어서 생성 |
| 5 | maintain 마지막 "소요 토큰"이 너무 작음 | 의도 분류 클라이언트 토큰만 세고 생성 클라이언트는 빠짐 | 둘 합산 + 내역 표시 |
| 6 | `resolve --intended`가 8회 전부 실패 | append 모드 머지가 고친 메서드를 파일 끝에 덧붙여서 `method already defined` 컴파일 에러, 안 붙이면 기존 그대로라 assert 실패 — 이걸 번갈아 반복 | 같은 이름 메서드는 어노테이션까지 제자리에서 교체 → 2회차에 통과 |
| 7 | resolve가 실패해도 escalation 항목이 삭제됨 | 결과 상관없이 `discard_escalation()` 호출 | 제안이 안 나오면 항목 유지하고 `--hint` 재시도 안내 |

6번이 제일 아팠습니다. `--intended`는 SC-003 시나리오의 핵심인데 실제로는 한 번도 통과한 적이 없었던 겁니다. 유닛 테스트에서는 머지 함수에 "새 메서드 추가" 케이스만 있었고 "기존 메서드 수정" 케이스가 없었습니다.

## 6. 검증

### 6.1 자동 테스트

```bash
ruff check . && ruff format --check .   # 통과
pytest -q                               # 314 passed, 4 deselected (docker·neo4j 마커)
```

Fake 어댑터와 저장된 LLM 호출 기록으로 돌아서 외부 의존이 없습니다. 레이어 규칙 검사, "메모나 호출자가 규칙 테이블 결과를 못 바꾼다"는 불변식 테스트, 게이트 불변식 테스트가 들어 있습니다.

### 6.2 실호출 시나리오 (gpt-5, 로컬 Maven)

| 시나리오 | 결과 |
|---|---|

## 7. 운영·보안

- 게이트웨이 URL과 API 키는 `.env`(gitignore) 또는 환경변수로만 받습니다. 커밋되는 건 `.env.example`(키 이름만)뿐입니다. 에러 메시지에 키가 섞이면 `masking.py`가 `****`로 바꿉니다.
- 생성물은 `cta apply` 전까지 `src/test`에 안 닿습니다.
- 기본 실행은 이 PC의 Maven·JDK라 샌드박스가 없습니다. 생성된 테스트가 내 권한으로 돕니다. 남의 코드나 CI에서는 `--runner docker`(네트워크 끊은 컨테이너, `~/.m2` 읽기 전용 마운트)를 써야 합니다.
- CI는 replay 모드입니다. 기록 파일이 없거나 프롬프트가 바뀌면 그냥 실패하고, 실호출로 폴백하지 않습니다.
- `cta.toml [budget] max_tokens_per_run`을 넘으면 실행을 멈춥니다.

## 8. 한계와 다음에 할 것

**솔직한 한계**

- Maven 단일 모듈 + JUnit 5만 됩니다. Gradle, 멀티모듈은 안 됩니다.
- Java 파서가 정규식이라 제네릭이 복잡하거나 중첩 클래스가 많으면 빗나갈 수 있습니다. 오버로드 메서드는 그래프 key가 겹칩니다.
- CALLS는 static analysis라 상속·DI·리플렉션 호출은 못 잡습니다. 그래서 규칙 테이블에는 안 넣었습니다.
- 임베딩 유사도 기준치 0.35는 몇 건 실측해서 정한 값이라 근거가 약합니다. 메모가 쌓이면 다시 잡아야 합니다.
- 제 PC에 Docker와 Neo4j가 없어서 `--runner docker`와 `cta graph`(Neo4j 적재)는 이번에 실행 못 했습니다. 코드는 마커 붙은 통합 테스트로만 확인했습니다.
- LLM이 준 확신도(%)는 화면에만 보여 주고 코드는 이 값으로 분기하지 않습니다. 보정된 확률이 아니기 때문입니다.

**다음에 할 것**

1. Docker·Neo4j 있는 환경에서 `--runner docker`, `cta graph --coverage` 실측.
2. 결함 세트에 실사용 중 놓친 케이스 추가해서 편향 줄이기.
3. `--impact` 켰을 때와 껐을 때 검출률 비교해서 호출자 경유 테스트가 실제로 도움이 되는지 수치화.
4. tree-sitter로 파서 교체 검토, 멀티모듈 Maven 지원.
