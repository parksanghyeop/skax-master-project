# 시연 영상 시나리오 (5분)

| 항목 | 내용 |
|---|---|
| 목표 | 「cta」가 코드 변경에 맞춰 테스트를 만들고, 위험한 경우엔 사람에게 넘기며, 호출자까지 시험 범위에 넣는 것을 5분 안에 보여 준다 |
| 형식 | 터미널 화면 녹화 + 나레이션. 4개 장면 + 인트로·마무리 |
| 대상 프로젝트 | 「examples/demo」 (Spring Boot 주문 서비스, JUnit 5 + Mockito) |
| 총 길이 | 5:00 (장면별 시간은 아래 표) |

## 0. 녹화 전 준비 (영상에 안 나옴)

| 순서 | 할 일 | 명령 / 확인 |
|---|---|---|
| 1 | 게이트웨이 설정 | 「.env」에 CTA_GATEWAY_URL, CTA_GATEWAY_API_KEY, CTA_LLM_MODEL=gpt-5 |
| 2 | Maven·JDK PATH | 「mvn -v」, 「java -version」 (JDK 17+) |
| 3 | 데모 브랜치 | 「git checkout -b demo-recording」 — 영상 끝나면 버린다 |
| 4 | 데모 프로젝트 초기화 | 「cd examples/demo」, 「rm -rf .cta」, 「git checkout -- .」 |
| 5 | 예열 | 「mvn -q test -Dtest=OrderServiceTest」 1회 (의존성 캐시, 첫 실행 지연 제거) |
| 6 | 터미널 | 글꼴 16pt 이상, 폭 120칸, 「PYTHONUTF8=1」 설정, 진행 줄이 보이도록 「--quiet」는 쓰지 않는다 |
| 7 | 장면 2·3의 코드 변경 스니펫을 클립보드나 별도 파일에 준비 | 아래 장면 설명의 diff 그대로 |
| 8 | 시간 초과 대비 | LLM·Maven 대기 구간은 편집에서 잘라낸다(x4 배속 또는 컷). 게이트웨이 장애 시 「cta demo」(저장된 호출 기록 재생)로 대체 |

실측 소요: generate 35초~2분, maintain 1분, maintain --impact 4~5분, resolve 1~2분. 실시간으로는 5분에 안 들어가므로 **녹화는 실제로 돌리고 편집에서 대기 구간을 압축**한다.

## 2. 장면별 대본

### 인트로 (0:00–0:30)

화면: 「examples/demo/src/main/java/com/example/demo/order/OrderService.java」를 연다. 「delete」 메서드에 테스트가 없음을 보여 준다.

나레이션:
> Java 코드를 고치면 JUnit 테스트도 같이 고쳐야 합니다. 이걸 LLM에 통째로 맡기면 두 가지 사고가 납니다. 기존 테스트의 기대값을 몰래 고쳐 통과시키거나, 리팩터링으로 동작이 바뀐 걸 덮어 버립니다. Code Test Agent, cta는 LLM을 판단과 작성 두 곳에만 쓰고, 나머지 판정은 전부 일반 코드가 합니다. 지금부터 네 장면으로 보여 드리겠습니다.

### 장면 1 — 테스트 생성 (0:30–1:30)

명령:
```
cta generate --class com.example.demo.order.OrderService --max-methods 1
```

화면에서 짚을 것 (출력 순서대로):
1. 「[1/4] 재료 수집」 — 테스트 없는 메서드 「delete」 선정, 확인 항목 2개(분기 1, 예외 1)
2. 「[2/4] 파라미터 객체 만드는 법 확인」 — OrderRepository → mock 사용, 적용 스킬 junit5-mockito
3. 「[3/4] 테스트 작성」 — LLM 호출 → 샌드박스 실행 → 통과 → 게이트[assert]·[skip]·[scope]·[coverage]·[mutation] 통과 (대기 구간은 편집 컷)
4. 「[4/4] 품질 확인」 — 확인 항목 충족 2/2, 버그 검출력 100%, 결과 상태 정상 완료

이어서:
```
cta diff
cta apply
```

나레이션:
> generate는 먼저 일반 코드가 재료를 모읍니다. 테스트 없는 메서드, 시험해야 할 분기와 예외, 어떤 의존 객체를 mock할지. 그다음 LLM이 테스트를 쓰고, 실제로 실행합니다. 통과하면 게이트 6종이 판정합니다. 기존 assert가 훼손됐는지, 스킵을 붙였는지, 허용 밖 파일을 건드렸는지, 그리고 JaCoCo 커버리지와 PIT 뮤테이션 실측. 여기선 커버리지 100%, 심은 버그 2개 중 2개를 잡았습니다. 생성물은 제안으로만 저장되고, diff로 보고 apply를 쳐야 소스에 들어갑니다.

### 장면 2 — 버그 수정 대응과 영향 범위 (1:30–3:00)

코드 변경 (OrderService.java, applyDiscount):
```
- if (customer.getGrade() == Grade.GOLD && amount.compareTo(THRESHOLD) > 0) {
+ if (customer.getGrade() == Grade.GOLD && amount.compareTo(THRESHOLD) >= 0) {
```
(임계금액과 같은 주문이 할인에서 빠지던 경계 버그를 고친 상황. 녹화 전 브랜치에는 「> 0」 상태를 커밋해 둔다.)

명령:
```
git commit -am "fix: 할인 임계금액 경계 조건 오류 수정 (#4821)"
cta maintain --diff HEAD~1 --impact
```

화면에서 짚을 것:
1. 「① OrderService.applyDiscount」 블록 — 판단 「버그 수정 (확신도 9x%)」, 근거 3줄(커밋 메시지·diff의 「>」→「>=」·시그니처 그대로), 기존 테스트 OrderServiceTest → 통과, 할 일 「재발 방지 테스트 추가」
2. 처리 — 「게이트[regression] 통과 — 수정 전 코드에서 실패함 (정상 — 버그를 잡는 테스트)」
3. 두 번째 예시로 「findById」에 null 방어를 추가한 커밋을 미리 준비해 두었다면 「영향 범위 OrderController.get [high], OrderService.pay [high] …」 줄과 「↳ 영향 범위」 파생 건 ②③④가 이어지는 화면을 보여 준다 (시간이 없으면 미리 찍어 둔 화면 삽입)

나레이션:
> maintain은 git diff에서 바뀐 메서드를 뽑고, 한 건마다 LLM이 의도를 판단합니다. 여기선 커밋 메시지와 diff를 근거로 버그 수정이라고 봤습니다. 조치는 LLM이 아니라 규칙 테이블이 정합니다. 버그 수정이면 재발 방지 테스트. 그리고 이 테스트가 정말 버그를 잡는지, 수정 전 코드에 끼워서 돌려 봅니다. 실패해야 통과입니다. --impact를 켜면 코드 그래프의 호출 관계로 이 메서드를 부르는 곳까지 찾아 파생 테스트를 만듭니다. 호출 관계는 정적 추정이라 확신도를 붙이고, 규칙 테이블 판정에는 쓰지 않습니다.

### 장면 3 — 리팩터링인데 테스트가 깨짐 (3:00–4:15)

코드 변경 (PricingCalculator.java, calculate — 리팩터링하면서 스케일을 바꿔 동작이 달라진 상황):
```
- return subtotal.multiply(rate).setScale(10, RoundingMode.HALF_DOWN);
+ BigDecimal total = subtotal.multiply(rate);
+ return total.setScale(2, RoundingMode.HALF_DOWN);
```

명령:
```
cta maintain --message "refactor: 금액 계산 결과를 변수로 분리해 정리"
```

화면에서 짚을 것:
1. 판단 「리팩터링 (동작 안 바뀜)」, 기존 테스트 실행 → 4건 중 2건 실패
2. 상자 「사람 확인 필요 — 자동으로 고치지 않았습니다」, 실패한 테스트 「기대 1500, 실제 1500.00」, 「확인해 보실 곳 PricingCalculator.java 27행」, 「수정한 테스트 0건 (일부러 안 함)」, 결과 상태 「사람 확인 필요」(exit 3)

이어서 (사람이 "일부러 바꾼 게 맞다"고 답하는 상황):
```
cta resolve <화면에 나온 id> --intended
cta diff
```

화면에서 짚을 것:
3. 「2차 전체 통과」, 「게이트[assert] 통과 — 기존 assert 27개 모두 보존됨 (사람 허용 2건 제외)」
4. diff에서 실패했던 두 메서드의 기대값만 「1500」→「1500.00」으로 바뀌고 나머지는 그대로

나레이션:
> 이번엔 리팩터링인데 테스트가 깨졌습니다. 동작이 실제로 바뀐 겁니다. cta는 기대값을 고치지 않고 멈춥니다. 규칙 테이블에 자동 갱신 행 자체가 없습니다. 무엇이 어떻게 깨졌는지, 어디를 봐야 하는지만 정리하고 종료 코드 3으로 사람에게 넘깁니다. 사람이 일부러 바꾼 게 맞다고 답하면, 실패한 그 메서드만 고칠 수 있게 허용하고 나머지 assert 27개는 게이트가 그대로 지킵니다.

### 장면 4 — 기억과 재현 (4:15–4:40)

명령:
```
cta maintain --message "refactor: 합계 계산을 스트림으로 정리" --plan-only
cta demo
```

화면에서 짚을 것:
1. 「판단 메모 검색: 이름 일치 + 상황 임베딩(text-embedding-3-small)」, 참고 줄에 방금 장면 3의 판단 메모가 붙는다
2. 「cta demo」 — 「LLM: 실호출 없음 — 저장된 호출 기록을 재생」, 몇 초 만에 완료

나레이션:
> 사람이 내린 판단은 메모로 남고, 다음 변경에서 비슷한 상황을 임베딩으로 찾아 참고로 보여 줍니다. 참고일 뿐 규칙은 못 바꿉니다. 그리고 모든 LLM 호출은 기록되고 재생됩니다. CI는 실호출 없이 이 기록으로만 돕니다.

### 마무리 (4:40–5:00)

화면: 수치 요약 (발표 슬라이드 1의 핵심 성과 또는 터미널에 미리 출력해 둔 표)

나레이션:
> 정리하면, LLM은 판단과 작성 두 곳에만 쓰고 가드레일은 전부 코드로 뒀습니다. 실측으로 생성 테스트 커버리지 100%, 결함 세트 검출률 83%, 의도 분류 정확도 100%, 기존 assert 훼손은 0건입니다. 감사합니다.

## 3. 장면별 대체 계획

| 상황 | 대체 |
|---|---|
| 게이트웨이 응답 지연·장애 | 장면 1·2·3은 사전 녹화본으로, 장면 4의 「cta demo」는 실호출이 없어 그대로 진행 |
| 「--impact」 파생 3건이 너무 오래 걸림 | 「cta.toml」에 「[impact] max_callers = 1」로 파생 1건만, 또는 사전 녹화본 삽입 |
| 커버리지·뮤테이션 게이트 대기 | 「--fast」로 생략 가능하나 게이트 통과 장면이 핵심이므로 편집 컷을 권장 |
| resolve가 2회차에도 실패 | 「--hint "기대값을 1500.00 형태로"」 추가 후 재시도. 항목은 삭제되지 않고 유지된다 |
