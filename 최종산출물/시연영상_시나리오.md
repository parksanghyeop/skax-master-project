## 2. 장면별 대본

### 인트로 (0:00–0:30)

화면: 「examples/demo/src/main/java/com/example/demo/order/OrderService.java」를 연다. 「delete」 메서드에 테스트가 없음을 보여 준다. 시간이 있으면 「cta demo」로 저장된 호출 기록 재생(비용 0)을 10초 보여 준다 — 반드시 코드를 바꾸기 전(장면 1 전)에 돌린다.

나레이션:
> Java 코드를 고치면 JUnit 테스트도 같이 고쳐야 합니다. 이걸 LLM에 통째로 맡기면 두 가지 사고가 납니다. 기존 테스트의 기대값을 몰래 고쳐 통과시키거나, 리팩터링으로 동작이 바뀐 걸 덮어 버립니다. Code Test Agent, cta는 LLM을 판단과 작성 두 곳에만 쓰고, 나머지 판정은 전부 일반 코드가 합니다. 네 장면으로 보여 드리겠습니다.

### 장면 1 — 테스트 생성 (0:30–1:30)

명령 3·4·5번.

화면에서 짚을 것:
1. 「[1/4] 재료 수집」 — 테스트 없는 메서드 「delete」 선정, 확인 항목 2개(분기 1, 예외 1)
2. 「[2/4] 파라미터 객체 만드는 법 확인」 — OrderRepository → mock 사용, 「적용 스킬: junit5-mockito」
3. 「[3/4] 테스트 작성」 — LLM 호출 → 샌드박스 실행 → 통과 → 게이트[assert]·[skip]·[scope]·[coverage]·[mutation] 통과 (대기 구간 편집 컷)
4. 「[4/4] 품질 확인」 — 확인 항목 충족 2/2, 버그 검출력 100%, 「결과 상태: 정상 완료」
5. 「cta diff」에서 새 테스트 2개, 「cta apply」로 반영

나레이션:
> generate는 먼저 일반 코드가 재료를 모읍니다. 테스트 없는 메서드, 시험해야 할 분기와 예외, 어떤 의존 객체를 mock할지. 그다음 LLM이 테스트를 쓰고 실제로 실행합니다. 통과하면 게이트가 판정합니다. 기존 assert가 훼손됐는지, 스킵을 붙였는지, 허용 밖 파일을 건드렸는지, 그리고 JaCoCo 커버리지와 PIT 뮤테이션 실측. 커버리지 100%, 심은 버그 2개 중 2개를 잡았습니다. 생성물은 제안으로만 저장되고 apply를 쳐야 소스에 들어갑니다.

### 장면 2 — 버그 수정 대응과 영향 범위 (1:30–3:00)

scene2가 넣는 변경 (OrderService.java, findById):
```
+ if (id == null) {
+     throw new IllegalArgumentException("id required");
+ }
  return repository.findById(id).orElseThrow(() -> new OrderNotFoundException(id));
```
커밋 메시지 「fix: findById에 null id 방어 추가」. findById는 컨트롤러 1곳 + 같은 클래스 3곳(pay·cancel·updateAmount)이 호출하므로 영향 범위가 잘 보인다.

명령 6·7·8·9번.

화면에서 짚을 것:
1. 「① OrderService.findById」 — 판단 「버그 수정 (확신도 9x%)」, 근거(커밋 메시지·null 방어 추가·시그니처 그대로), 기존 테스트 OrderServiceTest → 통과
2. 「영향 범위 OrderController.get [high], OrderService.cancel [high], OrderService.pay [high], OrderService.updateAmount [high] (정적 추정)」
3. 「② OrderController.get ↳ 영향 범위 (OrderService.findById 변경의 호출자)」 ③ cancel ④ pay — 파생 건 3개
4. 처리 — 「게이트[regression] 통과 — 수정 전 코드에서 실패함 (정상 — 버그를 잡는 테스트)」, 컨트롤러 테스트 파일은 새로 생성됨
5. 「cta diff」에 제안 2건, 「cta apply --all」

나레이션:
> maintain은 git diff에서 바뀐 메서드를 뽑고 한 건마다 LLM이 의도를 판단합니다. 커밋 메시지와 diff를 근거로 버그 수정이라고 봤습니다. 조치는 LLM이 아니라 규칙 테이블이 정합니다. 버그 수정이면 재발 방지 테스트. 이 테스트가 정말 버그를 잡는지 수정 전 코드에 끼워서 돌려 봅니다. 실패해야 통과입니다. --impact를 켜면 코드 그래프의 호출 관계로 이 메서드를 부르는 곳까지 찾아 파생 테스트를 만듭니다. 컨트롤러엔 테스트가 없었는데 새로 생겼습니다. 호출 관계는 정적 추정이라 확신도를 붙이고 규칙 테이블 판정에는 쓰지 않습니다.
